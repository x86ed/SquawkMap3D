## Context

`RecordPanelHero.tsx` currently renders either a real Planespotters photo (linked, credited) or a static "✈" placeholder glyph when no photo exists — see its doc comment and `styles.iconBlock`. `PlaneCard.tsx` already vendors a separate live 3D pipeline (`planeCardFrontArt.ts`'s `loadAircraftGltfScene`/`mountCardArt`, backing the front face's flip-hover silhouette) and a live `ResizeObserver`-driven scale correction in `AircraftOverlay.tsx`; this change adds a *second*, independent live-3D mount point (the compass card) rather than reusing `PlaneCard`'s.

`plens-win/Card` (fetched and read directly from GitHub for this design — `packages/core/src/compass-track-card.ts`, `.types.ts`, `credit-link.ts`, `packages/compass-track-three/src/index.ts`, re-checked after upstream PR #10 "change how unknown author functions") is a `"private": true` npm workspace, never published to the registry. Its `compass-track` card kind is two cooperating pieces:
- `@card/core`'s `buildCompassTrackCard(input)` returns a static HTML string shell: a mount `<div id="card-compass-track-slot">`, three HUD `<div>`s (heading/pitch, lat/lon, and a bottom-right credit HUD), pre-populated from `input.initialState`. The credit HUD's link markup is built by the shared `creditLinkMarkup()` helper (`credit-link.ts`, also used by the `aircraft` card kind's own model/author credit): when `model.modelerName`/`model.modelerProfileUrl` are both non-blank it renders a resolved `@{modelerName}` link to `modelerProfileUrl`; when either is blank, it renders a "+ Add a model" call-to-action linking to `model.modelerAddUrl` (or, if that's also unset, an unlinked "+ Add a model" placeholder span with no CTA). This blank/CTA handling is now entirely upstream's own built-in behavior — as of PR #10 the CTA is not something this app needs to fabricate.
- `@card/compass-track-three`'s `mountCompassTrackCard(slot, model, initialState)` finds that shell's mount slot and HUD elements (via the stable exported ids/classes), loads `model.modelUrl` (a `.glb`) with three.js's `GLTFLoader`, and runs a continuous animation loop: tweens toward whatever telemetry was last pushed via the returned handle's `update(state)`, toggles a named gear mesh group by altitude. It only overwrites the credit link's text/href (from `model.modelerName`/`model.modelerProfileUrl`) when *both* are non-blank — confirmed directly in its current source (`if (creditLinkEl && model.modelerName.trim() && model.modelerProfileUrl.trim())`) — so the blank-model "+ Add a model" CTA markup `buildCompassTrackCard` already rendered is left untouched by mount rather than being clobbered. `dispose()` tears the whole scene down.
- `RarityTier` and `RARITY_TIER_STYLES` in `@card/core` are a byte-for-byte port of this app's own `aircraftRarity.ts` nine-tier taxonomy (confirmed from the vendored source's own doc comment) — no mapping/adapter needed, `SelectedAircraftInfo.rarityTier` passes straight through.

`CompassTrackModel` (in `compass-track-card.types.ts`) now has an explicit optional `modelerAddUrl?: string` field for exactly this app's use case: "Call-to-action URL for the bottom-right HUD's `UNKNOWN` placeholder when `modelerName` or `modelerProfileUrl` is blank." No DOM reach-in is needed — the whole credit-vs-CTA behavior is a pure function of what this app puts in the `CompassTrackModel` it passes in.

There is currently no per-type 3D model dataset in this app at all (the existing `.glb` scenegraph layer in `animatedAircraftScenegraphLayer.ts`/`constants.ts` is for the live map's moving-aircraft icons, keyed by category/type for a different rendering pipeline, and carries no modeler-credit metadata). There is also no app settings/config surface for external URLs beyond build-time `NEXT_PUBLIC_*` env vars (`mapStyles.ts`, `constants.ts`).

## Goals / Non-Goals

**Goals:**
- Replace `RecordPanelHero`'s blank placeholder with a live compass card by default when no photo exists, toggleable back to photo once one loads.
- Vendor and wire up `plens-win/Card`'s `compass-track` card kind with this app's own live telemetry for the selected aircraft.
- Establish a small per-ICAO-type(+variant) 3D model registry (with one default/generic stand-in entry) that the compass card's `model` input is built from.
- Add configurable, optional deep-link "Edit"/"create a model" affordances into three external CRUD UIs this app doesn't own or build.

**Non-Goals:**
- Building or hosting the CRUD pages themselves (model/type/aircraft editing UIs) — purely external, out of scope.
- Any editing controls inside the compass card beyond what `plens-win/Card` itself renders (explicit proposal constraint).
- Authoring new `.glb` 3D models for every ICAO type — one default/generic stand-in model ships with this change; real per-type models arrive over time via the (external) model CRUD flow this change only links to.
- Changing `PlaneCard`'s existing front-face 3D art pipeline (`planeCardFrontArt.ts`) — the compass card is a wholly separate mount.

## Decisions

**Vendor `@card/core` + `@card/compass-track-three` source rather than depend on the private npm packages.** Both packages are `"private": true` (confirmed in the fetched `package.json`s) and unpublished — an `npm install @card/core` is not possible. Rather than a git-URL dependency into an unbuilt monorepo (the workspace's `dist/` outputs aren't committed; building requires running the whole workspace's `tsc` scripts), vendor the two packages' `src/` files directly under this app (e.g. `components/map/overlay/compassCard/vendor/`), matching the existing vendoring precedent (`aircraftShapes.ts`'s doc comment: vendored from `RexKramer1/AircraftShapesSVG`, regenerated by a manual script, "not part of the build/CI"). Re-exports keep the vendored module boundary identical to the upstream package split (`core` vs `compass-track-three`) so a future upstream diff stays easy to re-apply by hand. `three` and `GLTFLoader` are already effectively a dependency of this app's existing `.glb` scenegraph pipeline (`animatedAircraftScenegraphLayer.ts`), so no new runtime dependency beyond the vendored card code itself.
  - *Alternative considered:* fork-and-publish to a private registry — rejected as unnecessary process overhead for ~400 lines of vendored source with no near-term upstream churn expected.

**New `CompassTrackModel` registry, keyed by ICAO type designator (+ optional variant), mirrors `aircraftShapes.ts`'s shape.** A new `components/map/overlay/compassCard/compassTrackModels.ts` (data-driven from a JSON manifest, same pattern as `aircraftShapes.json`) maps `typeDesignator` (optionally refined by `variant`) to a registry entry (`modelUrl`, `gearMeshGroupName`, `gearDeploymentAltitudeMeters`, `modelerName?`, `modelerProfileUrl?`); `rarityTier` is filled in per-selection from `SelectedAircraftInfo.rarityTier`, not stored in the manifest (it's per-aircraft, not per-type). A lookup miss returns one shared default/generic stand-in entry (a plain, unauthored placeholder `.glb`) with `modelerName`/`modelerProfileUrl` both omitted — the same "no exact match" fallback shape `aircraftShapes.ts`'s `getAircraftShape` already uses for its category/"Unidentified" fallbacks, kept as its own dataset since the compass card's 3D asset and the top-view SVG silhouette are unrelated asset pipelines.
  - *Alternative considered:* reuse `aircraftShapes.ts`'s existing manifest/keys for the compass model too — rejected because that manifest has no room for `modelerName`/`modelerProfileUrl`/gear metadata and mixes concerns between two independent asset pipelines (2D outline vs. 3D card model).

**Credit-HUD-vs-"create a model" CTA is the card's own native `modelerAddUrl` behavior — no DOM patch, no fork.** `CompassTrackModel` already has a `modelerAddUrl?: string` field built exactly for this (per the design's Context section) and `buildCompassTrackCard`/`creditLinkMarkup` already render the right thing from it: an "@handle" credit link when `modelerName`/`modelerProfileUrl` are set, a "+ Add a model" CTA to `modelerAddUrl` when they're blank and `modelerAddUrl` is set, or an unlinked placeholder when all three are blank — and `mountCompassTrackCard` never overwrites that markup unless both credit fields are non-blank. This app's wrapper therefore only needs to build the `CompassTrackModel` object it passes in: leave `modelerName`/`modelerProfileUrl` unset for the default stand-in (or any registry entry with no recorded credit) and set `modelerAddUrl` to the configured model CRUD URL (built from ICAO + variant, per `aircraft-record-edit-links`) whenever that endpoint is configured, omitting it when not (so an unconfigured endpoint yields the library's own unlinked placeholder — no dead link, no extra logic needed here). This supersedes an earlier version of this design that planned a post-mount DOM patch against the credit HUD's exported id/class constants — no longer needed now that upstream (`plens-win/Card` PR #10, "change how unknown author functions") added first-class support for this exact case.
  - *Alternative previously considered, now moot:* a post-mount DOM patch reaching into the credit HUD by its exported id/class constants — this predated upstream's `modelerAddUrl` support; superseded once that landed.

**`RecordPanelHero` owns view-mode state (`"photo" | "compass"`) and mount/dispose lifecycle for the compass card, mirroring its existing photo-fetch `useEffect` pattern.** Default view is `"photo"` when a photo has loaded for the current hex, else `"compass"`; switching hex resets to that same default rather than preserving the user's last manual toggle across different aircraft (consistent with the panel's existing per-hex photo fetch/reset). The toggle control itself only renders once both a photo *and* a resolved `CompassTrackModel` view are available to switch between — i.e. it's hidden whenever there's truly nothing to toggle to (no photo case still shows the compass card as the sole view, matching the proposal's "toggle... only once a photo becomes available" behavior). `mountCompassTrackCard`'s handle is disposed on hex change, view-mode switch away from compass, and unmount — never left running invisibly (mirrors `AircraftOverlay.tsx`'s existing care around `ResizeObserver` cleanup).

**Live telemetry feed for `CompassTrackState`:** `SelectedAircraftInfo` gains `lat`/`lon` (currently computed internally in `buildSelectedAircraftInfo` for `distanceNm` but not exposed — trivial to also expose) and a derived `pitchDegrees`. ADS-B carries no real pitch; this app estimates it the same way most consumer flight trackers do — `pitchDegrees = atan2(verticalRate_ms, groundSpeed_ms)` in degrees, clamped to a small sane range (e.g. ±20°) and `0` when `groundSpeed` is `0`/`undefined` — clearly a visual approximation, not a claim of real attitude data, and called out as such in the exported helper's doc comment. Units: `altitude` (feet) → meters, `groundSpeed` (knots) → m/s, `verticalRate` (feet/min) → m/s, converted once in the same helper. `update()` is called on every existing per-aircraft poll tick (same cadence `TelemetryMarquee`/sparklines already update on) — no new polling loop.

**CRUD endpoint URLs are build-time `NEXT_PUBLIC_*` env-var templates, following the existing `NEXT_PUBLIC_FEEDER_URL`/`NEXT_PUBLIC_OPENAIP_API_KEY` convention** (`constants.ts`'s doc comment on `NEXT_PUBLIC_FEEDER_URL` explicitly frames this as the established pattern for "low-sensitivity" values, contrasted with `feederUuid.ts`'s deliberate `localStorage`-only real-credential handling). Each template is a URL containing `{icao}`/`{variant}`/`{hex}` placeholders (e.g. `NEXT_PUBLIC_MODEL_CRUD_URL="https://models.example.com/edit?icao={icao}&variant={variant}"`), substituted client-side by a small `buildCrudUrl(template, params)` helper that URI-encodes each value. Any edit/CTA control whose corresponding env var is unset simply doesn't render (per proposal) — checked once via a shared `getModelCrudUrl()`/`getTypeCrudUrl()`/`getAircraftCrudUrl()` trio in a new `crudLinks.ts`, mirroring `constants.ts`'s existing `getOpenAipApiKey()`-style accessor functions.

## Risks / Trade-offs

- **Estimated pitch is not real attitude data** → could look subtly wrong for unusual flight profiles (steep turns, aerobatics). Mitigation: clamped range + doc comment framing it explicitly as an approximation; acceptable given the proposal only asks for a "live and useful" empty-state visual, not flight-instrument accuracy.
- **One default/generic stand-in `.glb` for every type with no registered model** → most aircraft initially show a generic shape in the compass card (mirrors `aircraftShapes.ts`'s own "Unidentified" fallback reality). Mitigation: this is precisely what the "create a model" CTA is for — the CTA is the intended on-ramp for the registry to fill in over time, not a bug to fully solve in this change.
- **Two independent live 3D pipelines now mounted in the overlay at once** (`PlaneCard`'s existing front-art mount + the new compass card) when both are visible in a wide-viewport layout → additional GPU/CPU cost per open overlay. Mitigation: the compass card only mounts when `RecordPanelHero`'s view mode is `"compass"` (not both views mounted simultaneously), same restraint `PlaneCard`'s own flip-card art already applies.

## Open Questions

- Real per-type `.glb` model assets and their modeler credits are out of scope for this change to author — the registry ships with (at most) a handful of hand-picked examples plus the default stand-in; growing it is expected to happen through the external model CRUD flow this change links to.
- Exact visual styling/placement of the "create a model" CTA within the credit HUD's footprint is left to implementation to match `RecordPanelHero`'s existing photo-caption styling rather than specified pixel-for-pixel here.
