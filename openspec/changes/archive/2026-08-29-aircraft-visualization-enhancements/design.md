## Context

The aircraft layer (`components/map/aircraftLayer.ts`, `aircraftIcons.ts`, `aircraftRarity.ts`, `aircraftShapes.ts`) currently renders every aircraft as a single deck.gl `IconLayer` tinted by a fixed altitude-only color ramp, with a track `PathLayer` sharing the same ramp, plus a selection glow. Icon selection/click state, camera-follow, and the `AircraftOverlay` drawer (`components/map/overlay/AircraftOverlay.tsx`) already exist and are out of scope to restructure. This change reworks the icon layer's color model, altitude positioning, camera-responsive tilt, rotorcraft animation, hit-testing, and hover affordance — all still 2D/2.5D — as groundwork before a later, separate change adds true 3D aircraft meshes (per the proposal's framing: "prior to adding in the 3d").

Two reference images from the request were fetched and inspected directly:
- The altitude color legend is a single continuous gradient bar with labeled stops at 0 / 500 / 1,000 / 2,000 / 4,000 / 6,000 / 8,000 / 10,000 / 20,000 / 30,000 / 40,000+ ft, running orange → yellow → green → cyan → blue → magenta (a tar1090-style "color by altitude" ramp), not the app's current 2-stop cyan→gold ramp.
- The hover tooltip is a small dark rounded-rect popup, two lines: `{callsign} · {type}` bold on line one, `{altitude} ft · {speed} kt` on line two.

## Goals / Non-Goals

**Goals:**
- Three switchable icon/track color modes (rarity, altitude, airspeed) with a matching legend (bottom-right) and 2-button control (bottom-left), each independently docked to the `AircraftOverlay` drawer.
- Aircraft altitude position visually consistent with the map's existing 3x terrain exaggeration.
- A camera-pitch-responsive tilt cue on icons, an animated rotor accent for rotorcraft positioned at their real altitude, a larger click/hit target, and a hover tooltip.

**Non-Goals:**
- True 3D aircraft meshes/models (explicitly deferred to a follow-up change).
- Changing the feeder data contract (`aircraft.ts`) — every mode/feature derives from fields already on `Aircraft`.
- Redesigning `AircraftOverlay`/`PlaneCard` internals — this change only makes the new control+legend dock to the drawer's existing open/close state.

## Decisions

### Decision 1: Color-mode state lives in `MapView`, resolution logic lives in `aircraftIcons.ts`
A new `colorMode: "rarity" | "altitude" | "airspeed"` state (default `"altitude"`, closest to current behavior) is added alongside `MapView`'s existing selection/visibility state, passed into `buildAircraftLayers`. A single `resolveAircraftColor(aircraft, mode)` function in `aircraftIcons.ts` dispatches to `rarityToColor` (new, wraps `RARITY_TIER_STYLES.color` — reused, not duplicated), `altitudeToColor` (rewritten, see Decision 2), or `airspeedToColor` (new, see Decision 3). `aircraftLayer.ts`'s `IconLayer.getColor`/track `getColor` call this instead of hardcoding `altitudeToColor`.

**Post-implementation correction**: getting `resolveAircraftColor`'s return value into `getColor` wasn't sufficient on its own — deck.gl's `IconLayer` fragment shader only tints an icon by `getColor` when its atlas-mapping entry sets `mask: true` (otherwise it renders the atlas texture's own baked pixel color verbatim, ignoring `getColor`). `aircraftIcons.ts`'s `IconAtlasEntry`/`buildAircraftIconAtlas` didn't set this, so every icon rendered its baked-white texture color literally regardless of color mode, for the entire icon layer's history predating this change too — not a regression introduced here, but this change is what surfaced it (a user-visible "icons stay white" report once color modes made icon tinting an expected, checked behavior). Fixed by adding `mask: true` to every atlas mapping entry.

### Decision 2: Altitude ramp is rewritten to match the reference gradient's exact stops
`ALTITUDE_COLOR_LOW`/`ALTITUDE_COLOR_HIGH` (a flat 2-color lerp) are replaced with a multi-stop gradient function using fixed `[ft, rgb]` control points at 0/500/1,000/2,000/4,000/6,000/8,000/10,000/20,000/30,000/40,000ft (orange → yellow → green → cyan → blue → magenta, sampled from the reference image), linearly interpolated between adjacent stops and clamped beyond 40,000ft. This is a **BREAKING** visual change to the current default aircraft tint — acceptable since altitude was already the default color and is now one of three equally-weighted modes, not a regression. The same stop table drives the altitude legend bar's CSS gradient, so the legend and live icon colors can't drift apart.

### Decision 3: Airspeed color uses fixed knot thresholds; Mach 1 is approximated
`airspeedToColor(groundSpeedKt)` buckets: grey (stopped/undefined), green <100kt, yellow 100-200kt, orange 200-400kt, red 400-500kt, magenta >500kt, hot pink above a `MACH1_APPROX_KTS` constant (~660kt, sea-level speed of sound). True Mach depends on true airspeed, altitude, and outside air temperature, none of which the feeder provides (only ADS-B ground speed) — this is a documented simplification, not a physically exact Mach computation.

**Post-implementation correction**: the legend originally rendered this as a straight horizontal gradient bar (matching the altitude/rarity legends' shape) with 7 range-text tick labels ("100-200kt", etc). The user flagged it as illegible (labels wider than their column, overlapping) and separately asked for a real speedometer *arch*, not a bar. `ColorModeLegend.tsx`'s `AirspeedGauge` now renders a half-circle dial: two nested CSS half-circles (an outer one painted with a `conic-gradient` swept over exactly the visible 180°, an inner one solid-filled with the legend's own background to punch out a ring) with short numeric tick labels ("0"/"100"/"200"/"400"/"500"/"M1"/">M1") placed by simple trigonometry around the same pivot the arc sweeps around. Plain CSS, no SVG/canvas — consistent with every other legend variant.

### Decision 4: Rarity mode reuses `RARITY_TIER_STYLES`, legend reuses `PlaneCard`'s 9-tier styling
No new rarity color table — `aircraftRarity.ts`'s existing `RARITY_TIER_STYLES`/`computeRarityTier` are the single source of truth for both the icon tint and the legend's 9 tier cards, keeping the map layer and `PlaneCard` visually identical for the same aircraft.

**Post-implementation correction**: the legend's rarity swatches initially used a flat `background: RARITY_TIER_STYLES[tier].color` — visually inconsistent with `PlaneCard`'s actual per-tier gradient card frame (`PlaneCard.module.css`'s `.aircraftRarityFrame[data-tier]`, a diagonal `highlight → color` blend, with mythic/apex overriding with their own conic/white-ramp formulas). Added `rarityTierGradient(tier)` to `aircraftRarity.ts`, reproducing those exact CSS formulas from the same `RARITY_TIER_STYLES` source (mythic/apex hardcoded verbatim to stay byte-for-byte in sync with the CSS, since they aren't derivable from `color`/`highlight` alone) — the legend swatches now use it, so they visually match the cards exactly rather than approximating them with a flat fill.

### Decision 5: Control and legend dock independently, at opposite bottom corners
Originally the control and legend shared one bottom-left stack (per the acceptance criteria's original wording), each reading the same open/closed signal `AircraftOverlay.module.css`'s `.drawer[data-open]` exposes and repositioning via a CSS transform keyed off it — no JS geometry measurement, matching the codebase's existing pattern of state-driven CSS attributes.

**Post-implementation correction**: once the airspeed legend became a tall arc gauge (Decision 3's correction), stacking it above the control made the combined group crowd/overlap the buttons — and the user asked for the legend to move to the bottom-right specifically to avoid that. Split into two independent docks, `AircraftColorDock` (control, bottom-left) and `ColorModeLegendDock` (legend, bottom-right), each still driven by its own `data-drawer-open` CSS attribute (same drawer-docking mechanism, now applied twice, at opposite corners, above the drawer's top-left and top-right edges respectively). Moving the legend to the bottom-right surfaced a second, unrelated pre-existing collision: `MapView.tsx`'s own top-right layer-toggle button column (`.controls`) is tall enough on a typical viewport to reach down near the bottom-right corner too. Rather than measuring that column's width at runtime (a `ResizeObserver`, more machinery than this warrants), `ColorModeLegendDock.module.css` uses a static `right: 210px` — the column's rendered width is driven by its longest button's text content ("Hide special use airspace"/"Hide airspace boundaries"), not viewport width, so it's effectively constant; documented as a coupling to revisit if that longest label changes meaningfully.

### Decision 6: Terrain-exaggeration-aware altitude — full uniform scaling, not ground-relative-only
`aircraftLayer.ts`'s `getPosition` (icon layer, glow layer, and track `PathLayer`) and `radarSweep.ts`'s aircraft dots multiply their altitude-derived z term by `TERRAIN_EXAGGERATION` (already `3` in `constants.ts`), i.e. `altitude * FEET_TO_METERS * TERRAIN_EXAGGERATION`, so aircraft height reads consistently against the equally-stretched terrain mesh. Considered exaggerating only the ground-elevation component (leaving above-ground-level clearance unscaled, which is arguably more physically "correct" since only the terrain mesh itself is exaggerated) but rejected as more complexity than the acceptance criterion ("match terrain exaggeration with plane altitude") asks for; revisit if high-altitude cruise traffic reads as visually wrong (e.g., appearing implausibly high above flat terrain) once implemented.

### Decision 7: Camera-pitch tilt via `billboard: false`, world-space rotation
The icon's `IconLayer` uses `billboard: false` (icon lies flat in its own ground plane, rotated by `getAngle`/track) so deck.gl's ordinary camera projection foreshortens/tilts it as the map pitches — a stand-in for true 3D mesh geometry, which remains out of scope (deferred to the follow-up 3D-aircraft-models change). Under `billboard: false`, the icon's rotation is applied in world/"common" space *before* the view-projection matrix, so it automatically follows the camera's bearing along with everything else — no manual bearing compensation needed, and `getAngle` is exactly `-(track)`, unchanged from the very first implementation.

**Mid-change detour (now resolved)**: this was briefly reverted to `billboard: true` after live testing seemed to show it breaking icon color legibility at this app's typical 60-85° pitch. That diagnosis was wrong. The real cause, found afterward, was a completely unrelated atlas-mapping bug (`aircraftIcons.ts`'s `IconAtlasEntry` never set `mask: true` — see Decision 1's correction) that made every icon render its baked-white texture color literally, *regardless* of `billboard`. The revert briefly needed a `bearingDeg` compensation added to `getAngle` (since `billboard: true` rotates in pure screen-pixel space, which does *not* automatically follow camera bearing — a real, separate deck.gl quirk, confirmed against `icon-layer-vertex.glsl.ts`) to fix a bearing-tracking bug it introduced; once `billboard: false` was restored, that compensation was removed too, since world-space rotation doesn't need it. Net effect: `billboard: false` was the right call from the start; the detour was two compounding-but-separate misdiagnoses (color legibility misattributed to billboard, then a real bearing bug in the wrong-fix's own workaround) that both resolved themselves once reverted back to the original design.

### Decision 8: Rotorcraft rotor accent is a second deck.gl `IconLayer`, not a MapLibre `Marker`
Originally implemented as a MapLibre `Marker` (DOM/SVG, `rotationAlignment: "map"`, CSS `@keyframes spin`) for ADS-B category `A7` aircraft — chosen because the deck.gl icon atlas is a canvas rasterized once at layer-mount time and can't animate a sub-element, and to avoid a `requestAnimationFrame` loop. **Reworked** after the user reported the rotor wasn't tracking the rotorcraft's altitude or pitch: MapLibre `Marker`s are fundamentally 2D, ground-plane-projected DOM elements with no altitude/elevation API at all (this was a known, documented limitation from the start, not a bug in the marker code itself) — for an airborne helicopter, the accent would sit at the aircraft's ground-projected lon/lat while the real icon (positioned via `altitudeToRenderMeters`) floated above it, visibly detached, worse the higher the aircraft and the more the camera tilted.

Replaced with a second `IconLayer` (`AIRCRAFT_ROTOR_ACCENT_LAYER_ID` in `aircraftLayer.ts`), built inside the same `buildAircraftLayers` call, reusing the *exact* `getPosition`/`billboard: false` the main icon uses — not a parallel computation that could drift, the same one. A new `ROTOR_ACCENT_KEY` atlas entry (`aircraftIcons.ts`'s `drawRotorAccent`, a plain white cross+hub drawn directly to canvas, tinted via a fixed light-grey `getColor`) supplies its sprite. The "spin" is no longer a continuous CSS animation: `getAngle` is derived from `Date.now()` (`(Date.now() / 7) % 360`), so it changes every ~1s poll along with everything else — a large enough step (~143°) to read as spinning, and consistent with the rest of this app's motion language, where aircraft themselves only move once per poll rather than smoothly interpolating (a continuously-animated rotor on a "teleporting" parent icon would have looked mismatched anyway). Alternatives still rejected for the reasons Decision 8 originally gave: re-rasterizing the atlas cell per frame (breaks the atlas's build-once design) and a `requestAnimationFrame`-driven continuous rotation (real per-frame cost for a cosmetic accent, mirroring `radarSweep.ts`'s loop unnecessarily) — the wall-clock-at-poll-time approach gets a "spinning" read without either.

### Decision 9: Clickability via deck.gl's built-in `pickingRadius`, not a synthetic hit layer
The `MapboxOverlay`/`Deck` instance's `pickingRadius` (pixels) is bumped from its default (0) to a value comfortably larger than small/distant icons, giving every aircraft a bigger effective click radius with no new layer. This is deck.gl's own built-in mechanism for exactly this problem. Fallback considered — a second, larger, fully transparent `ScatterplotLayer` purely for picking — noted as a follow-up if `pickingRadius` alone proves ambiguous in dense traffic (overlapping aircraft), but not implemented up front to keep the change minimal.

### Decision 10: Hover tooltip via `IconLayer.onHover`, matching the captured reference exactly
A new `onHover` handler (parallel to the existing `onClick`) drives a small piece of React state (hovered aircraft or `null`) in `MapView.tsx`, rendered as a lightweight, absolutely-positioned tooltip (not reusing `AircraftOverlay` — that stays click-to-select-only) near the cursor: bold `{callsign ?? registration} · {typeDesignator}` on line one, `{altitude} ft · {groundSpeed} kt` on line two, styled as a small dark rounded-rect matching the captured reference image. State updates only on hovered-object identity change (not every pixel of pointer movement) to avoid excessive re-renders.

## Risks / Trade-offs

- [Foreshortening pitch cue isn't true 3D rotation] → Acceptable, explicitly scoped as a stand-in ahead of the separate 3D-aircraft-models change; documented in code as an intentional limitation.
- [Airspeed's Mach-1 threshold is a fixed-knots approximation, not true Mach] → Documented simplification; the feeder never exposes true airspeed/OAT needed for a real Mach computation.
- [Altitude gradient stops are hand-sampled from a reference image, not colorimetrically derived] → A close visual match is what was asked for; stops are pinned constants (like the existing rarity octile thresholds), not recomputed.
- [Rotor accent's per-poll (~1s) spin step, not a continuous animation] → Deliberate, matching this app's own aircraft-position update cadence (see Decision 8); revisit with a dedicated `requestAnimationFrame` loop if a smoother spin is wanted later.
- [`pickingRadius` increase can create pick ambiguity when aircraft icons overlap in dense traffic] → deck.gl resolves overlapping picks to the nearest hit under the cursor; acceptable at this app's single-feeder traffic density, revisit with a dedicated hit layer if it proves confusing in practice.
- [`ColorModeLegendDock`'s static `right: 210px` offset is coupled to the top-right toggle sidebar's current longest button label] → Acceptable given that sidebar's width doesn't vary with viewport width, only content; revisit with a `ResizeObserver`-measured offset if that label changes meaningfully.
- [Control and legend docks at narrow viewports] → Each follows `AircraftOverlay`'s existing responsive stacking pattern (the same `760px` breakpoint/`80vh` drawer-height swap) rather than inventing a new one.

## Migration Plan

Purely additive UI/rendering change with no data migration and no feeder contract change. Default color mode is `"altitude"` (closest to current behavior), so existing users see the same default coloring scheme (with the corrected gradient from Decision 2) until they explicitly switch modes. No feature flag — ships as a normal PR; rollback is a plain revert.

## Open Questions

- The proposal's "arrow icon and recenter the view" gang-box button doesn't pin down its recenter target. Defaulting to the existing `handleJumpToLocation` behavior (recenter to the feeder/browser-resolved location, same as the current "My location" control) as the closest existing analog — confirm during implementation if a different target (e.g., `DEFAULT_VIEW`, or the currently-selected aircraft) is actually intended.
- Whether `pickingRadius` alone resolves clickability sufficiently, or a secondary hit-testing layer (Decision 9's fallback) is also needed, is left to be settled by testing against real traffic during implementation.
