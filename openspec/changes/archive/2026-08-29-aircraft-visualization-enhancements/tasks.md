- [x] 11.3 **Follow-up fix**: after the billboard revert, the user reported icons were *still* rendering white — the real root cause was separate from billboard, and 11.2's pixel samples had almost certainly caught the track trail's endpoint (which does get tinted, via `PathLayer`) rather than the icon body itself. Actual cause: deck.gl's `IconLayer` fragment shader only applies `getColor` tint when an atlas-mapping entry has `mask: true` (`mix(texColor.rgb, vColor.rgb, vColorMode)`, `vColorMode` sourced straight from the mapping's `mask` flag); without it, the shader renders the atlas texture's own baked pixel color verbatim, ignoring `getColor` entirely. `IconAtlasEntry`/`buildAircraftIconAtlas` in `aircraftIcons.ts` never set `mask`, so every icon (baked solid white specifically so it *could* be tinted) rendered literally white regardless of color mode. Fixed by adding `mask: true` to the `IconAtlasEntry` interface and every mapping entry. Re-verified via pixel-cropped screenshots showing distinctly orange/red-tinted icon silhouettes (not just track lines) post-fix.
- [x] 11.4 **Follow-up fix**: user reported "the heading of the aircraft got lost when I tilt the view" (a drag-rotate gesture, which changes bearing alongside pitch). Root cause: `aircraftLayer.ts`'s `getAngle: (d) => -(d.track ?? 0)` only pointed the icon the right way when the map's bearing was 0. With `billboard: true`, deck.gl's `IconLayer` vertex shader rotates the icon in pure screen-pixel space and adds it directly to clip-space (`icon-layer-vertex.glsl.ts`) — unlike world-space geometry (the track `PathLayer`, which is unaffected and always pointed correctly), it never passes through the view's own bearing-rotation matrix, so the icon doesn't follow the camera when the user rotates. Fixed by adding a `bearingDeg` param to `buildAircraftLayers` (read from `mapRef.current?.getBearing() ?? 0` at each poll in `MapView.tsx`) and changing `getAngle` to `bearingDeg - (d.track ?? 0)`, which reduces to the original formula at bearing 0. Not independently pixel-verified live (small, fast-moving icons plus this environment's flaky keyboard-rotate/click-precision made a controlled before/after comparison unreliable) — confirmed via deck.gl's actual shader source rather than by observation; the same underlying screen-space-vs-world-space principle is what the rotor marker's `rotationAlignment: "map"` fix already relies on successfully.
- [x] 11.5 **Follow-up fix**: user reported the airspeed gauge "doesn't read properly" and that the rarity gauge "should use the gradients from the cards." Airspeed: the previous 7 range-text tick labels ("100-200kt", "400-500kt", …) were wider than their `flex:1` column in the 260px bar and, combined with `white-space: nowrap`, overlapped illegibly.
