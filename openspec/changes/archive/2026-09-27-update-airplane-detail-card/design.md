## Context

`PlaneCard.tsx`/`PlaneCard.module.css` currently render a single, non-flipping `.aircraftRarityFrame > .aircraftTierCard` face: header row (type badge, manufacturer, model, tightly-cropped silhouette SVG) plus a stat region below (empty state, feeder-UUID form, error state, or the real stat grid/XP bar). A `ResizeObserver`-driven `transform: scale()` contain-fits the whole frame into its grid cell.

**Revision note (post-implementation-review):** an earlier version of this design sourced the flip-card structure from the sibling `iconizer` project's *hand-rolled* `3D-modeler/src/card.ts`/`style.css` (which predated `iconizer` actually consuming the real `plens-win/Card` library) and, believing this app had no 3D-modeling capability, rendered the front face's art as this app's existing flat 2D silhouette. Both turned out to be wrong: (1) that hand-rolled version kept the tier-colored border/badge chrome *static* outside the rotating element, so only the inner content flipped — visibly different from a real flip card, where the whole bordered object rotates; and (2) `iconizer` has since migrated to the actual `plens-win/Card` library (vendored locally at `iconizer/3D-modeler/vendor/card/{core,wireframe-three,aircraft-model-card}`, per `iconizer`'s own `replace-card-preview-with-card-library` change), whose `@card/wireframe-three` package renders a real live 3D wireframe from a `THREE.Scene` — and this app in fact *does* have real vendored 3D models (`public/aircraft-models/*.glb`, already used by the map's `ScenegraphLayer` via `aircraftModels.ts`), just not previously wired into a mini card-scoped renderer. This revision re-sources the port from the actual library and corrects the flip structure and front-face art accordingly (Decisions 1, 2, and 5 below).

## Goals / Non-Goals

**Goals:**
- Port the two-face flip-card DOM structure and CSS (`.card-frame`/`.card-inner`/`.card-face`/`.card-face-front`/`.card-face-back`) from the real `plens-win/Card` library (`@card/core`'s `card.css`/`aircraft-card.js`, vendored locally in `iconizer` at `3D-modeler/vendor/card/core`) into `PlaneCard.tsx`/`PlaneCard.module.css`, translated to this app's CSS Modules naming and React (JSX) authoring instead of the library's template-string HTML — including its per-face gradient border (the whole card flips as one object, not just its inner content).
- Make the back face (current identity+stats content) the default-shown face; hovering flips to the front face (touch-flip parity is out of scope — see Open Questions).
- Preserve the existing whole-card click behavior (open `https://adsb.win/dashboard/aircraft/{TYPE}` in a new tab) across both faces, still excluding clicks on the feeder-UUID form's interactive children.
- Preserve the existing `ResizeObserver` contain-fit scaling behavior, rarity-tier-driven gradient border/glow (including `mythic`/`apex` sheen), and all existing `cardStats`-driven stat-region states (empty, not-configured, invalid-token, error, ok+XP bar) — none of this app's existing data/logic changes, only where that content is rendered.
- Render the front face's art as a real live 3D wireframe of the selected aircraft's vendored `.glb` model (ported verbatim from `@card/wireframe-three`'s `mountCardArt`), falling back to the existing flat 2D silhouette only when the aircraft has no vendored model — matching the library's own fallback behavior (Decision 5).

**Non-Goals:**
- No changes to `aircraftModelCard.ts`, `tierProgress.ts`, `feederUuid.ts`, `manufacturerModel.ts`, `computeTightViewBox`, or any other stats/tier-fetching logic; `PlaneCardProps` gains exactly one new field (`showBack`, see Decision 2) and is otherwise unchanged. (`aircraftModels.ts` and `aircraftShapes.ts` do gain small additions — see Impact/Decision 5.)
- Not adopting `@card/core`/`@card/wireframe-three` as an installed npm dependency (the private `plens-win/Card` repo isn't published/accessible from this app's package registry); the port is a local, attributed re-implementation, matching this app's existing "vendor/port, don't add a runtime dependency for a small self-contained UI piece" pattern (e.g. `aircraftShapes.ts`'s vendored SVGs) — see Decision 1.
- No live reconstruction/tracing capability — this app has no equivalent to `iconizer`'s 3D-modeler tool; the front face's 3D art renders this app's own pre-existing vendored `.glb` models (already used by the map), not a user-built model.
- Not changing the overlay's four-component layout, grid/stacking behavior, or any other overlay component (`RecordPanelHero`, `TelemetryMarquee`, `FlightInfoPane`).

## Decisions

**Decision 1 — Source the flip markup/CSS from the real, vendored `plens-win/Card` library, not a hand-rolled reimplementation.**
`iconizer` originally hand-rolled its own card renderer (`3D-modeler/src/card.ts`/`style.css`) and has since migrated to consuming the actual `plens-win/Card` library (per `iconizer`'s own `replace-card-preview-with-card-library` change), vendored locally at `iconizer/3D-modeler/vendor/card/{core,wireframe-three,aircraft-model-card}` (built `dist/` + a `card.css` reference stylesheet, no network fetch required to read it). This design ports from that vendored library output — `@card/core`'s `aircraft-card.js`/`card.css` for markup/CSS, `@card/wireframe-three`'s `index.js` for the 3D art (Decision 5) — rather than from `iconizer`'s superseded hand-rolled version, since the library is the actual thing the acceptance criteria point at ("the new card library is there: github.com/plens-win/Card") and fixes a real structural bug the hand-rolled version had (Decision 2). Alternative considered: clone/inspect `plens-win/Card` from GitHub directly — unnecessary; the vendored `dist/` output on this machine already *is* that library's real, built code.

**Decision 2 — Each face is a complete bordered card (gradient border included); the whole card flips, not just its inner content.**
An earlier version of this design kept the tier-colored gradient border/glow (`.aircraftRarityFrame`) as a single *static* element wrapping a `.cardInner` that only rotated the plain dark inner content — visibly wrong: the border/badge chrome stayed put while a picture flipped inside it, rather than the card itself flipping. The real library's CSS (`@card/core`'s `card.css`) reveals why: `.card-frame` (this app's `.aircraftRarityFrame`) holds only the `--tier-*` CSS custom properties, `perspective`, and sizing (`width`/`aspect-ratio`) — no border/background of its own. The border/background/box-shadow (previously on `.aircraftRarityFrame`) is instead declared once on a shared `.card-face` class (this app's `.cardFace`) applied to *both* `.card-face-front` and `.card-face-back`, so each face independently renders as a complete bordered card (both inheriting the same `--tier-*` variables from their common `.aircraftRarityFrame` ancestor, so they render identically) — and `.card-inner`/`.cardInner` (`position: absolute; inset: 0`) is what actually rotates, carrying both complete faces with it. This requires `.aircraftRarityFrame` to have a determinate box (neither face is in normal flow anymore, both are `position: absolute; inset: 0` within `.cardInner`) — this design adopts the library's own `width: 320px; aspect-ratio: 5 / 7` for that, replacing the pre-flip version's natural-content-height auto-sizing (a real, acknowledged trade-off — see Risks). Back-face default is a `PlaneCardProps.showBack?: boolean` prop (default `true`), mirrored via `data-show-back`'s mere *presence* (not a `"true"`/`"false"` string value) — matching the library's own boolean-attribute convention (`@card/core`'s `buildAircraftCard`: `showBack ? ' data-show-back' : ''`) exactly, so this stays a drop-in match for the library's CSS contract: `.card-frame:hover .card-inner{rotateY(180deg)}` (generic hover), `.card-frame[data-show-back] .card-inner{rotateY(180deg)}` (rest state when back-default), `.card-frame[data-show-back]:hover .card-inner{rotateY(0deg)}` (hover un-rotates to front) — three rules, ported verbatim (the library's fourth/fifth rules cover a `lockCard` feature this app doesn't need and aren't ported). Alternative considered: keep the border static and only widen what "flips" — rejected; this is the actual bug being fixed here, not a stylistic choice.

**Decision 3 — Whole-card click-through onto both faces, unchanged destination and exclusions.**
The current single-face `onClick` — opening `https://adsb.win/dashboard/aircraft/{typeDesignator}` in a new tab, skipping clicks inside `form, input, button, a` — lives on `.cardInner`, the shared ancestor of both faces (since only one face is interactable at a time given `backface-visibility: hidden`). No new URL scheme is introduced; "the new card library ... on click ... take the user to adsb.win page for the aircraft" describes behavior this component already implements. Alternative considered: link out to the library's `card-front-author`/`card-credit-link` per-operator adsb.win *profile* links instead of the aircraft dashboard — rejected; those link to a different destination (an operator handle this app has no equivalent field for, and this app's card omits the library's credit-line markup entirely — see Impact) and the acceptance criteria specifically asks for "the adsb.win page for the aircraft", the dashboard-per-type-designator URL this card already uses.

**Decision 4 — Badges/pills move onto their respective faces (not a shared static overlay); front face gets its own header layout, not a reuse of the back's.**
The library's back face has its own `.card-badge-row` (rarity + tier badges) as a direct flex-column child of `.card-face-back` (sibling of `.card-content`, sitting on the exposed border strip below it) and the front face has its own `.card-front-pills` (top-left, same badges) plus a mirrored identity block (top-right, manufacturer/name, no ICAO badge, no icon — replaced by full-bleed art). This design keeps that split: `.cardBadgeRow` (renamed from an earlier static, absolutely-positioned `.badgeRow` shared across both faces) is now a normal-flow child of `.cardFaceBack` only, and a new `.cardFrontHeader`/`.cardFrontPills`/`.cardFrontIdentity` renders the front's own header — reusing the existing `.rarityBadge`/`.tierBadge` classes (same visual pill, styled by the same `:has()`-driven tier-color tables, which still work correctly since `.aircraftTierCard` remains a CSS descendant of `.aircraftRarityFrame` regardless of nesting depth) rather than duplicating pill CSS. One fix required beyond a straight port: `.rarityBadge`/`.tierBadge`'s `max-width: calc(100% - 2rem)` + `text-overflow: ellipsis` (needed in the back's wide, centered badge row) gave them a near-zero flex `min-width` inside the front's narrow `.cardFrontPills` column, truncating "LEGENDARY"/"TITANIUM" to "LEG…"/"TITANI…" against the identity block's flex-shrink competition — fixed by unsetting `max-width`/`overflow`/`text-overflow` specifically within `.cardFrontPills` (matching the library's own `.card-pill`, which has no such constraint at all) and giving `.cardFrontPills` `flex-shrink: 0`.

**Decision 5 — Front-face 3D art: port `@card/wireframe-three`'s renderer verbatim, feeding it this app's own vendored `.glb` models instead of a live in-app reconstruction.**
The library's front face isn't a static icon — `@card/wireframe-three`'s `mountCardArt` renders a full-bleed, tier-tinted wireframe of a real `THREE.Scene` (camera angle, ground-plane grid, edge-geometry-per-mesh technique all specific/tuned) from a fixed perspective, falling back to a flat SVG only when no scene is available. This app has no equivalent to `iconizer`'s in-app 3D reconstruction tool, but it *does* have real, already-vendored `.glb` models (`public/aircraft-models/`, fed to the map's `ScenegraphLayer` via `aircraftModels.ts`) — an initial version of this design incorrectly assumed no 3D capability existed at all and rendered the front face with the flat 2D silhouette unconditionally, which doesn't match "the new card library" the acceptance criteria point at. This revision instead: (a) ports `mountCardArt`/`collectMeshes` verbatim into a new `components/map/overlay/planeCardFrontArt.ts` (camera math, grid sizing, disposal — all unchanged from the library); (b) adds `loadAircraftGltfScene(typeDesignator, category)` to that same file, which loads the aircraft's vendored `.glb` via `three`'s own `GLTFLoader` (a new `three`/`@types/three` dependency — this app's *first* three.js usage; the map's existing `.glb` pipeline uses `@loaders.gl/gltf`+deck.gl `ScenegraphLayer`, which parses into a loaders.gl-shaped object, not a `THREE.Object3D` `mountCardArt` can traverse, so a second, independent parse via `three`'s own loader is necessary — cached per model key so repeated selections don't re-fetch/re-parse); (c) exports `resolveModelKeyForTypeAndCategory`/`modelUrl` from `aircraftModels.ts` (a minimal refactor of the existing `Aircraft`-shaped `resolveModelKey`, since `PlaneCard` only has `typeDesignator`/`category`, not a full `Aircraft`) so the front-face loader can reuse the exact same vendored-model resolution the map itself uses (including the category fallback) rather than re-deriving it. When an aircraft has no vendored model (or the load fails), `mountCardArt`'s existing fallback path renders the flat 2D silhouette (`shape.markup`) tinted to the tier color — this app's pre-existing silhouette asset slots directly into the library's own designed fallback, so no separate flat-mode implementation was needed. Alternative considered: keep the flat-silhouette-only front face — rejected per explicit user correction that the 3D model should come from the library's own rendering path, not be silently dropped. Alternative considered: reuse the map's already-parsed `@loaders.gl/gltf` scenegraph objects instead of a second `three`-native parse — rejected; converting a loaders.gl scenegraph into a `THREE.Object3D` graph `collectMeshes`/`EdgesGeometry` can traverse is a non-trivial format bridge for a small, infrequently-mounted card, whereas a second small `.glb` fetch+parse (browser-cached HTTP response either way) is simple and matches the library's own expected input shape exactly.

## Risks / Trade-offs

- [Risk] `.aircraftRarityFrame` switching from natural-content auto-height to a fixed `aspect-ratio: 5 / 7` (required so both absolutely-positioned faces share one determinate box — Decision 2) means the card's height no longer grows/shrinks with its own content the way the pre-flip single face did. → Mitigation: `320px` / `5:7` were chosen to match this card's own pre-flip natural proportions at typical content; the existing `ResizeObserver` contain-fit `transform: scale()` still uniformly scales the whole (now fixed-aspect) frame to fit its grid cell, so the visual regression is limited to "the box shape is now fixed" rather than "content overflows/clips" — no cardStats state was observed clipping during manual verification (see tasks.md).
- [Risk] Reversing which face is "default" vs. the library's own front-default convention could read as an unintentional bug to anyone comparing directly against the upstream library. → Mitigation: this reversal is an explicit acceptance criterion ("make the back not the front show by default"), documented here and in the updated `aircraft-info-overlay` spec scenarios, so it's traceable as intentional.
- [Risk] Hover-only flip has no equivalent on touch devices (no persistent hover state), which could leave touch users unable to ever see the front face. → Mitigation: out of scope for this change per the acceptance criteria (which only specifies default-face and click-through behavior, not touch-flip parity); flagged as an Open Question below rather than silently shipping a touch regression relative to today's card (today's card has only one face, so touch users lose nothing they had).
- [Risk] A second, `three`-native `.glb` parse per modeled aircraft type (alongside the map's existing `@loaders.gl/gltf` parse of the same files) doubles the parse cost for modeled types, and adds a first-time `three`/`GLTFLoader` bundle-size cost to any page rendering `PlaneCard`. → Mitigation: parsed scenes are cached per model key (`gltfSceneCache`) so this cost is paid at most once per type per page load, not per aircraft selection; `PlaneCard` only mounts inside the already-heavy map overlay, which already loads deck.gl/maplibre, so the incremental bundle cost of `three` is proportionally small.
- [Risk] `resolveModelKeyForTypeAndCategory`'s refactor of `aircraftModels.ts`'s existing `resolveModelKey` is a public-API-shaped change to a module the map's own aircraft-rendering pipeline depends on. → Mitigation: `resolveModelKey(aircraft)` now simply delegates to `resolveModelKeyForTypeAndCategory(aircraft.typeDesignator, aircraft.category)` — identical behavior, verified by the full existing test suite passing unchanged (173/173).

## Open Questions

- Should a tap-to-flip (or explicit flip affordance) be added for touch devices in a follow-up, given hover-only flip is unusable on touch? Not addressed by the stated acceptance criteria for this change.
