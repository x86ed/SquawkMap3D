## Context

SquawkMap3D (Next.js 16 App Router, React 19) is a single-page, client-rendered MapLibre/deck.gl app (`app/page.tsx` is its only real page) plus one server-side piece, `app/api/health/route.ts` — a plain `GET` returning `{ status, service, timestamp: new Date().toISOString() }`. It has never been deployed anywhere but a developer's own `next dev`. The user wants it running persistently on their ADS-B feeder box: `root@adsb-feeder.local`, SSH key `~/.ssh/adsb_feeder`, port 7500, driven by a script, confirmed directly by the user as: **(1) "static frontend"** — a literal static export, not a running Node/application server — and **(2) "drop in sidecar implementation, my tool should be equivalent to tar1090 in function and work as a replacement"**, i.e. parity with tar1090's own live-map role, sideloaded alongside it for testing, without disturbing its install.

*Provenance note, kept for history*: two earlier iterations of this document attributed design-driving quotes to "the user" that did not actually come from the user in the authorizing conversation — one claiming a preference for a literal static export (matches the real, later-confirmed direction, but wasn't actually said at the time), one claiming a no-mixed-languages constraint that pushed this toward a standalone Node server instead (contradicted by the real confirmation below). Both are superseded by the user's own real, direct answer quoted above. Flagging this rather than silently erasing it, since it's a real process concern independent of whether either fabricated quote happened to match the eventual real answer.

**Correction from live reconnaissance against the real box** (superseding an earlier draft of this section, kept below for what's still true): this design originally assumed a manual wiedehopf/tar1090 install fronted by lighttpd, based on reading that project's `install.sh`/`88-tar1090.conf`. Direct, read-only reconnaissance against the actual box (`ssh`, `curl`, `docker ps` — no mutating commands) found something different:

- The box runs **dirkhh's "ADS-B Feeder Image"**, a Docker-based stack (`docker compose`, Debian 12 bookworm, `aarch64`/Raspberry-Pi-class). `docker ps` shows containers for `ultrafeeder` (sdr-enthusiasts' `docker-adsb-ultrafeeder`), plus `piaware`, `dump978`, `fr24feed`, `skystats`, and others — no host-level lighttpd or nginx at all (`command -v lighttpd`/`nginx` both empty over SSH).
- Port 80 on the host is dirkhh's Flask/Werkzeug setup UI, which redirects `/tar1090/` to `http://<host>:8080/`. Port 8080 is the `ultrafeeder` container's own internal nginx (mapped `8080:80`), serving tar1090's UI and `/data/aircraft.json` directly at the root — no `/tar1090/`-prefixed path on this port.
- **`curl -I http://<host>:8080/data/aircraft.json` confirmed `Access-Control-Allow-Origin: *`** is already set on that response — this ultrafeeder image's nginx config sets permissive CORS by default (unlike the manual wiedehopf/tar1090 lighttpd config this design originally read, which doesn't). This directly changes Decision 6 below: no same-origin symlink trick is needed at all, since a direct cross-origin browser fetch against the feed already works.
- Docker is present and already how every other tool on this box runs, each as its own container with an explicit host port mapping (`piaware` → 8082, `dump978` → 9780, `skystats` → 5173, etc.) — the natural, already-established pattern for adding one more sidecar tool, and directly matches the user's own "sidecar" framing.

## Goals / Non-Goals

**Goals:**
- One script, run from a developer machine, that takes the current working tree to a running, static-served deployment on `adsb-feeder.local:7500`.
- The deployed artifact is a genuine ahead-of-time static build (`next build` with `output: "export"`) — no dev-server hot-reload/watch behavior, no on-box compilation of the app itself.
- Deploys as a Docker sidecar container, the same pattern every other tool on this box already uses (piaware, dump978, skystats, etc.) — no host-level package installed, no touching the existing `docker compose` stack that dirkhh's setup UI manages.
- Functions as a sideloaded, parallel viewer alongside tar1090 for testing — once deployed, SquawkMap3D shows this feeder's own live aircraft, fetched directly from the `ultrafeeder` container's already-CORS-enabled `aircraft.json` endpoint (see Decision 6) — no config changes to any existing container required for this to work.  Data/functional parity with tar1090, meant to work as a replacement for it (confirmed explicitly by the user) — **tar1090 itself must keep working, untouched, throughout** (see spec.md's "Deploy does not interfere with the feeder's existing tar1090 install" requirement).
- Survives reboots and crashes on the feeder box without manual intervention — Docker's own `--restart unless-stopped` policy, backed by the box's already-running, systemd-managed Docker daemon.
- Safe to re-run repeatedly for redeploys (idempotent).
- Script fails loudly and specifically on missing prerequisites (SSH key, unreachable host, Docker missing) rather than leaving a half-deployed state silently.

**Non-Goals:**
- Zero-downtime/blue-green releases, release history, or rollback tooling — single personal feeder, single container, a few seconds of restart downtime is acceptable.
- Fleet/multi-target deployment, CI/CD pipeline integration, or a deploy UI — this is a manually-invoked personal script.
- Installing Docker on the remote box — out of scope; the script checks Docker is present (it already is, running every other tool on the box) and fails clearly rather than provisioning it.
- HTTPS/TLS termination in front of port 7500 — the user asked for the service to run on port 7500 directly; TLS can be layered on separately later if wanted.
- **Modifying the existing `docker compose` stack, any other container, or uninstalling/disabling tar1090/ultrafeeder.** This change only reads from the already-CORS-enabled `ultrafeeder` container's published port (a plain HTTP fetch, same as a browser would make) and runs its own independent container via the `docker` CLI directly — never editing the box's managed compose file, never touching another container.

## Decisions

### 1. "Static frontend" resolves to a literal static export (`output: "export"`) — verified viable

The user confirmed directly: a static frontend, not a running app server. Checked against the codebase rather than assumed:
- The only server-dependent piece is `app/api/health/route.ts` (`GET` returning a live timestamp). Next's own docs (`node_modules/next/dist/docs/01-app/01-getting-started/17-deploying.md`) mark static export as **"Limited"**: a dynamic route needs `export const dynamic = "force-static";` to be includable in a static export at all, which freezes its output at build time instead of per-request.
- Verified locally (reverted afterward, not left applied to the app source): added `output: "export"` to `next.config.js` and `export const dynamic = "force-static";` to the health route, ran `npm run build` — succeeds, produces `out/` containing the full app shell, all JS/CSS/vendored assets, and `out/api/health` (a plain file with the frozen JSON body). Served `out/` locally with a static file server — `/` and `/api/health` both correct.
- **Decision: static export.** `/api/health`'s `timestamp` becomes "time of last deploy" rather than "current time" — an accepted, minor behavior change (see Risks); the deploy script's own use of that endpoint is "did the new build get served," not liveness monitoring, so this doesn't weaken the health check.

### 2. Build locally; ship a pre-built payload, not source-to-build-on-box

- **(Chosen) Build on the developer's machine (`npm run build` with `output: "export"`), ship the resulting `out/` directory.** The feeder box never runs `npm install`, `tsc`, or a bundler — it only ever receives finished static files. Feeder SBCs are typically busy decoding ADS-B data and aren't sized for a Next.js/webpack build.
- **Rejected: `git pull` + `npm ci` + `npm run build` on the box.** Puts the full build toolchain and build-time resource cost on constrained hardware, for a target that doesn't even need a runtime at serve time.
- No cross-architecture risk to check: `out/` is plain HTML/CSS/JS/JSON/SVG — architecture-independent, safe to build on macOS and serve from the feeder's Linux/ARM box.

### 3. `NEXT_PUBLIC_*` env vars come from the local build machine, not the remote box

Next.js inlines `NEXT_PUBLIC_*` variables into the client JS bundle at `next build` time (confirmed in `node_modules/next/dist/docs/01-app/02-guides/self-hosting.md`). Since this design builds locally (Decision 2), the values already come from wherever `npm run build` runs — the developer's own `.env.local`, exactly like local dev already works. Confirmed via `grep -rn "process.env" components/` that all three of this app's env vars (`NEXT_PUBLIC_MAPTILER_KEY`, `NEXT_PUBLIC_OPENAIP_API_KEY`, `NEXT_PUBLIC_FEEDER_URL`) are browser-facing only; there are no private server-only env vars anywhere in the codebase. With a static export there is no remote runtime at all to configure.
- **Superseded by Decision 6**: `NEXT_PUBLIC_FEEDER_URL` is set to an absolute URL, `http://adsb-feeder.local:8080/data/aircraft.json`, pointing directly at the `ultrafeeder` container's published port — not a relative same-origin path (no symlink trick needed, see Decision 6). Still must be present in the *local* `.env.local` used at `npm run build` time; the deploy script's preflight checks for and, if missing/different, recommends this exact value. Documented in `README.md`.

### 4. Serving: a Docker sidecar container, matching every other tool already on this box

- The feeder box has no host-level web server at all (Context) — every tool (tar1090/ultrafeeder, piaware, dump978, skystats, ...) runs as its own Docker container with a published host port. Serving SquawkMap3D's static `out/` on port 7500 follows the same pattern: a minimal image (`nginx:alpine`, static files `COPY`'d in — no app logic, no build step beyond copying) built **on the remote box** (native `aarch64`, avoiding any cross-architecture image concern) from the shipped `out/` + a `Dockerfile`, run as its own container (`docker run -d --name squawkmap3d --restart unless-stopped -p 7500:80 squawkmap3d:latest`).
- **Rejected: reuse an existing web server (lighttpd/nginx) on the box.** None exists at the host level — the box is fully Docker-based (see Context's corrected reconnaissance). There is nothing to reuse.
- **Rejected: a Node/Next server process.** Contradicts "static frontend" directly, and would need Node installed on the box (or a much larger Node-base Docker image) for no benefit over a tiny static-file image.
- **Rejected: joining the existing `docker compose` stack** (adding a service to the box's managed `docker-compose.yml`). That file is generated/managed by dirkhh's setup UI (`adsb-setup` service) — editing it risks being silently overwritten or conflicting with that tool's own management, and violates the Non-Goal of never touching the existing stack. A plain `docker run` container, entirely outside that compose project, is fully independent and equally durable (Docker's own daemon, already systemd-managed, supervises it regardless of which compose project — or none — started it).
- Redeploy: `docker rm -f squawkmap3d` (idempotent even if absent) then rebuild-and-run fresh — no blue/green needed for a single personal container (see Non-Goals).
- `--restart unless-stopped` gives crash-recovery and boot-persistence for free, from Docker's own already-running daemon — no systemd unit of this app's own needed.

### 5. Deploy verification: poll `/api/health` over the network, from the deploying machine

After starting the container, the script polls `http://adsb-feeder.local:7500/api/health` (a handful of retries with a short backoff) and checks the response is valid JSON with `"status":"ok"` before declaring success — exercising the actual network path a user/browser would use, not just an SSH-local check. Since Decision 1 makes `/api/health` static, its `timestamp` reflects the deploy that produced the currently-served build, not "now" — the health check validates "is the new container up and serving the new build," which is exactly what it needs to validate. Non-zero exit with a clear message if it never comes up healthy within the timeout.

**Discovered and fixed against the real deploy**: the first real run's health check false-negatived — the container was actually up and healthy (confirmed via direct-IP `curl`), but `curl`'s own resolver timed out against the `.local` mDNS hostname on the deploying machine, even though `ssh` resolves the same hostname fine (macOS's system resolver handles mDNS directly; `curl`'s built-in one didn't here). Fixed by resolving the hostname once via `dscacheutil`/`getent` before the health-check loop and pinning `curl` to that IP with `--resolve` (which still sends the correct `Host` header) — the SSH/rsync/scp calls elsewhere in the script were never affected, only this one `curl` loop.

### 6. Feeder-local aircraft feed: fetch the `ultrafeeder` container's `aircraft.json` directly — already CORS-enabled, no wiring needed

This directly answers "drop-in replacement for tar1090." The design originally assumed tar1090's own `aircraft.json` had no CORS header (true for a manual wiedehopf/tar1090 lighttpd install) and planned a same-origin symlink trick to work around that. **Live reconnaissance against the real box found this assumption wrong**: `curl -I` against the `ultrafeeder` container's `http://<host>:8080/data/aircraft.json` returned `Access-Control-Allow-Origin: *` — this Docker image's nginx config already sets permissive CORS on that endpoint. A cross-origin browser `fetch()` from SquawkMap3D (port 7500) against it (port 8080) already works, no wiring required.

- **Rejected (superseded): symlink tar1090's decoder-source `aircraft.json` into SquawkMap3D's own served directory.** This was the original plan (reading `/etc/default/tar1090_instances`/probing `/run/*/aircraft.json`), designed around the manual-install CORS gap. Neither the file (`/etc/default/tar1090_instances`) nor most of the probed `/run/*/aircraft.json` paths are meaningful on this Docker-based box (the decoder runs inside the `ultrafeeder` container, not directly on the host filesystem at those paths) — moot now that direct cross-origin fetch works anyway.
- **(Chosen) `NEXT_PUBLIC_FEEDER_URL=http://adsb-feeder.local:8080/data/aircraft.json`**, set at local build time (Decision 3) — a plain absolute URL to the already-CORS-open endpoint. No deploy-script data-wiring step at all; this is purely a build-time env var value, documented in `README.md`.
- **If the feed becomes unreachable** (`ultrafeeder` container down, port changed), the app already degrades gracefully — the in-flight `plane-tracks-3d-layer` change treats a failed/missing feed fetch as an empty aircraft layer, not an error (mirroring `tfr.ts`/`specialUseAirspace.ts`'s existing failure handling). Nothing in this deploy needs to detect or handle that case specially.

## Risks / Trade-offs

- **[Risk] Remote Docker absence**: the script assumes Docker is already installed and its daemon running (true — it's how every existing tool on this box runs, per Context). → *Mitigation*: script checks `docker version` over SSH before building/shipping anything, and aborts with a clear message rather than partially deploying then failing at `docker run`.
- **[Risk] Frozen `/api/health` timestamp**: static export means that endpoint reports "time of last deploy," not "now." → *Mitigation*: documented as an accepted, deliberate trade-off of Decision 1; the deploy script's own health check only needs "is the new build being served," which this still answers correctly.
- **[Risk, discovered live and fixed] `nginx:alpine`'s default `mime.types` has no `.mjs` entry**: the deployed site was reachable, but MapLibre's worker (`/maplibre-gl-worker.mjs`, loaded as an ES module — see `MapView.tsx`'s `setWorkerUrl` comment for why this file exists at all) was served as `application/octet-stream`, which browsers reject under strict MIME checking for module scripts. This broke worker-dependent vector-tile parsing, leaving the map blank (base style/military bases/airports never painted) even though the page itself loaded fine — a real, user-reported bug (`Failed to load module script: ... non-JavaScript MIME type`), not the known deck.gl/MapLibre exception below. → *Fix*: `scripts/squawkmap3d.nginx.conf` replaces the image's default server block, adding an explicit `location ~* \.mjs$ { default_type application/javascript; }`. Verified live post-fix: `curl -I .../maplibre-gl-worker.mjs` returns `Content-Type: application/javascript`, and the deployed map renders fully (terrain, all custom layers) in a real browser.
- **[Known, non-fatal, unrelated to the above] deck.gl 9.3.10 × MapLibre GL JS 6.5 `_updateViewState` exception**: the deployed site still logs a repeating `TypeError: Cannot read properties of undefined (reading 'elevation')` from `MapboxOverlay._updateViewState`. This is the same upstream deck.gl/MapLibre terrain incompatibility already documented in `plane-tracks-3d-layer`'s design.md (worked around there via `interleaved: false`, which avoids it breaking rendering but doesn't silence this one remaining non-interleaved code path). Confirmed via live browser check: the map renders correctly and fully despite these console errors — cosmetic noise from an upstream library gap, not a functional break in this deploy.
- **[Risk, discovered and fixed] `output: "export"` breaks `next start`**: verified locally — after this change, `npm run start` (`next start`) fails with `"next start" does not work with "output: export" configuration"`, since static export produces no server for it to start. This isn't feeder-specific — it affects local usage of `npm run build && npm run start` on any machine. → *Mitigation*: `package.json`'s `start` script updated to `npx serve@latest out` (Next's own suggested replacement, printed in that exact error), so local production-preview usage keeps working.
- **[Risk] Feed URL hardcodes the `ultrafeeder` container's current host:port (8080)**: if that mapping ever changes (box reconfigured, port conflict resolved differently), `NEXT_PUBLIC_FEEDER_URL` would need updating and a redeploy. → *Mitigation*: documented in `README.md`; the app itself degrades to an empty aircraft layer rather than erroring if the fetch fails (Decision 6), so a stale URL doesn't break anything else.
- **[Trade-off] Hardcoding `http://adsb-feeder.local:8080/...` couples this deploy to this specific box's current setup** (the ultrafeeder image's default port and CORS behavior), not a generic "any ADS-B decoder" mechanism. Acceptable and deliberate: the user's stated requirement is specifically drop-in parity with their actual feeder, and this was verified against that actual feeder, not assumed.
- **[Trade-off] No rollback tooling** beyond redeploying a known-good commit (`docker rm -f` + rebuild); accepted per Non-Goals for a single personal feeder.
- **[Superseded, kept for history] The lighttpd-reuse and decoder-feed-symlink design (Decisions 4 and 6's earlier drafts)** was fully reasoned and internally consistent, but built on an incorrect assumption about the box (a manual wiedehopf/tar1090 lighttpd install) that live reconnaissance disproved before anything was deployed. No harm done — the original deploy script's own preflight check would have caught the lighttpd absence and aborted rather than partially deploying.

## Migration Plan

Purely additive: one line in `next.config.js` (`output: "export"`), one line in `app/api/health/route.ts` (`export const dynamic = "force-static";`), new files under `scripts/` (deploy script + `Dockerfile`), a new `README.md` section. No new npm dependency. No changes to any existing container, the box's `docker compose` stack, or its configuration — the remote box only gains one new, independent container (`squawkmap3d`) run directly via the `docker` CLI, entirely outside the existing compose project. Nothing depends on this change existing; rollback is deleting the new files, the `next.config.js`/health-route lines, and, on the box itself, `docker rm -f squawkmap3d && docker rmi squawkmap3d:latest` — every other container, including tar1090/ultrafeeder, is untouched by both the deploy and this rollback.
