## Why

SquawkMap3D already shows the feeder's *actual* observed reception envelope (`actual-range-outline-layer`, `outline.json`), but that only reflects what has already been received — it says nothing about where the antenna's line of sight is blocked by terrain, or how far it *should* be able to see an aircraft at a given altitude if signal were the only limit. [HeyWhatsThat](https://www.heywhatsthat.com/) computes exactly that from a digital elevation model, given a "panorama" generated for a site: a per-bearing horizon profile, and — via its `upintheair.json` API — a ready-made set of maximum theoretical detection-range rings, one per requested altitude.

SquawkMap3D is deployed as a Docker sidecar on top of a running **adsb.im (`dirkhh/adsb-feeder-image`)** instance (`openspec/changes/archive/2026-08-23-deploy-to-feeder`) — the same box already runs dirkhh's `adsb-setup` web UI (port 80) and the `ultrafeeder` container (sdr-enthusiasts' `docker-adsb-ultrafeeder`, itself built on `docker-tar1090`, port 8080), and SquawkMap3D's own `rangeOutline.ts`/`feederLocation.ts` already read that same `ultrafeeder` container's server-generated `outline.json`/`receiver.json` through a same-origin nginx proxy (`scripts/squawkmap3d.nginx.conf`), because ultrafeeder's own nginx only CORS-patches its `aircraft.json` location block (confirmed in `docker-tar1090`'s `rootfs/etc/s6-overlay/startup.d/07-nginx-configure`).

adsb.im already has its own, first-class HeyWhatsThat integration, and it does **not** work by having a browser call HeyWhatsThat's public API directly:
- adsb.im's own setup UI (`utils/multioutline.py`/`templates/visualization.html`) exposes a "HeyWhat'sThat" checkbox and a panorama-ID text field, storing the value as `FEEDER_HEYWHATSTHAT_ID` (passed to the `ultrafeeder` container as `HEYWHATSTHAT_PANORAMA_ID`, plus `HEYWHATSTHAT_ALTS` for the altitude list — `docker-compose.yml`/`stage2.yml`).
- `docker-tar1090`'s own container-startup script (`rootfs/etc/s6-overlay/startup.d/06-range-outline`) is what actually calls `http://www.heywhatsthat.com/api/upintheair.json?id=...&refraction=0.25&alts=...` — server-side, once at container start (cached across restarts via a `upintheair.json.url` sentinel file so it isn't re-fetched unless the deployer changes the ID/altitudes) — and writes the raw response verbatim to `${TAR1090_INSTALL_DIR}/html-webroot/upintheair.json`, i.e. served at the ultrafeeder container's own nginx root as plain `/upintheair.json` (confirmed by reading `docker-tar1090`'s `06-range-outline`/`07-nginx-configure` directly, and cross-checked against `dirkhh/adsb-feeder-image`'s `push_multioutline.py`, which `docker cp`s an equivalent combined file to that exact same in-container path for its multi-site/stage2 case).
- Exactly like `outline.json`/`receiver.json`, `/upintheair.json` sits outside the one location block (`aircraft.json`) that `07-nginx-configure` CORS-patches — it is **not** CORS-enabled, so a direct cross-origin browser fetch against it from SquawkMap3D's own origin would be blocked, the same gap `rangeOutline.ts`/`feederLocation.ts` already work around via a same-origin proxy.

`wiedehopf/tar1090`'s own client (`html/script.js`'s `drawUpintheair()`) simply fetches this already-generated, same-origin `/upintheair.json` once at page load and never re-fetches it — this change ports that same client-side consumption pattern, reading from the same already-running adsb.im stack SquawkMap3D is already built on top of, rather than treating HeyWhatsThat as a service SquawkMap3D itself would configure or call directly.

## What Changes

- Add a **Terrain-Based Outline** layer that reads the running adsb.im/`ultrafeeder` instance's own server-generated `upintheair.json` (produced by `docker-tar1090`'s `06-range-outline` startup script from whatever `HEYWHATSTHAT_PANORAMA_ID`/`HEYWHATSTHAT_ALTS` the deployer already configured via adsb.im's own setup UI) through a new same-origin proxy path, `/upintheair.json`, added to `scripts/squawkmap3d.nginx.conf` alongside the existing `/data/outline.json`/`/data/receiver.json` proxy blocks — same `getFeederUrl()`-gated, "no feeder configured → skip the request" pattern `rangeOutline.ts` already uses, no new build-time env var, no direct browser call to HeyWhatsThat's own API.
- Parses the response's `rings` array (`[{ alt: <meters>, points: [[lat, lon], ...] }, ...]`, one ring per altitude the feeder was configured to fetch, an open — not closed — ring of one point per degree of azimuth) into a GeoJSON `FeatureCollection` of closed `LineString` features, one per altitude, each carrying its altitude (feet) as a feature property — the same reverse-engineered response shape `drawUpintheair()` and `multioutline.py` both already consume, and the same "close the ring by repeating the first point" convention `rangeOutline.ts`/tar1090's own `drawOutlineJson()` already use for `outline.json`.
- Renders those rings as **unfilled stroked outlines** (a deliberate difference from `actual-range-outline-layer`'s solid fill — this layer's own acceptance criterion calls for "a series of outlines," and a solid fill would make an outer, larger-altitude ring's interior opaquely cover every smaller ring nested inside it), one line per altitude present in the response, colored along this app's existing `ALTITUDE_COLOR_STOPS` gradient (`aircraftIcons.ts`, the same ramp already used for altitude-colored aircraft icons/tracks) so each ring's color ties back to a legible altitude, without inventing a second color convention.
- The whole set of rings is a single toggle, named "terrain-based outline" per the acceptance criteria, in the existing layer-toggle row (`MapView.tsx`'s `.controls` list), following the established visibility ref/state pair pattern every other layer already uses, and survives theme/pilot-mode style swaps.
- No new configuration surface in SquawkMap3D itself: whether the layer has any rings to show is entirely a function of whether the deployer already enabled HeyWhatsThat on the running adsb.im instance (its own existing "HeyWhat'sThat" checkbox + panorama-ID field) — matching `getFeederUrl()`'s existing "optional, degrades to empty when unset/unavailable" convention for every other feeder-sourced layer, rather than adding a second, SquawkMap3D-specific place to configure the same underlying setting.

## Capabilities

### New Capabilities
- `terrain-based-outline-layer`: a layer that reads the running adsb.im/`ultrafeeder` instance's own server-generated, HeyWhatsThat-panorama-derived `upintheair.json` (proxied same-origin, same pattern as `outline.json`/`receiver.json`) and renders it as a toggleable set of stroked (unfilled) outlines colored by altitude.

### Modified Capabilities
(none — additive layer; existing `actual-range-outline-layer`, `map-view`, and every other capability are unaffected)

## Impact

- `components/map/terrainOutline.ts` (new): `fetchTerrainOutline(): Promise<GeoJSON.FeatureCollection<LineString, { altitudeFt: number }>>` — mirrors `rangeOutline.ts`'s `fetchRangeOutline()` shape: returns an empty `FeatureCollection` immediately (no network request) when `getFeederUrl()` is unset, otherwise fetches the same-origin proxy path `/upintheair.json`, parses `rings`, converts each ring's `[lat, lon]` points to a closed GeoJSON `[lon, lat]` `LineString` tagged with `altitudeFt`, and returns an empty `FeatureCollection` (never throws) on a non-OK response (including a 404 — this file simply doesn't exist server-side when the deployer hasn't configured a HeyWhatsThat panorama ID on the feeder, or the feeder's own fetch of it failed at container start), an empty/unparseable response body, or a missing/empty `rings` array — mirrors `rangeOutline.ts`/`tfr.ts`'s "fail to empty, never error" convention.
- `scripts/squawkmap3d.nginx.conf`: add a `location = /upintheair.json` block proxying to `http://host.docker.internal:8080/upintheair.json` (the `ultrafeeder` container's own webroot-root path this file is served from — not under `/data/`), same `proxy_set_header Host $host` pattern as the existing `/data/outline.json`/`/data/receiver.json` blocks.
- `components/map/layers.ts`: `TERRAIN_OUTLINE_SOURCE_ID`/`TERRAIN_OUTLINE_LINE_LAYER_ID` (added to `addCustomLayers`/`CustomLayerVisibility`/`CUSTOM_LAYER_IDS`, same pattern as the TFR/SUA/actual-range-outline layers), a `line-color` paint expression interpolating along `ALTITUDE_COLOR_STOPS` by each feature's `altitudeFt` property, `setTerrainOutlineVisibility`, `refreshTerrainOutline`.
- `components/map/rangeOutline.ts`: export the existing (currently private) `toClosedLngLatRing()` helper so `terrainOutline.ts` can reuse it instead of duplicating an equivalent ring-closing function.
- `components/map/MapView.tsx`: new visibility ref/state pair, a "Hide/Show terrain-based outline" toggle button, and a fetch-once-on-mount-and-on-style-reload wiring (no polling interval — the feeder's own `upintheair.json` only changes when the deployer reconfigures HeyWhatsThat on adsb.im and the `ultrafeeder` container restarts, so there's nothing to periodically refetch from SquawkMap3D's side).
- No breaking changes to any existing layer or capability; no new npm dependencies; no build-time env var added.
