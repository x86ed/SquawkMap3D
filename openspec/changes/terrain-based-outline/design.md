## Context

SquawkMap3D (Next.js 16 App Router, React 19, MapLibre GL JS 6 in `components/map/MapView.tsx`) already has one terrain/range-adjacent layer, `actual-range-outline-layer` (`components/map/rangeOutline.ts`, `components/map/layers.ts`'s `RANGE_OUTLINE_*` constants), which fetches the feeder's own server-generated `outline.json` (readsb's accumulated *actual* reception envelope) through a same-origin nginx proxy, because that endpoint lives on the user's own feeder box and isn't CORS-enabled. This change adds a second, unrelated-in-origin layer: a *theoretical*, terrain-derived range outline computed by the third-party HeyWhatsThat service from a digital elevation model, independent of whether a feeder is even configured.

Two external references anchor this change:
- **HeyWhatsThat** (`heywhatsthat.com`) — a public web service that, given a "panorama" (a horizon profile computed once for a lat/lon/elevation a user registers on the site), exposes `GET /api/upintheair.json?id=<panorama id>&refraction=<r>&alts=<meters,...>`, returning `{ id, lat, lon, elev_amsl, refraction, rings: [{ alt: <meters>, points: [[lat, lon], ...] }, ...] }` — one ring per requested altitude, each ring an *open* array of one `[lat, lon]` point per degree of azimuth (confirmed live: `curl` against a real panorama ID returns exactly this shape, 360 points per ring for a plain `alts=` request, and `Access-Control-Allow-Origin: *` on every response). An invalid/unknown panorama ID returns HTTP 200 with an **empty body** (confirmed live), not a 404 or an error JSON payload — `fetchTerrainOutline()` must treat "empty or unparseable body" as an explicit failure case, not let `JSON.parse`'s exception escape uncaught.
- **`wiedehopf/tar1090`** (`html/script.js`) — not fetched or embedded; it defines the reference client behavior for consuming this exact API response: `drawUpintheair()` (~line 7265) reads a pre-fetched `upintheair.json` (see `html/early.js`'s `get_history()`, which fetches it once at page load and caches it in `calcOutlineData` — never re-fetched/polled, since a panorama's terrain data is static) and, for each ring, draws an unfilled stroked `LineString` (closed by re-appending the first point, `fill: null` in its `ol.style.Style`), optionally colored per-altitude via its own `altitudeColor()` HSL ramp when `range_outline_colored_by_altitude` is enabled (`html/config.js`). The actual `upintheair.json` file itself is produced entirely server-side by a one-line `wget` against HeyWhatsThat's own API (`getupintheair.sh`) — tar1090 does no terrain computation of its own. `dirkhh/adsb-feeder-image`'s `utils/multioutline.py` (`create_heywhatsthat()`) confirms the same `rings: [{alt, points}]` shape is treated as the standard interchange format one layer up the stack (combining multiple sites' `upintheair.json` files by altitude). This change ports tar1090's *client-side consumption pattern* (fetch once, one stroked ring per altitude, altitude-colored) directly against HeyWhatsThat's API — it does not proxy through a server-generated `upintheair.json` file the way tar1090/adsb.im do, since this app has no server-side component that would otherwise generate one, and HeyWhatsThat's API is directly browser-fetchable anyway (see Decision 1).

## Goals / Non-Goals

**Goals:**
- Accept a HeyWhatsThat panorama ID, in either bare-ID or full-panorama-URL form (matching the acceptance criteria's own example, `https://www.heywhatsthat.com/?view=CG4B3P7M`).
- Fetch `upintheair.json`-shaped data directly from HeyWhatsThat's own API (no server-side generation step, no proxy) and render it as a toggleable set of stroked, altitude-colored outline rings — "terrain-based outline," matching the acceptance criteria's exact naming and this app's established per-layer toggle convention.
- Reuse this app's existing altitude-color ramp (`ALTITUDE_COLOR_STOPS`/`altitudeToColor`, `aircraftIcons.ts`) rather than inventing a second one, so the new rings' colors read consistently with the color-by-altitude aircraft mode already in the app.
- Fail gracefully (empty layer, no error, no broken map) when no panorama ID is configured, the ID is invalid, or the request fails for any reason — same convention every other optional/public feed in this app already follows (`tfr.ts`, `specialUseAirspace.ts`, `rangeOutline.ts`).

**Non-Goals:**
- Any in-app UI for entering/managing a panorama ID. This app has no settings/config UI anywhere; every other optional feed (`NEXT_PUBLIC_FEEDER_URL`, `NEXT_PUBLIC_OPENAIP_API_KEY`) is a build-time env var, and this follows the same pattern rather than introducing the first settings form.
- Computing horizon/line-of-sight geometry client-side from a DEM. HeyWhatsThat already does this server-side from its own panorama; reimplementing terrain horizon math in the browser would be a large, unrelated undertaking and directly duplicates a service this feature exists specifically to consume.
- Periodic refetching/polling. A HeyWhatsThat panorama's terrain data for a fixed site never changes between requests (unlike `outline.json`'s continuously-accumulating actual-range data, or TFRs/SUA's periodically-updated feeds) — refetching on an interval would just be wasted third-party API calls for identical data.
- Multi-site combination (`adsb-feeder-image`'s `multioutline.py`-style merging of several panoramas' rings into one unioned shape). Single-panorama scope only, matching this app's existing "one configured feeder" scope for `NEXT_PUBLIC_FEEDER_URL`.
- A user-facing altitude-list, color, or line-width control. `TERRAIN_OUTLINE_ALTITUDES_FT` is a fixed constant, matching how every other layer's paint properties are fixed (not user-configurable) in this app.
- Antimeridian-wraparound ring splitting (tar1090's own `Math.abs(lon - lastLon) > 270` check) — HeyWhatsThat panoramas are single-site, and a site's terrain-limited horizon range (well under 300 NM even at high altitude) never spans the antimeridian in practice; same reasoning `actual-range-outline-layer`'s design already used to exclude this.

## Decisions

### 1. Fetch HeyWhatsThat's API directly from the browser — no proxy, unlike `outline.json`
`GET https://www.heywhatsthat.com/api/upintheair.json?id=<id>&refraction=0.25&alts=<meters,...>`, called directly client-side. Confirmed live: this endpoint returns `Access-Control-Allow-Origin: *`, so — unlike `rangeOutline.ts`'s `outline.json` (which needed a same-origin nginx proxy because it lives on the user's own feeder box, whose nginx only CORS-patches `aircraft.json`) — there is no CORS obstacle here, and HeyWhatsThat is a public third-party service this app doesn't control the deployment of anyway. This makes the implementation closer to `rainviewer.ts`/`specialUseAirspace.ts` (public feed, fetched directly, no proxy) than to `rangeOutline.ts`/`feederLocation.ts` (local feeder resource requiring a proxy).
- **Alternative considered (rejected)**: mirror tar1090/adsb.im's own architecture exactly — have some server-side process periodically `wget` `upintheair.json` and serve it same-origin. Rejected: this app has no long-running server-side component analogous to tar1090's install, and there's no CORS reason to need one here — the extra indirection would add a moving part (a cron/script, a file to keep fresh) purely to imitate an architecture that exists there for a reason (nginx CORS gap) that doesn't apply to a third-party API.

### 2. Response shape and parsing: mirror `rangeOutline.ts`'s ring-closing convention
Each `rings[i]` entry (`{ alt: <meters>, points: [[lat, lon], ...] }`) becomes one GeoJSON `Feature<LineString>` with `properties: { altitudeFt: round(alt * 3.28084) }`. Points are converted `[lat, lon] → [lon, lat]` and the ring is closed by re-appending the first coordinate if the response's own last point doesn't already equal the first (HeyWhatsThat's own response is not closed — confirmed live, 360 points for a plain one-point-per-degree request) — the same "close it ourselves" step `rangeOutline.ts`'s `toClosedLngLatRing()` already performs for `outline.json`, reused here rather than duplicated as a near-identical second implementation (see Decision 5).
- **Known limitation, accepted**: HeyWhatsThat can return more than one ring for a single requested altitude for extreme/split terrain shadowing in theory; this endpoint's actual response for any real single site is one ring per altitude (confirmed against a real panorama), and `rangeOutline.ts`'s own multi-ring (`multiRange`) handling doesn't apply to this endpoint's response shape at all (`upintheair.json` has no `multiRange` key). Not handled specially — each `rings[i]` maps 1:1 to one `LineString` feature regardless.

### 3. Stroked outline, not filled — deliberately different from `actual-range-outline-layer`
Rendered via a plain MapLibre `line` layer (`type: "line"`) on the ring `LineString` source, `fill: none` (there is no fill layer at all here, unlike `RANGE_OUTLINE_FILL_LAYER_ID`'s solid fill). This is the acceptance criteria's own wording ("draw a series of outlines"), and also a practical necessity: multiple concentric rings at increasing altitude are, geometrically, mostly nested inside one another (a higher-altitude aircraft is visible farther away in every direction the terrain doesn't block) — filling every ring solid would visually bury every inner, lower-altitude ring under the outer rings' opaque fill, defeating the point of showing several altitude bands at once. `actual-range-outline-layer`'s solid fill works precisely because it only ever draws one ring (a single accumulated actual-range envelope); this layer routinely draws several nested rings at once, so stroke-only is the only rendering that keeps every ring visible and legible simultaneously.

### 4. Color by altitude using this app's existing `ALTITUDE_COLOR_STOPS` ramp, not tar1090's own `altitudeColor()`
`components/map/layers.ts`'s new line layer's `line-color` paint property is a MapLibre `["interpolate", ["linear"], ["get", "altitudeFt"], ...]` expression built at layer-construction time from `aircraftIcons.ts`'s existing `ALTITUDE_COLOR_STOPS` table (converting each stop's `[r,g,b]` to an `"rgb(r,g,b)"` string) — the same gradient already used for altitude-colored aircraft icons/tracks (`altitudeToColor`). This ties the new rings' colors to a color language this app's users can already see used elsewhere (the aircraft color-mode legend), rather than introducing tar1090's own separate HSL ramp, which would mean two different "altitude → color" conventions existing side by side in the same app for no reason other than incidental origin.
- `TERRAIN_OUTLINE_ALTITUDES_FT` is chosen to land on `ALTITUDE_COLOR_STOPS`' own more distinctive stops (`1_000, 2_000, 4_000, 6_000, 8_000, 10_000, 20_000, 30_000, 40_000`, skipping only the `0` ft stop, which isn't a meaningful "range profile" altitude) so the rendered rings sample the gradient at points that are visually well spread out, rather than an arbitrary altitude list that might land several rings in a narrow, hard-to-distinguish color band.
- **Alternative considered (rejected)**: a single fixed color for every ring (tar1090's own default, `range_outline_colored_by_altitude = false`). Rejected — with up to nine simultaneous rings, per-altitude coloring is the only way to tell which ring corresponds to which altitude at a glance; a legend/label per ring was considered and deferred (see Open Questions) rather than blocking the whole layer on it.

### 5. New module (`terrainOutline.ts`), reusing `rangeOutline.ts`'s ring-closing helper rather than duplicating it
`toClosedLngLatRing()` (currently private to `rangeOutline.ts`) is exported from `rangeOutline.ts` and imported by the new `terrainOutline.ts`, instead of copy-pasting an equivalent function — both modules need the exact same "`[lat,lon]` pairs → closed `[lon,lat]` ring" transform, and keeping one implementation avoids the two ever silently drifting apart (e.g. one fixing an edge case the other doesn't get). `terrainOutline.ts` itself stays a separate module (not folded into `rangeOutline.ts`) because the two features are otherwise unrelated in data source, refresh cadence, and rendering style (stroke-only + altitude-colored vs. solid fill + radar sweep) — bundling them would only make one already-large-enough file larger for no shared benefit beyond the one small helper.

### 6. No env-configured panorama ID → layer renders empty, exactly like every other optional feed
`getHeywhatsthatPanoramaId()` (in `constants.ts`, alongside `getFeederUrl()`/`getOpenAipApiKey()`) returns `undefined` when `NEXT_PUBLIC_HEYWHATSTHAT_PANORAMA_ID` is unset; `fetchTerrainOutline()` short-circuits to an empty `FeatureCollection` in that case without ever making a network request — same gate shape as `getFeederUrl()`'s "no feeder configured" check in `rangeOutline.ts`. The toggle button, layer, and empty source all still exist and behave normally (togglable, no error) whether or not a panorama ID is configured, exactly like the TFR layer's "no feed configured yet" state.
- **ID extraction**: `extractHeywhatsthatPanoramaId(raw: string): string` — if `raw` contains `view=`, extract everything after it up to the next `&` or end of string (a plain string search/slice, not a full `URL`/`URLSearchParams` parse, since the acceptance criteria's example URL isn't guaranteed to be a syntactically complete absolute URL a strict parser would accept, and a manual extraction is simpler and more forgiving here); otherwise, return `raw` trimmed as-is (the bare-ID case). Applied once inside `getHeywhatsthatPanoramaId()`, so callers never see the raw env value.

## Risks / Trade-offs

- **[Risk] Third-party service availability/rate limits**: HeyWhatsThat is a small, free, unauthenticated public service with no documented SLA or published rate limit. → *Mitigation*: fetched once per page load/style-reload (Non-Goals: no polling), the lowest possible request volume; failure degrades to an empty layer (Goals), never a broken map.
- **[Risk] Panorama ID silently wrong/stale**: if `NEXT_PUBLIC_HEYWHATSTHAT_PANORAMA_ID` points at a panorama for the wrong location (e.g. copy-paste error, or the antenna moved since the panorama was generated), the rendered rings will be silently centered on the wrong site with no in-app indication of the mismatch. → *Mitigation*: out of scope to detect (this app has no independent ground truth for "where is the panorama's site" beyond the response's own `lat`/`lon`, which isn't cross-checked against `getFeederLocation()` in this change); left as an open question below.
- **[Trade-off] No legend for which color = which altitude**: reusing `ALTITUDE_COLOR_STOPS` ties the rings to a color language already used elsewhere, but this layer alone doesn't add a new legend UI naming each ring's specific altitude. → *Mitigation*: deferred, see Open Questions; the existing aircraft color-mode legend (if visible) uses the same ramp and is the closest existing reference a user has.
- **[Trade-off] No periodic refresh**: if a deployer regenerates the HeyWhatsThat panorama (e.g. re-surveys the antenna) without redeploying/restarting the app, already-open tabs won't pick up the new data until the map style reloads (theme/pilot-mode toggle) or the page is refreshed. Accepted — this mirrors "static until redeploy" for every other build-time-configured constant in this app (e.g. `NEXT_PUBLIC_FEEDER_URL` itself doesn't hot-reload either).

## Migration Plan

Purely additive — one new file (`terrainOutline.ts`), one new toggle/layer, no changes to any existing layer's behavior, no new npm dependencies, no nginx/proxy changes. Rollback is deleting the new file/toggle/layer entries; nothing else depends on this layer existing.

## Open Questions

- Whether to add a small legend (ring color → altitude) is left to implementation/a follow-up change — not blocking, since the rings are still individually distinguishable by color even without on-screen labels, matching how `ALTITUDE_COLOR_STOPS`' own legend (if any exists today for aircraft color mode) is a separate, already-existing UI element this change doesn't have to duplicate.
- Whether to cross-check the response's own `lat`/`lon` against `getFeederLocation()` (when a feeder happens to also be configured) and warn/no-op on a large mismatch is left unresolved — not required by the acceptance criteria, and this layer is explicitly usable with no feeder configured at all.
