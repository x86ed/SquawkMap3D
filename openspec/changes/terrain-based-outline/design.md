## Context

SquawkMap3D (Next.js 16 App Router, React 19, MapLibre GL JS 6 in `components/map/MapView.tsx`) already has one terrain/range-adjacent layer, `actual-range-outline-layer` (`components/map/rangeOutline.ts`, `components/map/layers.ts`'s `RANGE_OUTLINE_*` constants), which fetches the feeder's own server-generated `outline.json` (readsb's accumulated *actual* reception envelope) through a same-origin nginx proxy, because that endpoint lives on the `ultrafeeder` container and isn't CORS-enabled. This change adds a second, related-in-origin layer: a *theoretical*, terrain-derived range outline that the same running feeder stack — not a client-side call to a third party — already computes and serves.

**SquawkMap3D's actual deployment target is a running adsb.im (`dirkhh/adsb-feeder-image`) instance**, not a bare feeder box (`openspec/changes/archive/2026-08-23-deploy-to-feeder`, confirmed via direct SSH/`docker ps` reconnaissance against the real box during that change): a Docker Compose stack managed by dirkhh's `adsb-setup` Flask UI (host port 80), running the `ultrafeeder` container (sdr-enthusiasts' `docker-adsb-ultrafeeder`, host port 8080 — itself `FROM ghcr.io/sdr-enthusiasts/docker-tar1090:latest`) alongside `piaware`, `dump978`, etc. SquawkMap3D itself runs as its own independent sidecar container on port 7500, with its own small nginx (`scripts/squawkmap3d.nginx.conf`) that already proxies two of `ultrafeeder`'s non-CORS-enabled endpoints same-origin: `/data/receiver.json` and `/data/outline.json` (`feederLocation.ts`, `rangeOutline.ts`). `NEXT_PUBLIC_FEEDER_URL` itself points directly at `ultrafeeder`'s `aircraft.json` (the one endpoint that *is* CORS-enabled) and is also used as the app-wide "is a feeder configured at all" gate (`getFeederUrl()`).

This change was originally drafted assuming SquawkMap3D had no server-side/proxy component and would call HeyWhatsThat's own public API directly from the browser with a SquawkMap3D-specific panorama-ID env var. That assumption was wrong on two counts, found by reading the real integration chain rather than assuming one:

1. **adsb.im already has its own first-class HeyWhatsThat integration**, configured through its own setup UI, not through anything SquawkMap3D would add:
   - `dirkhh/adsb-feeder-image`'s `templates/visualization.html` renders a "HeyWhat'sThat" checkbox and a panorama-ID text field; `utils/data.py` persists the value as `FEEDER_HEYWHATSTHAT_ID` (plus `FEEDER_HEYWHATSTHAT_ALTS`).
   - `docker-compose.yml`/`stage2.yml`/`stage2_main.yml` pass those through to the `ultrafeeder` container as `HEYWHATSTHAT_PANORAMA_ID`/`HEYWHATSTHAT_ALTS` environment variables.
   - `docker-adsb-ultrafeeder` is `FROM ghcr.io/sdr-enthusiasts/docker-tar1090:latest`; that image's own container-startup script, `rootfs/etc/s6-overlay/startup.d/06-range-outline`, is what actually issues `curl` against `http://www.heywhatsthat.com/api/upintheair.json?id=${HEYWHATSTHAT_PANORAMA_ID}&refraction=0.25&alts=${HEYWHATSTHAT_ALTS}` (confirmed by reading that script directly) — **once, at container start**, caching the result via a sentinel `upintheair.json.url` file compared against the current URL, so it is not re-fetched on every container restart unless the deployer changes the ID/altitudes. It writes the raw response verbatim to `${TAR1090_INSTALL_DIR}/html-webroot/upintheair.json` — the ultrafeeder container's own nginx webroot **root**, i.e. served at plain `/upintheair.json`, not under `/data/`. (`dirkhh/adsb-feeder-image`'s own `push_multioutline.py`, used for its multi-site/"stage2" combined-outline feature, confirms the same in-container path convention: it `docker cp`s an equivalent combined file to `ultrafeeder:/usr/local/share/tar1090/html-webroot/upintheair.json`.)
   - **The user's reference for this change**, `dirkhh/adsb-feeder-image`'s `templates/base.html` (line 96 at the pinned commit, `<li><a id="options" class="dropdown-item" href="/visualization">Options</a></li>`), is exactly the nav link into that same `visualization.html` settings page — i.e. the acceptance criteria's own reference point *is* adsb.im's existing HeyWhatsThat configuration UI, not a hint to reimplement HeyWhatsThat configuration inside SquawkMap3D.
2. **`/upintheair.json` is not CORS-enabled**, same gap as `outline.json`/`receiver.json`: `docker-tar1090`'s `rootfs/etc/s6-overlay/startup.d/07-nginx-configure` only patches an `Access-Control-Allow-Origin` header onto the `location ~ aircraft\.json$` block — every other path, including the webroot-root `/upintheair.json`, falls through to the default `location /` block with no CORS header at all. A direct cross-origin `fetch()` from SquawkMap3D's own origin (port 7500) against `http://<feeder-host>:8080/upintheair.json` would be blocked by the browser, exactly like `outline.json`/`receiver.json` already are — this rules out "fetch HeyWhatsThat-shaped data directly from the browser" for the *feeder's* copy, and there is no reason to bypass the feeder's copy and call HeyWhatsThat's own public API directly from SquawkMap3D when the already-running, already-configured feeder stack already produces the identical file.

Given both of those, this change follows the exact same integration pattern `rangeOutline.ts`/`feederLocation.ts` already established for `outline.json`/`receiver.json`: same-origin nginx proxy in front of an `ultrafeeder`-served, non-CORS file, gated on whether a feeder is configured at all (`getFeederUrl()`), degrading to an empty layer rather than erroring when the file doesn't exist (no panorama ID configured on adsb.im) or the feeder isn't reachable.

`wiedehopf/tar1090` (`html/script.js`) remains the reference for *client-side consumption* of the resulting data, unchanged from the original draft: `drawUpintheair()` (~line 7265) reads the pre-fetched `upintheair.json` (`html/early.js`'s `get_history()` fetches it once at page load, cached in `calcOutlineData`, never re-fetched/polled) and, for each ring, draws an unfilled stroked `LineString` (closed by re-appending the first point), optionally colored per-altitude via its own `altitudeColor()` HSL ramp. This change ports that same "fetch once, one stroked ring per altitude, altitude-colored" client behavior — the only thing that changes from the original draft is *where the fetch points* (the feeder's own same-origin proxy, not HeyWhatsThat's public API) and *how the panorama ID is configured* (already done, on adsb.im itself — not a new SquawkMap3D env var).

## Goals / Non-Goals

**Goals:**
- Read whatever per-altitude `upintheair.json` rings the running adsb.im instance's `ultrafeeder` container has already fetched and is already serving, through a new same-origin proxy path (`/upintheair.json`) added to `scripts/squawkmap3d.nginx.conf`, following the exact pattern `outline.json`/`receiver.json` already use.
- Render that data as a toggleable set of stroked, altitude-colored outline rings — "terrain-based outline," matching the acceptance criteria's exact naming and this app's established per-layer toggle convention.
- Reuse this app's existing altitude-color ramp (`ALTITUDE_COLOR_STOPS`/`altitudeToColor`, `aircraftIcons.ts`) rather than inventing a second one, so the new rings' colors read consistently with the color-by-altitude aircraft mode already in the app.
- Fail gracefully (empty layer, no error, no broken map) when no feeder is configured (`getFeederUrl()` unset), the feeder hasn't been configured with a HeyWhatsThat panorama ID (adsb.im's own "HeyWhat'sThat" setting, `/upintheair.json` simply doesn't exist server-side), or the request fails for any reason — same convention every other optional/public feed in this app already follows (`tfr.ts`, `specialUseAirspace.ts`, `rangeOutline.ts`).

**Non-Goals:**
- Any in-app UI, or any SquawkMap3D-specific build-time env var, for entering/managing a HeyWhatsThat panorama ID. adsb.im already has this UI (`templates/visualization.html`'s "HeyWhat'sThat" checkbox + panorama-ID field, referenced by the user's own linked `base.html` nav entry) — adding a second, SquawkMap3D-specific place to configure the same underlying setting would let the two drift out of sync for no benefit.
- Calling HeyWhatsThat's own public API (`www.heywhatsthat.com`) directly from SquawkMap3D, from either the browser or a build/deploy step. The already-running feeder stack already does this server-side (`docker-tar1090`'s `06-range-outline`) and already serves the identical resulting data; duplicating that call would mean two independent fetches of the same panorama for no benefit, and would need SquawkMap3D to independently learn the panorama ID adsb.im already has configured.
- Computing horizon/line-of-sight geometry client-side from a DEM. HeyWhatsThat already does this server-side from its own panorama, and the feeder stack this app is deployed on top of already retrieves the result; reimplementing terrain horizon math in the browser would be a large, unrelated undertaking.
- Periodic refetching/polling of `/upintheair.json` from SquawkMap3D's side. The feeder's own copy of this file only changes when the deployer reconfigures HeyWhatsThat on adsb.im and the `ultrafeeder` container restarts (`06-range-outline` only runs at container start) — refetching on an interval from SquawkMap3D would just be wasted requests against unchanged data, mirroring why `outline.json` (which *does* accumulate live) polls but this wouldn't.
- Multi-site combination (`adsb-feeder-image`'s `multioutline.py`-style merging of several panoramas' rings into one unioned shape). That's already adsb.im's own "stage2" feature, upstream of the single `/upintheair.json` file this change reads — SquawkMap3D reads whatever that one file already contains, single- or multi-site, without re-implementing the merge itself.
- A user-facing altitude-list, color, or line-width control. Which altitudes appear is entirely a function of the feeder's own `HEYWHATSTHAT_ALTS` configuration (adsb.im's own setting); SquawkMap3D renders whatever `rings` the fetched file contains, and colors/line-width are fixed paint properties like every other layer's.
- Antimeridian-wraparound ring splitting (tar1090's own `Math.abs(lon - lastLon) > 270` check) — a HeyWhatsThat panorama is single-site, and a site's terrain-limited horizon range (well under 300 NM even at high altitude) never spans the antimeridian in practice; same reasoning `actual-range-outline-layer`'s design already used to exclude this.

## Decisions

### 1. Fetch the feeder's own `/upintheair.json` through a new same-origin nginx proxy — not HeyWhatsThat's API directly, and not a new build-time env var
`fetchTerrainOutline()` fetches a relative, same-origin path (`/upintheair.json`), gated on `getFeederUrl()` being configured (mirrors `fetchRangeOutline()`'s `getRangeOutlineUrl()` gate exactly — reuses the existing "is a feeder configured" signal rather than adding a second one). `scripts/squawkmap3d.nginx.conf` gains a new `location = /upintheair.json { proxy_pass http://host.docker.internal:8080/upintheair.json; proxy_set_header Host $host; }` block, the same shape as its existing `/data/outline.json`/`/data/receiver.json` blocks, pointing at `ultrafeeder`'s own webroot-root path (not `/data/` — confirmed via `docker-tar1090`'s `06-range-outline`, which writes to `${TAR1090_INSTALL_DIR}/html-webroot/upintheair.json`, the container's nginx doc root, not the readsb-data-backed `/data/` location).
- **Alternative considered (rejected, this change's original draft)**: fetch `https://www.heywhatsthat.com/api/upintheair.json` directly from the browser with a new `NEXT_PUBLIC_HEYWHATSTHAT_PANORAMA_ID` env var. Rejected once the real deployment target was checked: this would call HeyWhatsThat a second, independent time for a panorama the feeder stack has *already* fetched and is *already* serving, would require SquawkMap3D to duplicate a panorama ID the deployer already entered once in adsb.im's own setup UI, and doesn't even avoid a CORS workaround — `heywhatsthat.com`'s own API is CORS-open, but that was never the blocker; the actual same-origin work this change needs is identical to `outline.json`/`receiver.json`'s regardless of which upstream call produced the file.
- **Alternative considered (rejected)**: read `HEYWHATSTHAT_PANORAMA_ID`/`HEYWHATSTHAT_ALTS` some other way (e.g. an adsb.im API call) and have SquawkMap3D build and issue the HeyWhatsThat request itself. Rejected — unnecessary: the feeder has already done this and the resulting file is one relative fetch away, exactly like every other feeder-derived layer in this app.

### 2. Response shape and parsing: unchanged from the original draft — mirror `rangeOutline.ts`'s ring-closing convention
Each `rings[i]` entry (`{ alt: <meters>, points: [[lat, lon], ...] }`) becomes one GeoJSON `Feature<LineString>` with `properties: { altitudeFt: round(alt * 3.28084) }`. Points are converted `[lat, lon] → [lon, lat]` and the ring is closed by re-appending the first coordinate if the response's own last point doesn't already equal the first (HeyWhatsThat's own response is not closed) — the same "close it ourselves" step `rangeOutline.ts`'s `toClosedLngLatRing()` already performs for `outline.json`, reused here rather than duplicated as a near-identical second implementation (see Decision 4). This part of the design doesn't change with the corrected fetch source, since the feeder's `/upintheair.json` is HeyWhatsThat's own response written to disk verbatim (`06-range-outline`'s `cp -f "${PFILE}" "${OUT_FILE}"` in the default, full-accuracy case) — same shape, same closing requirement, only reached via a different URL.
- **Known limitation, accepted**: HeyWhatsThat can in theory return more than one ring for a single requested altitude for extreme/split terrain shadowing; not handled specially — each `rings[i]` maps 1:1 to one `LineString` feature regardless, matching `rangeOutline.ts`'s own scope decisions for `outline.json`'s analogous `multiRange` handling not applying here.
- **Redacted-location variant**: `06-range-outline` strips `lat`/`lon`/`id`/`elev_amsl` from the served file when the feeder's `READSB_RX_LOCATION_ACCURACY` isn't left at its default/exact setting — `rings` itself is untouched either way, so this doesn't affect parsing; `fetchTerrainOutline()` never reads those top-level fields.

### 3. Stroked outline, not filled — deliberately different from `actual-range-outline-layer`
Rendered via a plain MapLibre `line` layer (`type: "line"`) on the ring `LineString` source, with no corresponding fill layer at all (unlike `RANGE_OUTLINE_FILL_LAYER_ID`'s solid fill). This is the acceptance criteria's own wording ("draw a series of outlines"), and also a practical necessity: multiple concentric rings at increasing altitude are, geometrically, mostly nested inside one another — filling every ring solid would visually bury every inner, lower-altitude ring under the outer rings' opaque fill. `actual-range-outline-layer`'s solid fill works precisely because it only ever draws one ring; this layer routinely draws several nested rings at once, so stroke-only is the only rendering that keeps every ring visible and legible simultaneously.

### 4. Color by altitude using this app's existing `ALTITUDE_COLOR_STOPS` ramp, not tar1090's own `altitudeColor()`
`components/map/layers.ts`'s new line layer's `line-color` paint property is a MapLibre `["interpolate", ["linear"], ["get", "altitudeFt"], ...]` expression built at layer-construction time from `aircraftIcons.ts`'s existing `ALTITUDE_COLOR_STOPS` table (converting each stop's `[r,g,b]` to an `"rgb(r,g,b)"` string) — the same gradient already used for altitude-colored aircraft icons/tracks (`altitudeToColor`). This ties the new rings' colors to a color language this app's users can already see used elsewhere, rather than introducing tar1090's own separate HSL ramp.
- Since the set of altitudes rendered is now whatever the feeder's own `HEYWHATSTHAT_ALTS` configuration produced (Non-Goals — no SquawkMap3D-side fixed altitude list), the interpolation expression is built purely from `ALTITUDE_COLOR_STOPS`' own stops (independent of how many rings the response actually contains), so any altitude the deployer configured on adsb.im maps to a color along the same continuous ramp used elsewhere, rather than requiring SquawkMap3D to know the exact altitude list in advance.
- **Alternative considered (rejected)**: a single fixed color for every ring (tar1090's own default, `range_outline_colored_by_altitude = false`). Rejected — with potentially several simultaneous rings, per-altitude coloring is the only way to tell which ring corresponds to which altitude at a glance; a legend/label per ring was considered and deferred (see Open Questions) rather than blocking the whole layer on it.

### 5. New module (`terrainOutline.ts`), reusing `rangeOutline.ts`'s ring-closing helper rather than duplicating it
`toClosedLngLatRing()` (currently private to `rangeOutline.ts`) is exported from `rangeOutline.ts` and imported by the new `terrainOutline.ts`, instead of copy-pasting an equivalent function — both modules need the exact same "`[lat,lon]` pairs → closed `[lon,lat]` ring" transform, and keeping one implementation avoids the two ever silently drifting apart. `terrainOutline.ts` itself stays a separate module (not folded into `rangeOutline.ts`) because the two features are otherwise unrelated in refresh cadence and rendering style (stroke-only + altitude-colored, fetched once vs. solid fill + radar sweep, polled every 15s) even though they now share the same feeder-proxy integration pattern and the same underlying `getFeederUrl()` gate.

### 6. No feeder configured, or feeder has no HeyWhatsThat panorama configured → layer renders empty, exactly like every other feeder-derived layer
`fetchTerrainOutline()` short-circuits to an empty `FeatureCollection` when `getFeederUrl()` returns `undefined`, without making a network request — same gate `rangeOutline.ts`'s `getRangeOutlineUrl()` already uses. When a feeder *is* configured but the deployer hasn't turned on HeyWhatsThat in adsb.im's own setup UI (or `06-range-outline` failed to fetch it at container start — e.g. HeyWhatsThat unreachable at that moment), `/upintheair.json` simply doesn't exist server-side (`06-range-outline` explicitly `rm -f`s the output file in both the "not configured" and "download failed" cases) — the proxy returns a 404, which `fetchTerrainOutline()` treats as any other non-OK response: empty `FeatureCollection`, no error. The toggle button, layer, and empty source all still exist and behave normally (toggleable, no error) in every one of these states, exactly like the TFR layer's "no feed configured yet" state.

## Risks / Trade-offs

- **[Risk] Feeder never re-fetches `/upintheair.json` after the `ultrafeeder` container starts**: `06-range-outline` only runs at container start, caching against a URL sentinel file. If a deployer changes the panorama ID or altitudes in adsb.im's setup UI without restarting the `ultrafeeder` container, SquawkMap3D (reading the same stale/absent file) won't see the update either. → *Mitigation*: this is adsb.im's own existing behavior, not something this change introduces or can fix from SquawkMap3D's side; out of scope, same as accepting `outline.json`'s own refresh cadence as given.
- **[Risk] Panorama ID silently wrong/stale**: if the feeder's configured panorama is for the wrong location (deployer copy-paste error, or the antenna moved since the panorama was generated), the rendered rings will be silently centered on the wrong site with no in-app indication of the mismatch. → *Mitigation*: out of scope to detect from SquawkMap3D (no independent ground truth beyond the response's own `lat`/`lon`, which may also be redacted per `READSB_RX_LOCATION_ACCURACY` — see Decision 2 — and isn't cross-checked against `getFeederLocation()` in this change); left as an open question below.
- **[Trade-off] No legend for which color = which altitude**: reusing `ALTITUDE_COLOR_STOPS` ties the rings to a color language already used elsewhere, but this layer alone doesn't add a new legend UI naming each ring's specific altitude. → *Mitigation*: deferred, see Open Questions.
- **[Trade-off] Coupled to the specific adsb.im/`ultrafeeder` file layout**: this change hardcodes `ultrafeeder`'s webroot-root `/upintheair.json` path, discovered by reading `docker-tar1090`'s actual startup scripts rather than assumed. If a deployer runs SquawkMap3D against a decoder stack that isn't adsb.im/`ultrafeeder`-based (e.g. a manual wiedehopf/tar1090 install with a different webroot layout, or no HeyWhatsThat integration at all), this proxy path simply 404s and the layer renders empty — same graceful degradation as `outline.json`'s own "readsb-only feature" caveat already accepts for non-readsb decoders.

## Migration Plan

Purely additive — one new file (`terrainOutline.ts`), one new toggle/layer, one new `location` block in `scripts/squawkmap3d.nginx.conf`, no changes to any existing layer's behavior, no new npm dependencies, no changes to the `ultrafeeder` container or the box's managed `docker compose` stack (this only ever reads an already-served file). Rollback is deleting the new file/toggle/layer entries and the new nginx `location` block; nothing else depends on this layer existing.

## Open Questions

- Whether to add a small legend (ring color → altitude) is left to implementation/a follow-up change — not blocking, since the rings are still individually distinguishable by color even without on-screen labels.
- Whether to cross-check the response's own `lat`/`lon` (when present and not redacted) against `getFeederLocation()` and warn/no-op on a large mismatch is left unresolved — not required by the acceptance criteria, and this layer is explicitly usable with no feeder configured at all.
