## Context

SquawkMap3D (Next.js 16 App Router, React 19, MapLibre GL JS 6 in `components/map/MapView.tsx`, plus a `@deck.gl/mapbox` overlay used only by the aircraft-tracks layer) already has a live feeder integration: `components/map/aircraft.ts` polls `NEXT_PUBLIC_FEEDER_URL`'s `aircraft.json`, and `components/map/feederLocation.ts` fetches the feeder's surveyed `receiver.json` position through a same-origin nginx proxy (`scripts/squawkmap3d.nginx.conf`), because ultrafeeder's own nginx only CORS-patches `aircraft.json`'s location block (see `feederLocation.ts`'s doc comment, `07-nginx-configure`).

Two external references anchor this change:
- **tar1090** (`wiedehopf/tar1090`, `html/script.js`) — not fetched or embedded; it defines both the data contract and the reference behavior for "actual range outline": `drawOutlineJson()` (around line 7316) polls `data/outline.json` (or `data/multiOutline.json` if `multiOutline` is enabled) every `actualOutline.refresh` (`15000`ms, set at line 2936), parses `{ points: [[lat, lon], ...] }` / `{ multiRange: [[[lat, lon], ...], ...] }` / `{ actualRange: { last24h: { points: [...] } } }`, and draws each ring as a closed `ol.geom.LineString` styled with `actual_range_outline_color`/`width`/`dash` (defaults: `#00596b`, `1.7`, solid — `html/defaults.js` lines 54-57). The underlying file is generated server-side by **readsb** (`wiedehopf/readsb`, confirmed via `track.c`) as it observes aircraft over time and accumulates the farthest-observed range per bearing — this app does not reimplement that accumulation; it consumes readsb's own output, same as tar1090 does.
- **`radar-sweep_4.html`** (user-provided reference) — a standalone MapLibre + Canvas2D demo: a `<canvas id="scope">` absolutely positioned over the map, redrawn every `requestAnimationFrame`, whose `draw(angleDeg)` function (1) fades the previous frame via `destination-out` compositing instead of clearing (phosphor persistence), (2) reprojects the site position via `map.project()` every frame so the scope tracks pan/zoom, (3) traces the site's coverage polygon and calls `ctx.clip()` so nothing is ever painted outside it, (4) draws a fading trailing wedge plus a bright leading edge for the sweep beam, and (5) paints "contacts" (dots + text labels) caught by the sweep as it passes their bearing. This change ports that *behavior* (rotating beam, trailing fade, bright leading edge, beam bounded by the coverage shape, contacts painted/flashed on the sweep), not its literal Canvas2D-over-the-map implementation — see Decision 4 below for why: the reference's own map is intentionally flat (`pitch: 0, dragRotate: false`), while this app's map defaults to a steep pitch (`INITIAL_PITCH = 60`, up to `MAX_PITCH = 85`) with real 3D terrain (`terrain.ts`), so a screen-space DOM canvas overlay would not track that pitched/terrain-draped scene correctly.

## Goals / Non-Goals

**Goals:**
- Fetch the feeder's own `outline.json` and render it as a solid-filled MapLibre layer (explicit acceptance criterion — deliberately not tar1090's own thin-stroke default).
- Add a `requestAnimationFrame`-driven rotating radar-sweep beam over that layer, bounded by the polygon's actual shape, using the trailing-fade/leading-edge *look* of `radar-sweep_4.html`, rendered through the same 3D-aware pipeline (deck.gl) already used for aircraft — so it stays correctly positioned and readable at this app's default steep pitch and over real terrain, not just in a flat top-down view.
- Paint currently-tracked aircraft as dots at their real lat/lon/altitude, each labeled with `hex`, via that same pipeline, flashing brighter as the sweep passes their bearing (porting the reference's contact-paint mechanic).
- Fit the existing per-layer toggle convention (`MapView.tsx`'s toggle row = this app's "layer menu", ref/state pair, survives theme/pilot-mode `setStyle` swaps).
- Fail gracefully (empty/no-op layer, no error) when `outline.json` is unavailable — unset feeder, network failure, or a non-readsb decoder that never generates the file.

**Non-Goals:**
- Computing a range outline client-side from accumulated `aircraft.json` polls when `outline.json` is unavailable. readsb already does this accumulation continuously since the receiver started; reimplementing it client-side would only ever reflect the current browser session and would duplicate work the decoder already does for free — same reasoning already established in `aircraft-tracks-layer`'s design for not reimplementing readsb's globe-history trace files.
- `multiOutline.json` (per-antenna/multi-receiver outline splitting) — single-feeder scope only, matching `getFeederUrl()`'s existing "one configured feeder" design.
- Antimeridian-wraparound ring splitting (tar1090's own `Math.abs(lon - lastLon) > 270` check in `drawOutlineJson()`) — a single feeder's real-world ADS-B range (tens to a few hundred NM) never spans the antimeridian in practice.
- A user-facing sweep-speed/color/style control. Fixed constants in `constants.ts`, matching how every other layer's paint properties are fixed, not user-configurable, in this app.
- Reproducing the reference's cross-frame Canvas2D "phosphor persistence" (`destination-out` accumulation across frames, never clearing) exactly. deck.gl layers redraw fresh every frame rather than accumulating onto a persistent framebuffer; see Decision 4 for the substitute technique that preserves the same "fading trailing wedge" requirement without a custom shader/render-to-texture pass.

## Decisions

### 1. Data source: readsb's own `outline.json`, not a client-computed polygon
`GET /data/outline.json` (same-origin, proxied — see Decision 2), refetched every `RANGE_OUTLINE_REFRESH_INTERVAL_MS` (`15_000`, matching tar1090's own `actualOutline.refresh`). Parsed with the same three-shape fallback chain as tar1090's `drawOutlineJson()` (`data.multiRange` → already an array of rings; `data.actualRange.last24h.points` → one ring; `data.points` → one ring), each ring's `[lat, lon]` pairs converted to GeoJSON `[lon, lat]` and closed (first coordinate repeated at the end, matching tar1090's own `j < points[p].length + 1` closing loop) into a `Polygon`/`MultiPolygon` `FeatureCollection`.
- **Alternative considered**: accumulate a per-bearing max-range client-side from every `fetchAircraft()` poll (same polling this app already does for `aircraft-tracks-layer`), building an outline independent of readsb's own file. Rejected (see Non-Goals) — would only reflect the current browser session's uptime, not the feeder's actual lifetime reception envelope, which is the entire point of the "actual" in "actual range outline."
- **Known limitation, accepted**: `outline.json` is a readsb (wiedehopf fork) feature. A feeder running plain `dump1090-fa` (FlightAware's fork, also accepted by this app's `aircraft.json`-parity design) never generates this file — the layer degrades to an empty fill (no error), same as the TFR layer's "no feed configured yet" state.

### 2. CORS: new same-origin proxy route, mirroring `receiver.json`
Ultrafeeder's own nginx only CORS-patches `aircraft.json`'s location block (`07-nginx-configure` — already documented in `feederLocation.ts`'s comment for exactly this reason). `outline.json` gets the same treatment as `receiver.json`: a fixed same-origin path (`/data/outline.json`), proxied server-side by this app's own nginx sidecar to `host.docker.internal:8080/data/outline.json` (new block in `scripts/squawkmap3d.nginx.conf`, copy of the existing `location = /data/receiver.json` block with the path swapped). `rangeOutline.ts`'s `fetchRangeOutline()` therefore always calls `fetch("/data/outline.json")` — never builds a URL from `NEXT_PUBLIC_FEEDER_URL` directly — gated on `getFeederUrl()` being set at all (same "no feeder configured → don't bother" gate `getReceiverUrl()` uses), exactly mirroring `feederLocation.ts`'s `getReceiverUrl()`.
- **Known limitation, accepted (inherited, not new)**: like `receiver.json` today, this proxy path only exists in the deployed nginx-sidecar setup (`deploy-to-feeder`); running via `next dev` locally without that sidecar means `/data/outline.json` 404s and the layer stays empty — not a regression, matches `receiver.json`'s existing local-dev behavior.

### 3. Fill layer: plain MapLibre `fill`, not deck.gl
The polygon is flat, non-elevated, GeoJSON-sourced data — exactly the shape `military-bases-fill`/`tfr-fill`/`sua-fill` already handle. Added via the existing `addCustomLayers`/`CustomLayerVisibility`/`CUSTOM_LAYER_IDS` machinery in `layers.ts`, no new rendering approach needed for the fill itself. Color: reuse tar1090's own `actual_range_outline_color` (`#00596b`, a dark teal, `html/defaults.js`) as `RANGE_OUTLINE_FILL_COLOR` — ties this app's rendering to the reference project's own convention and is visually distinct from every existing layer color (military pink, TFR red, SUA amber, airspace-boundaries cyan, airport purple).

### 4. Sweep animation: deck.gl layers on a dedicated overlay, not a flat DOM canvas
**Correction from the initial draft of this design**: a raw `<canvas>` absolutely positioned over the map (the reference's literal technique — `ctx.clip()`, `map.project()`-per-frame, `destination-out` fade) was the first approach considered here, but it does not play nice with this app's 3D view. `radar-sweep_4.html`'s own map is deliberately flat (`pitch: 0, dragRotate: false, pitchWithRotate: false`) — under those conditions, screen-space `map.project()` points and straight 2D lines between them are an adequate stand-in for "draped on the ground." This app's map is the opposite: it defaults to `INITIAL_PITCH = 60` (`MAX_PITCH = 85`) and has real 3D terrain (`terrain.ts`, `TERRAIN_EXAGGERATION = 3`). At a real pitch, a flat DOM canvas drawing straight screen-space lines between a handful of `map.project()`-ed polygon vertices would visibly diverge from the camera's actual perspective projection of that ground shape (worse the more oblique the view), wouldn't respect terrain occlusion at all (it's a flat layer always painted on top of everything, including any terrain in front of it), and — most importantly — is a fundamentally different rendering model than every other 3D-aware element in this app. This app already solved exactly this class of problem once: `aircraft-tracks-layer`'s design (Decision 1) chose deck.gl specifically because "MapLibre's `symbol`/`circle`/`line` layers drape onto the ground or terrain surface; there's no per-feature 'float this marker N meters above the terrain' property," and a flat canvas has the same limitation, minus even the ground-draping MapLibre gets for free. So: the sweep beam and aircraft dots (Decision 6) are built as **deck.gl layers**, recomputed each animation frame in real lng/lat (world) space and handed to deck.gl's own camera/projection — the same pipeline `aircraftLayer.ts` already uses and that this app's pitched/terrain view is designed around — rather than manually reprojecting to screen pixels every frame.
- Mounted on a **second, dedicated `MapboxOverlay`** (`interleaved: false`, same as the existing aircraft overlay — see `MapView.tsx`'s comment on the deck.gl/MapLibre terrain patch this app already carries), *not* folded into the existing aircraft `deckOverlayRef`. Keeping it separate avoids coupling this layer's ~60fps `requestAnimationFrame` update loop to the aircraft layer's ~1Hz poll-driven `setProps` calls (which would otherwise require merging two independently-updating layer arrays into one `setProps({ layers })` call every time either changes). This is a second small overlay instance, not a second big dependency — no new npm package.
- The wedge/beam geometry (`SolidPolygonLayer`, one or a few thin angular slices for the graded trailing-fade look — see Decision 4b) and the aircraft dots/labels (`ScatterplotLayer` + `TextLayer`, Decision 6) are computed as ordinary lng/lat polygons/points every frame and pushed via `overlay.setProps({ layers })`, exactly like `buildAircraftLayers()` already does for the aircraft overlay — just on a `requestAnimationFrame` cadence instead of a poll-interval cadence.
- **Trade-off, inherited from the existing aircraft overlay**: `interleaved: false` means this overlay's content, like the aircraft icons, does not depth-sort against the 3D terrain mesh (see `aircraft-tracks-layer`'s design, Decision 1's documented risk) — a sweep wedge won't be occluded by a mountain the camera is looking past. Accepted for the same reason it was accepted there: revisiting `interleaved: true` is a pre-existing, already-tracked follow-up for this app's whole deck.gl integration, not something to solve newly for this one layer.
- **Alternative considered (rejected)**: the flat `<canvas>` overlay described above — rejected per this decision's opening paragraph.
- **Alternative considered (rejected)**: folding the sweep/dots into the existing aircraft `MapboxOverlay`. Rejected — needless coupling between a ~1Hz data-poll-driven layer set and a ~60fps animation-driven one; a second overlay keeps both update loops independent and simple.
- **Alternative considered (rejected)**: sweeping via MapLibre `fill`/`fill-extrusion` with per-frame `setData`/`setPaintProperty`. Rejected — no per-frame rotate-a-wedge primitive, and constant style-layer mutation at 60fps is expensive; deck.gl is already the established tool in this codebase for exactly this kind of frequently-updated, elevation-aware geometry.

### 4b. Wedge geometry: ray-polygon intersection, not a clip mask
Without `ctx.clip()`, "the beam falls short in directions the site can't see" (matching the reference's visual behavior) is achieved by building the wedge polygon's own vertices to stop at the outline polygon's boundary, rather than drawing an unbounded shape and clipping it: for each angle sampled across the trailing wedge's width, cast a ray from the site position at that bearing and find its intersection with the actual-range outline polygon's ring, and use that intersection distance (or a fallback max radius if the ray doesn't hit the polygon — e.g. site position itself sits outside a multi-ring/oddly-shaped outline) as the wedge vertex's distance from the site. The same intersection distance also caps how far out an aircraft can be considered "on the scope" for the flash-on-pass effect in Decision 6, though dots themselves are still drawn at the aircraft's real position regardless (see Decision 6's note on this). This ray-casting approach is strictly more general than the reference's `ctx.clip()` (which relied on the reference's own simple parametric `POLAR_SHAPE`, not an arbitrary polygon) and works identically whether the outline is a single simple ring or (per Decision on `multiRange`) has multiple disjoint rings.
- The graded "fading trailing wedge" look itself (multiple angular slices with decreasing opacity moving away from the leading edge) is built the same way the reference already does *within* a single frame's beam draw (its own `WEDGE_STEPS` loop, independent of its separate cross-frame persistence effect) — so this alone reproduces the "fading trailing wedge" requirement without needing the reference's additional cross-frame accumulation trick, which doesn't have a clean deck.gl equivalent (see this design's Non-Goals).

### 5. Site position and sweep rate
The sweep's rotation center is the feeder's own surveyed antenna position — reuse the existing `getFeederLocation()` (`feederLocation.ts`) rather than resolving a separate location; this is the same anchor the actual-range outline itself is centered on (readsb computes the outline relative to its own configured receiver location).
Sweep rate is a fixed, decorative `RANGE_OUTLINE_SWEEP_PERIOD_MS` (one full revolution every 8 seconds — fast enough to read as "live," slow enough that aircraft flash-highlights and hex labels stay legible as the beam passes, unlike the reference's real-marine-radar 24-36 RPM which is tuned for a fast tactical display, not an ambient background effect over a slowly-changing ADS-B range polygon). Purely aesthetic; tunable in `constants.ts` without touching layout/logic.

### 6. Aircraft dots: deck.gl `ScatterplotLayer` + `TextLayer`, positioned at real altitude, independent of `aircraft-tracks-layer`
The sweep overlay's own module polls the same `fetchAircraft()` (`aircraft.ts`) this app's `aircraft-tracks-layer` already polls — not a new feed, not a second network integration — but builds its own dot+hex-label representation on its own dedicated overlay (Decision 4), gated only by this layer's own visibility toggle, independent of whether the aircraft-icons layer is separately toggled on or off. Every currently-reported aircraft with a known `lat`/`lon` gets a `ScatterplotLayer` point and a `TextLayer` label showing `hex` (not `callsign`/`flight` — the acceptance criteria specifically calls for the ICAO hex). Positioned at `[lon, lat, altitude * FEET_TO_METERS]` — the same real-altitude elevation `aircraftLayer.ts`'s `IconLayer` already uses (reuse that conversion) — rather than flattened to ground level, so a dot sits at the same 3D point in the pitched/terrain scene as that aircraft's own icon on the aircraft-icons layer, keeping the two layers visually consistent with each other when both happen to be on. A dot's color/size brightens for a short duration when the sweep beam's current bearing passes over that aircraft's bearing-from-site, porting the reference's `paintEvents`/`flashContactRow` mechanic (there: vessel callsign + shape, on sweep-pass only, contacts list panel; here: aircraft hex + dot, always drawn, brightened on sweep-pass — no separate list panel, since this app's existing UI has no equivalent side panel to reuse).
- **Not gated on being inside the outline polygon**: an aircraft can be currently tracked outside the actual-range polygon (e.g. a strong transient reception at unusually long range, or the outline simply hasn't caught up to a new max yet) — dots are drawn wherever the aircraft actually is; only the sweep beam's own wedge geometry is bounded by the polygon (Decision 4b).

## Risks / Trade-offs

- **[Risk] `outline.json` is readsb-specific**: plain `dump1090-fa` feeders (already an explicitly-supported `aircraft.json` source per this app's existing design) will never populate this file. → *Mitigation*: same graceful-empty handling as every other optional feed (TFR with no configured feed, OpenAIP with no API key); document this plainly rather than implying the layer works for every feeder type.
- **[Risk] New same-origin proxy route required for real deployments**: without the `scripts/squawkmap3d.nginx.conf` change, `outline.json` fetches will 404 even on a fully-configured readsb feeder. → *Mitigation*: ship the nginx change in the same PR (not a follow-up); call out in the deploy docs alongside the existing `receiver.json` proxy note.
- **[Risk] Per-frame cost**: rebuilding the wedge/dot deck.gl layers and running the ray-polygon intersection (Decision 4b) on every `requestAnimationFrame` (up to 60fps) adds CPU work beyond the existing aircraft overlay (which only rebuilds its layers on each 1s poll, not per animation frame). → *Mitigation*: typical feeder aircraft counts (tens, rarely hundreds) and a single polygon with a modest ring-vertex count keep this cheap; not pre-optimized (no throttled redraw below 60fps, no memoized ray-cast results between frames) per this app's stated "don't build it until real usage shows it's needed" philosophy (see `aircraft-tracks-layer`'s design, Risks) — revisit only if profiling shows it matters.
- **[Risk] A second `MapboxOverlay` instance's stacking order relative to the existing aircraft overlay is unverified**: two `interleaved: false` overlays each render to their own canvas layered over the map; which one visually paints on top depends on mount/control-add order, untested at design time. → *Mitigation*: flagged as an explicit verification task (aircraft icons should read clearly on top of the sweep wedge, not the reverse) — adjust mount order (or the overlay canvas's DOM/z-index position) during implementation if the default ordering reads wrong.
- **[Trade-off] Dropped the reference's cross-frame Canvas2D "phosphor persistence"** (repeated `destination-out` compositing that never clears, so old sweep positions/contacts visibly linger and fade across many frames) in favor of an intra-frame graded wedge only (Decision 4b) — deck.gl layers redraw fresh each frame rather than accumulating onto a persistent framebuffer, and building true cross-frame persistence would need a custom deck.gl layer/render-to-texture pass, out of scope for a decorative effect. The spec's "fading trailing wedge" requirement is still met by the intra-frame graded slices; only the reference's *additional*, slower-fading multi-frame glow is not reproduced.
- **[Trade-off] Deliberately diverges from tar1090's own visual style**: a solid fill instead of tar1090's thin stroke, plus a sweep animation tar1090 doesn't have at all. This is intentional per the acceptance criteria, not an oversight — call out clearly in `proposal.md`/code comments so it isn't "corrected" back toward tar1090 parity later.
- **[Trade-off] No historical range-outline diffing/animation** (e.g. "outline grew since last week") — this renders whatever `outline.json` currently reports, refetched every 15s, nothing more.

## Migration Plan

Purely additive — new files (`rangeOutline.ts`, `radarSweep.ts`), new layer/toggle, one new nginx proxy block, no new npm dependencies, no changes to any existing layer's behavior or the `aircraft-tracks-layer`/`feeder-deployment` capabilities' documented behavior. Rollback is deleting the new files/toggle/nginx block; nothing else depends on this layer existing.

## Open Questions

- Exact trailing-wedge width/fade-alpha/leading-edge styling constants are left to implementation to tune visually against a real or simulated `outline.json` + live feeder aircraft, same as `AIRCRAFT_TRACK_RETENTION_MS` was left to implementation in `aircraft-tracks-layer`'s design — not fixed precisely here beyond the `RANGE_OUTLINE_SWEEP_PERIOD_MS` default.
- Should the aircraft-dot flash-on-sweep-pass be skipped entirely if the sweep beam itself is invisible in that direction (i.e. outside the polygon at that bearing, per Decision 4 step 3's clip)? Left to implementation — a reasonable default is "flash regardless of clip," matching Decision 6's "dots aren't gated by being inside the polygon."
