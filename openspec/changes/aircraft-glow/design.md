## Context

`components/map/aircraftLayer.ts`'s `buildAircraftLayers()` already builds four deck.gl layers per feeder poll, in back-to-front paint order: `glowLayer` (a `ScatterplotLayer`, `AIRCRAFT_SELECTION_GLOW_LAYER_ID`, rarity-colored, data limited to zero-or-one element — only the currently *selected* aircraft), `trackLayer` (a `PathLayer` of many two-point segments, one per consecutive pair of recorded track points, colored per-segment via `resolveTrackPointColor`), `rotorLayer` (rotorcraft-only spin accent), and `iconLayer` (the `IconLayer`, colored per-aircraft via `resolveAircraftColor`). Both `resolveAircraftColor`/`resolveTrackPointColor` (`components/map/aircraftIcons.ts`) dispatch on the currently active `ColorMode` (`rarity` | `altitude` | `airspeed`, per the `aircraft-color-mode-control` capability) and return a plain `[r, g, b]` 0-255 triple.

Every icon/track element today is drawn at a single flat, non-glowing color. The only "glow" in the app is `AIRCRAFT_SELECTION_GLOW_*` (`constants.ts`) — a fixed-radius, rarity-tier-colored ring that exists purely as a "this is the selected aircraft" indicator, and only ever renders for that one aircraft. It is not a general visibility aid, and its color is intentionally decoupled from the active color mode (always rarity, regardless of whether rarity/altitude/airspeed mode is active) — this change must not alter that existing behavior.

## Goals / Non-Goals

**Goals:**
- Every rendered aircraft icon (not just the selected one) gets an always-on outer glow, colored as a brightened variant of that same aircraft's own current `resolveAircraftColor` result — so the glow's hue always matches whatever color mode is active.
- Every rendered track segment gets an always-on outer glow, colored as a brightened variant of that same segment's own current `resolveTrackPointColor` result, for the same reason.
- Keep the existing selected-aircraft rarity-colored highlight (`AIRCRAFT_SELECTION_GLOW_*`) completely unchanged in behavior, color, and sizing — the new glow is additive and stacks with it, not a replacement.
- No new npm dependencies — pure deck.gl, reusing exactly the `ScatterplotLayer`/`PathLayer` primitives already imported in `aircraftLayer.ts`.

**Non-Goals:**
- A user-facing control for glow intensity/size/on-off. Fixed tuning constants in `constants.ts`, matching how the existing selection glow and every other layer's paint properties are already fixed, not user-configurable.
- Glow around the rotorcraft rotor-accent icon (`AIRCRAFT_ROTOR_ACCENT_LAYER_ID`) — the acceptance criteria calls out tracks and icons (the aircraft's own airplane icon); the rotor accent is a small decorative overlay, not itself a primary visibility element.
- Any change to which color an aircraft/track renders under a given color mode, to icon size, to selection/hover/click hit-testing, or to the existing rarity-colored selection highlight's own appearance.
- A cross-fading/pulsing/animated glow. Static per-poll color and geometry, same update cadence (~1s, on feeder poll) as every other element `buildAircraftLayers()` already produces — not a `requestAnimationFrame`-driven effect like `radarSweep.ts`'s sweep beam.

## Decisions

### 1. Glow color: brighten the element's own current draw color, not a new fixed color
Both the icon glow and the track glow reuse the exact same color each element already renders under the active color mode (`resolveAircraftColor(d, colorMode)` for icons, `resolveTrackPointColor(point, colorMode, typeDesignator)` for track segments) and pass it through a new shared helper that blends it toward white by a fixed fraction. This directly satisfies the acceptance criteria's "slightly brighter than the draw color" — literally the same color, lightened — and means the glow never disagrees with what color mode is active (e.g. an airspeed-mode red aircraft gets a brighter red glow, not an unrelated fixed glow color).
- **Alternative considered (rejected)**: a single fixed glow color (e.g. white or pale yellow) applied to every icon/track regardless of color mode. Rejected — would visually flatten the color-mode distinctions this app already invests in (`aircraft-color-mode-control`), and doesn't read as "brighter than the draw color," which implies per-element variation.
- **Alternative considered (rejected)**: reuse `rarityToColor`/the existing selection glow's color logic for the new always-on glow too. Rejected — the selection highlight is deliberately rarity-colored *regardless* of active color mode (its whole purpose is "this is a selected aircraft, colored by rarity"); reusing that logic for an always-on, every-aircraft glow would make every aircraft's glow rarity-colored even in altitude/airspeed mode, contradicting Goal 1.

### 2. Brighten via linear channel blend toward white, not an HSL/HSV round-trip
New `brightenColor(rgb: [number, number, number], amount: number): [number, number, number]` in `components/map/aircraftIcons.ts` (alongside `hexColorToRgb`, which already does similar plain-RGB-triple math for the selection glow): each channel becomes `channel + (255 - channel) * amount`, rounded. This is a direct, dependency-free way to make a color "brighter" (closer to white) without introducing an RGB→HSL→RGB conversion utility this codebase doesn't otherwise need. `amount` is a shared constant (`AIRCRAFT_GLOW_BRIGHTEN_AMOUNT`), not re-derived per call site, so the icon glow and track glow are always "brighter by the same degree."
- **Alternative considered (rejected)**: convert to HSL, increase lightness, convert back. Rejected — more code and a new color-space dependency for a purely cosmetic, already-well-served-by-linear-blend effect; every other color helper in this file (`hexColorToRgb`, `altitudeToColor`, `airspeedToColor`) already works directly in RGB.

### 3. Icon glow: new, separate always-on `ScatterplotLayer`, not a modification of the existing selection-glow layer
A new layer (id `AIRCRAFT_ICON_GLOW_LAYER_ID`), built from `positioned` (the same filtered, has-lat/lon aircraft array the icon layer itself uses — i.e. every currently rendered aircraft, not `selectedAircraft`), `getFillColor: (d) => [...brightenColor(resolveAircraftColor(d, colorMode), AIRCRAFT_GLOW_BRIGHTEN_AMOUNT), AIRCRAFT_ICON_GLOW_ALPHA]`, `getRadius: AIRCRAFT_ICON_GLOW_RADIUS_PIXELS`, `pickable: false` (matches the existing glow layer — the glow itself is never a click/hover target; the `IconLayer` above it keeps that role). Kept as its own layer/id/constant group, entirely separate from `AIRCRAFT_SELECTION_GLOW_*`, so neither this change nor a future one can accidentally conflate "the always-on visibility glow" with "the selected-aircraft rarity highlight" — they have different colors, different trigger conditions (all aircraft vs. one selected aircraft), and different intended radii.
- **Sizing, relative to the existing selection glow**: `AIRCRAFT_ICON_GLOW_RADIUS_PIXELS` is deliberately smaller than `AIRCRAFT_SELECTION_GLOW_RADIUS_PIXELS` (32px) — a subtle halo just outside the 40px-wide icon (e.g. ~24px radius), not as large as the selection ring — so a selected aircraft still visibly stands out with its own larger rarity-colored ring layered outside this smaller, dimmer, per-aircraft glow, rather than the two being visually indistinguishable in size.
- **Alternative considered (rejected)**: repurpose `AIRCRAFT_SELECTION_GLOW_LAYER_ID` itself — feed it `positioned` instead of `selectedAircraft ? [selectedAircraft] : []` and switch its color from rarity to the brightened draw color. Rejected — this would silently remove the existing "selected aircraft gets a distinct rarity-colored highlight" requirement (still in `aircraft-tracks-layer`'s spec, unmodified by this change), since there'd be no remaining visual distinction between "selected" and "not selected" beyond nothing.

### 4. Track glow: a second, wider, lower-opacity `PathLayer` reusing the exact same `segments` array
Rather than duplicating the `for (const [hex, points] of tracks)` loop that already builds `segments: TrackSegment[]` (each with its own resolved `color`), the track glow layer (id `AIRCRAFT_TRACK_GLOW_LAYER_ID`) is built from that same `segments` array, with `getColor: (d) => [...brightenColor(d.color, AIRCRAFT_GLOW_BRIGHTEN_AMOUNT), AIRCRAFT_TRACK_GLOW_ALPHA]` and `getWidth: AIRCRAFT_TRACK_GLOW_WIDTH_PIXELS` (wider than the existing 2px track line), `pickable: false`. No changes to `TrackSegment`'s shape or the segment-building loop itself — the glow layer is purely a second consumer of the same computed data.
- **Alternative considered (rejected)**: bake the glow into the existing `trackLayer`'s own paint properties (e.g. a wider stroke with a gradient). Rejected — `PathLayer` has no built-in "glow"/outer-stroke concept; a second, wider, dimmer path underneath the first is the standard deck.gl technique for a glow/halo effect around a line, and keeps the crisp, fully-opaque original line completely unchanged (still legible for precise color-mode reading) with the glow purely additive beneath it.

### 5. Layer stacking order
`buildAircraftLayers()`'s returned array becomes `[selectionGlowLayer, iconGlowLayer, trackGlowLayer, trackLayer, rotorLayer, iconLayer]` — both new glows painted at the very bottom of the stack (beneath the existing selection glow, which stays visually outermost/largest since it's the least-frequently-visible, most-emphatic indicator and must not be swallowed by the new always-on glow), then the crisp track line, rotor accent, and icon on top, unchanged from today's relative order.

## Risks / Trade-offs

- **[Risk] Dense traffic areas**: overlapping per-aircraft glow circles or overlapping track glows in a busy terminal area could visually blur together into a less legible haze rather than a clean per-aircraft highlight. → *Mitigation*: keep both glows small-radius/low-alpha by default (tuned in `constants.ts`, adjustable without touching layout/logic — same "left to implementation to tune visually" approach `actual-range-outline`'s design used for its own trailing-wedge styling); not solved algorithmically (no clustering/decluttering), consistent with this app's existing "don't over-build until real usage shows it's needed" philosophy.
- **[Risk] Doubling the per-poll layer/data-array construction cost**: two additional deck.gl layers are built every feeder poll (~1s), one reusing the existing `positioned` array unchanged and one reusing the existing `segments` array unchanged (no new filtering/mapping passes beyond the color-brighten call, which is cheap arithmetic). → *Mitigation*: same order of magnitude as the work `buildAircraftLayers()` already does each poll; not pre-optimized, revisit only if profiling shows it matters.
- **[Trade-off] Selection highlight and always-on glow can look visually close for a selected aircraft** (a rarity-colored ring at 32px stacked outside a brightened-draw-color ring at a smaller radius) — accepted; Decision 3's sizing keeps them distinguishable, and exact final radii/alphas are left to visual tuning during implementation (Open Questions).

## Migration Plan

Purely additive — two new deck.gl layers, one new shared color helper, a handful of new constants, no new files, no new npm dependencies, no changes to any existing layer id, existing constant, or the `aircraft-color-mode-control`/selection/hover/click behavior. Rollback is deleting the two new layers, the new constants, and the new helper function; nothing else depends on them.

## Open Questions

- Exact `AIRCRAFT_ICON_GLOW_RADIUS_PIXELS` / `AIRCRAFT_ICON_GLOW_ALPHA` / `AIRCRAFT_TRACK_GLOW_WIDTH_PIXELS` / `AIRCRAFT_TRACK_GLOW_ALPHA` / `AIRCRAFT_GLOW_BRIGHTEN_AMOUNT` values are left to implementation to tune visually against a real feeder feed (starting points suggested in `tasks.md`), same as `AIRCRAFT_SELECTION_GLOW_RADIUS_PIXELS`/`AIRCRAFT_SELECTION_GLOW_ALPHA` and `RANGE_OUTLINE_SWEEP_PERIOD_MS` were left to implementation in prior changes' designs — not fixed precisely here beyond the relative-sizing constraint in Decision 3.
