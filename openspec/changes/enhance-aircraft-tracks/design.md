## Context

`components/map/aircraftLayer.ts`'s `buildAircraftLayers()` already builds, per feeder poll (~1s, `AIRCRAFT_FEED_REFRESH_INTERVAL_MS`): `iconGlowLayer`, `trackGlowLayer`, `trackLayer`, `rotorLayer`, `iconLayer` (paint order back-to-front), plus a separately-driven `requestAnimationFrame` selection-pulse overlay (`selectionPulse.ts`, out of scope here). `trackLayer`/`trackGlowLayer` are both `PathLayer`s built from a `segments: TrackSegment[]` array — one two-point segment per consecutive pair of a track's recorded points, each colored via `resolveTrackPointColor(point, colorMode, typeDesignator)` (`aircraftIcons.ts`), which dispatches on whichever of rarity/altitude/airspeed is the active `ColorMode`.

Track points themselves come from `components/map/aircraft.ts`'s `updateTracks()`: every feeder poll appends one `TrackPoint` (lat/lon/altitude/timestamp/groundSpeed) per aircraft to an in-memory per-hex buffer, pruned only by `AIRCRAFT_TRACK_RETENTION_MS` (10 minutes) — no point-count decimation. At the 1s poll interval this means a long-lived track can hold ~600 raw points, and `buildAircraftLayers()` already turns that into ~600 two-point `PathLayer` segments per aircraft, every poll, with no decimation today. This change adds two more per-point/per-segment visual elements (ground droplines, a ground curtain) that would multiply that already-uncapped cost if built from every raw point — see Decision 2.

Aircraft *icon* visibility (`aircraftVisible`/`aircraftVisibleRef` in `MapView.tsx`) currently gates the entire deck.gl overlay: when off, `refreshAircraft()` short-circuits before even calling `fetchAircraft()`, so polling itself stops and `clearTracks()` runs (aircraft.ts's documented "tracks reset on re-enable rather than resuming a stale trail" behavior). There is no separate toggle for the trail alone today — hiding aircraft hides everything, and there is no way to hide just the trail while keeping icons visible.

## Goals / Non-Goals

**Goals:**
- Every rendered track segment fades in opacity by age, except the single most-recent segment (the aircraft's current position, connecting it to its immediately-prior reported position), which stays fully solid — matching today's opaque line.
- A dotted vertical reference line drops from a decimated subset of each track's recorded points straight down to the ground (world z=0) at that point's lon/lat, always including the track's most recent point.
- A gradient "curtain" fades from the trail's own color down to transparent toward the ground beneath the trail, built from the same decimated point subset as the droplines.
- Track *visibility* (trail line, its glow, the new droplines, the new curtain) becomes independently toggleable from aircraft *icon* visibility, without stopping feeder polling, track recording, or icon rendering.

**Non-Goals:**
- Changing feeder polling, track recording/retention (`aircraft.ts`), or the `aircraft-color-mode-control` capability's color resolution itself — this change only adds an age-derived alpha and two new decorative elements layered on top of colors `resolveTrackPointColor` already produces.
- Applying the age-fade, droplines, or curtain to the aircraft icon itself, its own glow, or the rotor accent — the acceptance criteria is specifically about the *trail*.
- A user-facing control for fade rate, dropline spacing, or curtain band count — fixed tuning constants in `constants.ts`, matching every other track/glow visual constant already there (`AIRCRAFT_GLOW_BRIGHTEN_AMOUNT`, `AIRCRAFT_SELECTION_GLOW_*`, etc.).
- True per-vertex GPU gradient shading for the curtain (a custom deck.gl layer/shader). Approximated with stacked, decreasing-alpha `PathLayer` bands instead — see Decision 3.
- Decimating or capping the *existing* trail line/glow's own point resolution — those stay built from every raw recorded point, unchanged; only the two new elements (droplines, curtain) use the new decimated marker subset.

## Decisions

### 1. Age-based fade lives in `TrackSegment`, computed once per `buildAircraftLayers()` call, most-recent segment pinned solid
`TrackSegment` gains an `alpha: number` (0-255) field, computed when each segment is built in the existing `for (const [hex, points] of tracks)` loop: `ageFraction = (now - b.timestamp) / AIRCRAFT_TRACK_RETENTION_MS`, clamped `[0, 1]`, then `alpha = lerp(255, AIRCRAFT_TRACK_FADE_MIN_ALPHA, ageFraction)` — except the very last segment of each track (`i === points.length - 1`, the one ending at the aircraft's current position), which is always `alpha = 255` regardless of the formula, satisfying "the most recent trace is solid" literally rather than as a limiting case of the fade curve (a segment recorded 900ms ago would otherwise already read as very slightly faded under the linear formula, which doesn't match "solid").

`trackLayer.getColor` and `trackGlowLayer.getColor` both switch from returning a 3-tuple `[r,g,b]` (deck.gl defaults missing alpha to 255) to `[r, g, b, d.alpha]` — for `trackGlowLayer`, the glow's own fixed `AIRCRAFT_TRACK_GLOW_ALPHA` is scaled by the same `d.alpha / 255` factor, so the glow fades in lockstep with the line it sits under rather than staying at constant brightness under a fading line (which would look like the glow "escaping" the line as it dims).
- **Alternative considered (rejected)**: fade by point *index* within the track (e.g., oldest 10% of points) instead of wall-clock age. Rejected — index-based fade would look inconsistent across aircraft with different poll histories (a track that just started following selection would fade differently than a long-tracked one for the "same" relative age), where wall-clock age directly matches `AIRCRAFT_TRACK_RETENTION_MS`, the value that already governs when a point disappears entirely.

### 2. Droplines and curtain are built from a decimated "track marker" subset, not every raw point
A new helper, `selectTrackMarkers(points: TrackPoint[]): TrackPoint[]` (in `aircraftLayer.ts`, no new file), walks a track's points and keeps one point every `AIRCRAFT_TRACK_MARKER_INTERVAL_MS` (wall-clock, by `timestamp`) of separation, **always including the last (most recent) point** even if it falls short of a full interval since the previous kept marker — so the current position always gets a dropline/curtain edge, never just the most recent multiple-of-the-interval point. This bounds dropline/curtain element count to roughly `AIRCRAFT_TRACK_RETENTION_MS / AIRCRAFT_TRACK_MARKER_INTERVAL_MS` (10 min / 15s = ~40) markers per aircraft, independent of the feeder's actual poll rate — unlike the existing trail line/glow, which intentionally stays at full per-poll resolution since it's cheap (a single 2px path per segment) and losing resolution there would visibly chunk the trail's own shape.
- **Alternative considered (rejected)**: apply the same decimation to the trail line/glow itself for consistency. Rejected — the trail's shape/color fidelity is the primary "flight path" readout; decimating it to match the new decorative elements would be a visible regression to the existing, already-shipped trail requirement, not something the acceptance criteria asked for.

### 3. Ground curtain: stacked, decreasing-alpha `PathLayer` bands between consecutive markers, not a true gradient shader
For each consecutive pair of markers `(a, b)` from `selectTrackMarkers()`, `AIRCRAFT_TRACK_CURTAIN_BAND_COUNT` (6) horizontal bands are generated, each at a fixed height fraction `f = i / (bandCount - 1)` between the markers' altitude and the ground (`altitudeToRenderMeters(a.altitude) * f` / `... * f` for the two endpoints — both ends of a band scale by the same fraction, not one). Band `i`'s color is `[...resolveTrackPointColor(b, colorMode, typeDesignator), alpha]`, where `alpha = lerp(AIRCRAFT_TRACK_CURTAIN_TOP_ALPHA, 0, f)` for `f` measured from the top (`i = bandCount - 1`) down — the band nearest the trail line is most opaque, the band nearest the ground is fully transparent, approximating a continuous vertical gradient as a small number of discrete, decreasing-alpha steps. All bands across all markers of all tracks are pushed into one flat array and rendered as a single `PathLayer` (one `getColor`/`getWidth` call site, not `AIRCRAFT_TRACK_CURTAIN_BAND_COUNT` separate layer instances) — same "one layer, many path entries" shape as the existing `trackLayer`/`trackGlowLayer`.
- **Alternative considered (rejected)**: a true per-vertex gradient via a `SolidPolygonLayer` quad per marker-pair with vertex colors, or a custom deck.gl layer/shader. Rejected — deck.gl's built-in polygon layers only support per-polygon (not per-vertex) fill color, and hand-writing a custom layer/shader for a purely cosmetic gradient is materially more code/risk than this codebase has taken on for cosmetic effects so far (the icon glow's own "blur" is a pre-baked canvas filter, not a shader — see `2026-08-30-aircraft-glow`'s design.md Decision 3). A handful of stacked bands reads as "a gradient" at this app's icon/line scale without that cost.
- **Alternative considered (rejected)**: build the curtain from every raw track point (matching the trail line's own resolution) instead of the decimated marker subset. Rejected on cost grounds — see Decision 2; six bands per raw ~1s segment over a 10-minute track would be ~3,600 path entries per aircraft, before multiplying by however many aircraft are in view.

### 4. Droplines: a single `ScatterplotLayer` of fixed-count dot instances per marker, fixed neutral color
For each marker from `selectTrackMarkers()` (including the always-kept most-recent point), `AIRCRAFT_TRACK_DROPLINE_DOT_COUNT` (5) dot instances are generated at evenly-spaced heights between the marker's altitude and the ground, all pushed into one flat array rendered by a single new `ScatterplotLayer` (`AIRCRAFT_TRACK_DROPLINE_LAYER_ID`), `pickable: false`. Dot color is a fixed neutral `AIRCRAFT_TRACK_DROPLINE_COLOR` (light grey) at a low fixed `AIRCRAFT_TRACK_DROPLINE_ALPHA`, **not** derived from `resolveTrackPointColor`/the active color mode — this is a ground-reference cue (Ā«how far below this point is the ground, and where on the ground is itĀ»), not a data-carrying element, so tying it to color-mode semantics would risk being read as meaningful data it isn't. `ScatterplotLayer` is imported from `@deck.gl/layers`, the same package `IconLayer`/`PathLayer` already come from — no new npm dependency.
- **Alternative considered (rejected)**: color droplines the same as their parent track point (matching the curtain's approach). Rejected per the above — the curtain is explicitly framed as a colored "glow wash" continuation of the trail's own color, while the droplines are framed as a plain technical reference line (more like a lollipop-chart stem than a data visualization), and keeping them visually distinct (neutral grey vs. color-mode-driven) avoids a viewer misreading the dropline color as meaningful.

### 5. Track visibility toggle: a rendering-only filter, not a polling/recording gate
A new `tracksVisible`/`tracksVisibleRef` state pair in `MapView.tsx` (default `true`, matching every other layer toggle's default-on convention) is threaded into `buildAircraftLayers()` as a new `tracksVisible: boolean` param. When `false`, the four track-related layers (`trackLayer`, `trackGlowLayer`, the new dropline `ScatterplotLayer`, the new curtain `PathLayer`) are simply not built/returned (icon, icon-glow, and rotor layers are unaffected). Unlike `handleAircraftToggle` (which stops `fetchAircraft()` entirely and calls `clearTracks()`), `handleTracksToggle` does **not** touch polling or call `clearTracks()` — feeder polling and `updateTracks()` keep running exactly as if the toggle were on, so toggling tracks back on shows the full, uninterrupted trail rather than one that restarts empty from the moment it was re-enabled.
- **Alternative considered (rejected)**: mirror `handleAircraftToggle`'s `clearTracks()`-on-disable behavior for symmetry. Rejected — that behavior exists there specifically because disabling the *aircraft* layer stops the feed entirely (nothing is being recorded to resume from, so starting fresh on re-enable is the only sane behavior); tracks toggle off/on while aircraft stay visible has an actively-recording buffer the whole time, and discarding it on every hide/show would make the toggle needlessly destructive for what the acceptance criteria frames as a pure visibility control ("show/hide visibility of tracks").
- **Alternative considered (rejected)**: gate `updateTracks()` itself (stop recording while hidden, like the icon-visibility gate stops fetching). Rejected — recording is comparatively cheap (an array push + a filter per poll, already happening for every visible-but-track-hidden aircraft's icon anyway) and gating it would mean a user toggling tracks on/off to reduce visual clutter would unexpectedly lose track history for the time it was hidden, which the acceptance criteria's "show/hide visibility" framing doesn't ask for.

## Risks / Trade-offs

- **[Risk] Curtain/dropline visual clutter in dense traffic**: many overlapping tracks' curtains/droplines in a busy terminal area could visually blur together. → *Mitigation*: `AIRCRAFT_TRACK_MARKER_INTERVAL_MS`/band count/alpha values are left to implementation to tune visually (Open Questions), same "not solved algorithmically, tune the constants" approach `2026-08-30-aircraft-glow`'s design.md took for its own glow sizing.
- **[Risk] Age-fade makes very old (near-10-minute) segments hard to see against a busy basemap**: `AIRCRAFT_TRACK_FADE_MIN_ALPHA` floors the fade rather than letting it reach 0, so the oldest visible segment is dim but never fully invisible before it's pruned from the buffer — an intentional trade-off, not a bug, so a long trail's oldest end doesn't abruptly vanish mid-render.
- **[Trade-off] Curtain is a stepped (banded) approximation, not a true smooth gradient** — visible banding may be noticeable at close zoom. Acceptable per Decision 3; `AIRCRAFT_TRACK_CURTAIN_BAND_COUNT` can be raised later if it reads as too coarse, at proportional per-band draw cost.
- **[Trade-off] Droplines/curtain use a coarser point subset than the trail line itself**, so at a track's sharpest turns the ground-reference elements may not land exactly under every trail vertex. Accepted — see Decision 2's rejected alternative; the trail's own shape fidelity is unaffected.

## Migration Plan

Purely additive — new fields on the existing `TrackSegment` type, two new deck.gl layers, a new decimation helper, a handful of new constants, one new toggle/state pair, no new npm dependencies, no changes to feeder polling, track recording/retention, color-mode resolution, or icon rendering. Rollback is deleting the two new layers/helper/constants/toggle; the existing trail line/glow revert to their pre-change (fixed full-opacity, always-visible-with-icons) behavior with no other code depending on the new pieces.

- Whether the "Aircraft tracks" toggle row should live directly beneath "Aircraft" in the drawer's layer list, or in its own small indented sub-row implying it's scoped to the aircraft layer — left to implementation to match whatever reads clearest in `Accordion.tsx`'s existing `LayerToggleRow` list, not specified further here.
