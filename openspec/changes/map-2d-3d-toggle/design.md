## Context

`MapView.tsx` constructs `MapLibreMap` with `pitch: INITIAL_PITCH` / `maxPitch: MAX_PITCH` and adds a `NavigationControl({ showZoom, showCompass, visualizePitch: true })` at `top-left`. Aircraft are drawn by `buildAircraftLayers` (`aircraftLayer.ts`) via a deck.gl `MapboxOverlay` (non-interleaved): aircraft with a loaded `.glb` go to `AnimatedAircraftScenegraphLayer` groups, the rest to `IconLayer` (+ glow/rotor). The 2D icon path already exists and is kept as the fallback for unmodeled types, so 2D mode needs no new rendering code. Terrain is applied by `applyTerrain(map)` in `terrain.ts` on every `style.load`.

## Decisions

### 1. View mode is a ref/state pair, default `3d`
Same pattern as other toggles (`terrainOutlineVisibleRef` + state). Ref is read in `style.load` and poll callbacks. Initial value comes from `getStoredViewMode() ?? "3d"` (see Decision 8); the map is constructed already in the restored mode (pitch/maxPitch/terrain per mode) so there is no 3D flash when 2D was saved.

### 2. Toggle = separate additional button in the top-left group
The existing `NavigationControl({ showZoom, showCompass, visualizePitch: true })` is left untouched; the compass keeps MapLibre's default reset-north behavior in both 2D and 3D (reset bearing; in 3D `visualizePitch` also resets pitch as today). There is no capture-phase listener, no compass hijack, and no fallback-button logic.

Create `components/map/viewModeControl.ts`: `class ViewModeControl implements IControl` taking `{ getMode, onToggle }`. `onAdd(map)` returns a new `div.maplibregl-ctrl.maplibregl-ctrl-group` containing a single `button.maplibregl-ctrl-view-mode` whose text is the current mode label ("2D"/"3D"); `title`/`aria-label` is the action ("Switch to 2D view"/"Switch to 3D view"). Clicking calls `onToggle()`. `setMode(mode)` updates label and aria text. Styling matches the neighbors: same `maplibregl-ctrl-group` class gives the border/shadow/size; a small CSS rule for `.maplibregl-ctrl-view-mode` sets font (bold ~12px), centered text, and dark-theme colors consistent with how the app already styles MapLibre controls (check existing global CSS for `.maplibregl-ctrl-group` overrides and reuse them).

Placement: add with `map.addControl(viewModeControl, "top-left")` immediately after the `NavigationControl` so MapLibre stacks it directly below as part of the same top-left column (MapLibre appends controls in add order within a corner). If visual grouping requires a single joined group, `onAdd` may instead return a container that visually continues the nav group; either is acceptable provided spacing and styling match. The label shows the CURRENT mode (initially "3D"); the aria-label states the target action.

### 3. Entering 2D
`map.setMaxPitch(0)` then `map.easeTo({ pitch: 0, duration: ~500 })`; save prior pitch in a ref first. Disable terrain via `map.setTerrain(null)` and sky off, since terrain relief at pitch 0 would still displace deck.gl icons relative to the flat basemap. Bearing is NOT forced to 0 by the toggle (the compass owns reset-north); the user may keep any bearing. Pitch is 0 and locked: `dragRotate`/`touchPitch` remain enabled for bearing but pitch cannot change because `maxPitch` is 0. Compass remains reset-north in 2D (bearing only).

### 4. Entering 3D
`map.setMaxPitch(MAX_PITCH)`, re-run `applyTerrain(map)`, `easeTo({ pitch: savedPitch ?? INITIAL_PITCH })`. Bearing is left unchanged.

### 5. Models off in 2D
`buildAircraftLayers` gets `modelsEnabled`. When false, skip `resolveModelScenegraph` and push every aircraft to `iconOnlyPositioned`. Triggers an immediate layer rebuild on toggle (call the same refresh used on poll) so the swap is not delayed to the next ~1 Hz poll. The icon layer's `billboard: false` flat-in-ground-plane behavior is already correct at pitch 0 (top-down, nose-up icon rotated by track).

### 6. Style swaps
`style.load` handler (`setupStyleDependentState`) must consult `viewModeRef` when applying terrain, so theme/pilot-mode switches in 2D don't re-enable terrain.

## Risks
- Visual match of the added button with the MapLibre nav group depends on MapLibre control CSS; verify in both light and dark themes.
- `setMaxPitch(0)` while pitched clamps immediately in some versions; call `setPitch`/`easeTo` before or rely on the clamp (verify with MapLibre 6.5 docs).

### 8. Persistence via localStorage helper
Existing user prefs use a per-feature module with a namespaced key and SSR-guarded, try/catch-wrapped `localStorage` accessors: `components/map/theme.ts` (`THEME_STORAGE_KEY = "squawkmap3d:theme"`, `getStoredTheme`/`storeTheme`, read on mount via `getInitialTheme()` in `useRef`/`useState` initialisers at `MapView.tsx` lines ~157/249) and `components/map/drawer/drawerWidth.ts` (`squawkmap3d:layerDrawer:width`). The view mode follows exactly this: new `components/map/viewMode.ts` exports `VIEW_MODE_STORAGE_KEY = "squawkmap3d:viewMode"`, `type ViewMode = "2d" | "3d"`, `getStoredViewMode(): ViewMode | null` (null when SSR, unavailable, or any value other than `"2d"`/`"3d"`), `storeViewMode(mode)`, and `getInitialViewMode()` returning stored ?? `"3d"`. The toggle handler calls `storeViewMode` (as `storeTheme` is called at line ~967). Unavailable storage degrades silently to non-persistence.

### 7. Rotor animation in 2D (added; driven by SVG rotor bindings)
Exported icon SVGs for helicopters/drones/etc. with top-mounted rotors carry inert bindings: each rotor is `<g data-rotor="r1" data-rotor-pivot="x y" data-rotor-direction="cw|ccw" data-rotor-rpm="600">` wrapping its paths (pivot in viewBox user units; mirrored copies are `<id>-mirror`; SVGs without a top rotor have none and must be left unchanged; tail rotors/props are never tagged). These bindings, not the ADS-B emitter category, define which aircraft spin and how. Only top rotors are tagged: tail rotors, propellers, and side/front-view drawings are never tagged and never spin; a tilted top rotor is still tagged and is spun flat about its pivot. Whether a given SVG has bindings is determined by querying it, never assumed from aircraft type. `data-rotor-direction` is `cw`/`ccw` as seen looking at the nose-up SVG and is always read from the attribute (a contra-rotating symmetric pair yields `<id>` and `<id>-mirror` with mirrored pivots and normally opposite directions, unless the model says both turn the same way); direction matches the GLB `extras.rotor` for the same aircraft. `data-rotor-rpm` is real RPM (default 600), not a display rate. The semantic reference is the requester's DOM recipe (also implemented in another repo as `src/rotor-animation.ts`: `parseRotorBindings`, `readRotorBindings`, `applyRotorSpin`, `spinAngleDeg`; not present here): parse `data-rotor-pivot` as `cx cy`, `rpm = Number(rpm) || 600`, `revs = min(4, max(1, rpm/600*2.5))`, `sign = direction === 'cw' ? 1 : -1` (SVG positive angle is clockwise), `deg = sign*revs*360*t % 360`, applied as `rotate(deg cx cy)` and reset by removing the transform. That DOM approach (and SMIL / CSS `transform-origin`, which is viewBox-relative and wrong for non-zero viewBox origins) cannot be used here because icons are rasterized into the atlas; this design reproduces the same math in deck.gl. The asset SVGs already carry `[data-rotor]` bindings, so no icon re-export is part of this change.

Current state: the 2D rotor is a small generic rotor-disc `IconLayer` (`AIRCRAFT_ROTOR_ACCENT_LAYER_ID`, `aircraftLayer.ts` ~line 447) filtered to `category === ROTORCRAFT_CATEGORY`, with a per-poll stepped `getAngle`. This is replaced for any type whose SVG has `[data-rotor]` groups.

Why not just animate the inline SVG: icons are rasterized once into a single deck.gl `IconLayer` atlas (`aircraftIcons.ts`), so DOM `transform` attributes / SMIL cannot animate them. The bindings are used at atlas-build time instead, and the spin is applied in deck.gl.

Decisions:
- **Parsing (atlas build, `aircraftIcons.ts`)**: for each type SVG, query `[data-rotor]`. If none, behave exactly as today (single entry, no rotor sprites). If present: (a) rasterize the fuselage entry with all `[data-rotor]` groups removed so blades are not baked in and double-drawn; (b) rasterize each rotor group as its own atlas entry `<KEY>#<rotorId>` on a canvas the same size/viewBox as the fuselage, so the pivot's position within the sprite is `data-rotor-pivot` mapped through the viewBox->pixel transform: `pivotPx = ((px - viewBox.minX) * canvasW / viewBox.width, (py - viewBox.minY) * canvasH / viewBox.height)`. The pivot is in viewBox user units and icon viewBoxes usually have a non-zero origin, so the min-x/min-y subtraction is mandatory; a missing viewBox falls back to origin 0 and the SVG width/height. Record per type `{ id, pivot: [x,y] in viewBox units, sign: cw?1:-1, rpm }[]` in an exported `rotorBindingsByType` map alongside the atlas mapping.
- **Rotation about the pivot, not the sprite center**: deck.gl `IconLayer` rotates about the icon anchor. Set each rotor entry's `anchorX/anchorY` in the atlas mapping to the pivot's pixel position inside its sprite (`iconMapping[...].anchorX/anchorY`), so `getAngle` spins it about the hub while `getPosition` places the hub. Because the fuselage sprite uses the default centered anchor, the rotor layer needs a per-instance pixel offset (`getPixelOffset`) equal to (pivot - viewBox center) scaled to icon size, rotated by the aircraft's track (fuselage orientation), so the hub stays attached to the fuselage as the aircraft heads change. Alternative: render rotor sprites with the same full-canvas size and same centered anchor as the fuselage and spin them about the canvas center only when the pivot is the center; rejected because pivots are generally off-center (tandem, twin-rotor drones).
- **Two angles per instance**: deck.gl `angle` is counter-clockwise-positive while SVG `rotate()` and the track are clockwise-positive (see the existing `getAngle: -(d.track ?? 0)` comment). With `sign = cw ? +1 : -1` and `spinDeg = sign*revs*360*t % 360` (clockwise-positive, as in the docs' recipe), rotor `getAngle = -(track) - spinDeg`, i.e. fuselage angle plus the rotor's own spin about its pivot with the spin sign flipped for deck.gl. A `cw` rotor therefore must appear clockwise on screen; unit-test this.
- **Speed**: `revsPerSecond = clamp(rpm / 600 * 2.5, 1, 4)`, per-rotor, sign from `data-rotor-direction` (never assume direction; contra-rotating pairs have opposite directions). Constants `ROTOR_DEFAULT_RPM = 600`, `ROTOR_REVS_MIN = 1`, `ROTOR_REVS_MAX = 4`, `ROTOR_REVS_AT_DEFAULT = 2.5` in `constants.ts`. Spin angle (clockwise-positive, before the deck.gl flip) = `(sign * revs * 360 * tSeconds) % 360`; per the docs the rate may differ from the reference formula but the sign always comes from `data-rotor-direction`.
- **Per-frame, not per-poll**: while `viewMode === "2d"` and at least one rendered aircraft has rotor bindings, a rAF loop (capped ~30 fps) bumps a frame tick and updates only the rotor layers (via `updateTriggers: { getAngle: tick }` and `deckOverlay.setProps({ layers })` with the cached non-rotor layers reused), not the full per-poll rebuild. Loop stops on switch to 3D, when no rotorcraft are visible, and on unmount.
- **Fallback**: aircraft the app already treats as rotorcraft (category A7) whose SVG has no `[data-rotor]` bindings keep the existing generic rotor-disc accent, now also per-frame instead of per-poll, so nothing regresses. Fixed-wing aircraft and SVGs without bindings never get rotor animation.
- **Not needed in 3D**: `AnimatedAircraftScenegraphLayer` already animates "Rotors" nodes per frame; 3D and 2D direction should agree since SVG direction matches the GLB `extras.rotor`.

### 9. No altitude lift in 2D (user decision)
In 2D mode the camera is top-down with perspective, so an aircraft drawn at its real altitude appears displaced from its ground position toward the screen edges. In 2D every aircraft-derived position uses z = 0: icon, icon glow, rotor accent, rotor binding, track paths, dropline dots (zero-length, so equivalent to a single point) and the selection pulse ring. `altitudeToRenderMeters(alt, flat)` is the single switch, with `flat = !modelsEnabled` (view mode 2D). 3D is unchanged. Altitude-based color and the altitude readout are unaffected; only the vertical lift is removed. Toggling modes already triggers an immediate rebuild, and the rotor/pulse rAF loops read the current mode each frame, so z follows the mode with no extra wiring.
