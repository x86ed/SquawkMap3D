## Context

`components/map/MapView.tsx` (1140 lines) currently renders every layer toggle as a flat `<button>` in a single `.controls` column (`MapView.module.css`, `position: absolute; top: 12px; right: 12px`), each wired to its own `ref`+`useState` pair and `handle*Toggle` function already defined in the file (e.g. `handleMilitaryToggle`, `handleAirportsToggle`, `handleTerminatorToggle`, ... `handleUserLocationToggle`). Two other floating docks already coexist with this column and are deliberately positioned to clear it: `ColorModeLegendDock` sits at `right: 210px` specifically because — per its own CSS comment — "MapView.tsx's own top-right toggle-button column ... needs to clear." `AircraftColorDock` (bottom-left) and `AircraftOverlay` (bottom, full-width, `z-index: 3`) round out the existing overlay landscape.

The user supplied a reference implementation, `/Users/adamsiegel/Downloads/adsb-drawer.html` (a self-contained MapLibre + vanilla-JS mock, ~1290 lines), demonstrating the exact drawer chrome, accordion behavior, tab nav, and sortable table this change should structurally match — its CSS custom-property theme tokens (`--drawer-w: 452px`, `--radius-md`, `--accent`, etc.), `.accordion-group`/`.acc-btn`/`.layer-row`/`.switch` class structure, and `.tabnav`/`.tabpanel`/table sort-indicator patterns are the direct visual/structural reference for the new components, adapted to this app's existing hand-rolled-CSS-Modules convention (no UI kit — see Decision 1) and *real* data (see Decision 6) rather than the reference's mocked/random aircraft generator.

This app already tracks real aircraft via `components/map/aircraft.ts`'s `fetchAircraft()`, polled independently in two places today (`MapView.tsx`'s own aircraft-icon-layer poll, and `rangeOutlineAircraftRef`'s separate poll for the radar-sweep dots — an established, accepted pattern of "each consumer polls independently" per `actual-range-outline`'s own design doc). The plane-listing panel added here is a third independent consumer of the same feed, following that same precedent (Decision 7).

## Goals / Non-Goals

**Goals:**
- Replace the unscalable flat `.controls` button stack with a right-hand drawer matching the reference's chrome/accordion/tab structure, without changing any existing layer's rendering, refresh, or visibility-toggle *logic* — only where its toggle control lives.
- Add a real, sortable, searchable/filterable table of currently-tracked aircraft inside that drawer, backed by data this app already fetches (`fetchAircraft()`), not a new feed.
- Split the "user location marker + range rings" combined toggle into two independent toggles, per the acceptance criteria's explicit requirement.
- Extend `Aircraft`/`normalize()` with the additional real `aircraft.json` fields the table's columns need (`messages`, `rssi`, `type`→`sourceType`, `dbFlags`→`isMilitary`, `wd`/`ws`), using only fields readsb's own JSON documents — no invented data.

**Non-Goals:**
- No new gamification/tracking system for XP, "registrations seen," or "flight time" — these don't exist anywhere in this codebase today (only `aircraftRarity.ts`'s tier/value system exists), and building session-persistent per-hex history tracking is a separate feature, not a UI-container change. These three columns ship as explicit, hidden-by-default placeholders (see Decision 9), same treatment the acceptance criteria itself gives the Wildfires layer.
- No new UI component library (MUI, Radix, shadcn, etc.) — every existing interactive component in `components/map/overlay/` and `components/map/controls/` is hand-rolled React + CSS Modules; this change follows that convention (Decision 1).
- No change to any layer's MapLibre/deck.gl rendering, data-fetch, or refresh-interval logic — every accordion row calls the exact same `handle*Toggle` function that today's flat button called; only the JSX that renders the button moves.
- No virtualized/windowed table implementation (e.g. `react-window`) — deferred; see Decision 8's note on typical row counts and the Risks section.
- No server-side or persisted sort/filter/column state beyond `localStorage`, mirroring `theme.ts`'s existing `THEME_STORAGE_KEY` pattern for the one thing worth persisting (visible columns), not the full filter/sort state.

## Decisions

### 1. Hand-rolled React + CSS Modules, no new UI library
Every existing interactive surface in this codebase (`AircraftOverlay`, `PlaneCard`, `AircraftColorDock`, `ColorModeLegendDock`, `TelemetryMarquee`) is a plain function component with a co-located `.module.css` file — no `package.json` dependency on any component/UI-kit library exists today. The drawer, accordion, tabs, and table are built the same way: `components/map/drawer/LayerDrawer.tsx` + `.module.css`, `Accordion.tsx` + `.module.css`, `PlaneListingPanel.tsx` + `.module.css`, `PlaneTable.tsx` + `.module.css`. The reference file's CSS custom-property tokens (`--panel`, `--border`, `--accent`, `--radius-md`, etc.) are reproduced as this app's own CSS Module custom properties, scoped under the drawer root rather than global `:root`, so they don't leak into or collide with any existing component's styling.
- **Alternative considered (rejected)**: adopt Radix UI primitives (`Accordion`, `Tabs`) for accessibility scaffolding. Rejected for this change — it would be the first UI-kit dependency in the project, a larger decision than this change's scope, and the reference implementation's own accordion/tab behavior (single `open` class toggle, `hidden` attribute on tab panels) is simple enough to hand-roll consistent with every other interactive component here. Revisit only if a future change needs more complex a11y behavior than a hand-rolled `aria-expanded`/`role="switch"` implementation provides.

### 2. Top-right cluster shrinks to 3 controls; everything else moves into the drawer
The acceptance criteria specifies exactly two elements in the top-right corner: a day/night slider and a drawer-toggle button. This app also has a pre-existing, unrelated-to-layers "Pilot mode" control (`pilot-map-mode` capability) that restyles the base map the same way the theme toggle does — conceptually a map-style switch, not a "layer." It stays as a third small pill alongside the slider/drawer-button in the same top-right cluster (unchanged behavior, only re-skinned to match the slider/button's new glass-pill look), rather than being buried inside the drawer's Layer Controls accordion where it doesn't fit any of the three named groups.
- Every other existing top-level control (`Follow selected aircraft`, `My location`/jump-to-location) relocates into a small, always-visible, non-accordion "view controls" row at the top of the drawer body (below the header, above the Layer Controls accordion) — not deleted, not folded into `AircraftColorDock`. `AircraftColorDock` is out of scope for this change (its own dock, color-mode-control specific); adding unrelated controls to it would be scope creep beyond "the minimum change required."
- **Alternative considered (rejected)**: drop the standalone "My location" button as redundant with `AircraftColorDock`'s existing `onRecenter` wiring (same `handleJumpToLocation`). Rejected — no behavior in the acceptance criteria authorizes removing an existing control, and `AircraftColorDock`'s recenter button only appears in that dock's own UI, a separate discoverability path a user relying on the old `.controls` column wouldn't necessarily find.

### 3. Aviation group includes two layers not named in the acceptance criteria (Military Bases, Aircraft icons)
The acceptance criteria's Aviation list (Airports, OpenAIP TMS, TFRs, SUA, Airspace Boundaries) doesn't mention this app's two other existing aviation-related toggles: `militaryVisible` (military-bases-layer) and `aircraftVisible` (the on-map aircraft icons themselves, `aircraft-tracks-layer`). Dropping either toggle's control entirely would be a silent regression (removing user-facing functionality the change request never asked to remove); neither fits the Location or Environmental groups. Both are added as additional Aviation rows after the five named ones, keeping every existing capability's documented toggle behavior intact.
- **Alternative considered (rejected)**: invent a fourth accordion group ("Traffic" or similar) just for these two. Rejected as unnecessary complexity for two rows; Aviation is the closest conceptual fit for both (military bases are aviation infrastructure; aircraft icons are the core aviation content layer), and the reference mock's own Aviation group description ("Airports, airspace & restrictions") is generic enough to comfortably host them.

### 4. "Weather" is a nested disclosure over 5 already-independent layers, not a new merged toggle
This app has 5 separately-specced, separately-toggleable weather/radar layers (`rainviewer-radar-layer`, `nexrad-layer`, `noaa-radar-layer`, `dwd-radolan-layer`, `noaa-infrared-satellite-layer`), each with a spec requirement stating the user "SHALL be able to show or hide [it] independently of any other map mode ... **or other toggleable layer**." The acceptance criteria's Environmental group lists a single "toggle weather" row (matching the reference mock's own single mocked "Weather Radar" toggle, which has no equivalent to this app's 5 real sources). Collapsing all 5 into one merged boolean would silently break each of those 5 specs' own documented independent-toggle requirement (a `noaa-radar-layer` on/`nexrad-layer` off combination the current spec set explicitly allows would become impossible).
Instead: the Environmental accordion group's "Weather" row is itself a nested one-level disclosure (same open/closed chevron mechanic as the outer accordion groups, reusing the same `Accordion`/`AccordionGroup` component recursively) that reveals the 5 existing layers' own switches, each still fully independent, each still governed by its own unmodified `handle*Toggle`/`set*Visibility` function. No spec file changes needed for any of the 5 weather-layer capabilities — this is a pure UI-placement decision.
- **Alternative considered (rejected)**: one boolean toggling all 5 layers together (matching the reference mock's literal single-switch-per-row visual simplicity). Rejected per the spec-regression reasoning above.
- **Alternative considered (rejected)**: promote all 5 to top-level Environmental rows (no nesting), abandoning "Weather" as a single row entirely. Rejected — doesn't satisfy the acceptance criteria's literal "toggle weather" line item as a discoverable single entry, and clutters the Environmental group more than the reference's 3-row design intends.

### 5. Range rings become an independent toggle, split out of `setUserLocationVisibility`
Today, `components/map/userLocation.ts`'s `setUserLocationVisibility(map, visible)` sets `USER_LOCATION_ICON_LAYER_ID`, `USER_RINGS_LINE_LAYER_ID`, and `USER_RINGS_LABEL_LAYER_ID`'s visibility together, and `user-location-marker`'s spec documents this as one combined requirement. The acceptance criteria explicitly calls for range rings to be "separated from transponder location layer." This change splits that one function into `setUserLocationMarkerVisibility(map, visible)` (icon layer only) and `setRangeRingsVisibility(map, visible)` (the two ring/label layers only), each called from its own new `MapView.tsx` ref+state+handler pair (`rangeRingsVisibleRef`/`rangeRingsVisible`/`handleRangeRingsToggle`, alongside the renamed-in-place `userLocationVisibleRef` which now governs the marker/icon alone).
- The underlying geometry-building code (`buildUserLocationFeatures`, `addUserLocationLayers`) is unchanged — both the marker source and the rings source are still built and added together whenever a location resolves; only which layers a given toggle affects changes.
- **Known limitation, accepted**: if a user hides "Transponder Location" while range rings stay visible, the rings appear centered on a now-invisible point with no marker there — this is the acceptance criteria's explicit intent (independent toggles necessarily allow this combination), not a bug.

### 6. Plane-listing columns render real data where it exists; XP/Registrations/Flight Time are explicit placeholders
Cross-referencing the acceptance criteria's 26-column list against what this app can actually compute:
- **Already available, no change needed**: Hex ID (`hex`), Callsign (`callsign`), Type (`typeDesignator`), Squawk (`squawk`), Altitude (`altitude`), Speed (`groundSpeed`), Vertical Rate (`verticalRate`), Track (`track`), Seen (`secondsSinceLastMessage`), Latitude/Longitude (`lat`/`lon`), Registration (`registration`).
- **Real data, needs `Aircraft`/`normalize()` extension** (readsb's `aircraft.json` documents all of these; this app just never parsed them): Messages (`messages`), RSSI (`rssi`), Source (`type` → `sourceType`, avoiding the `type` keyword clash the same way `t`→`typeDesignator` already does), Mil. (`dbFlags` bit `0x1` → `isMilitary`), Wind D./Wind S. (`wd`/`ws` → `windDirection`/`windSpeed`).
- **Real data, needs a small new derivation, no new fetch**: Distance (great-circle distance from the resolved site location — reusing the exact `GeoCoords` this app already resolves for range rings/rangeOutline — to the aircraft's `lat`/`lon`, via `@turf/turf`'s already-installed `distance()`), Flag (registration-prefix → ISO country code → `flagSvgPathForCountryCode()`, already used by `airportPopup.ts` for a different purpose), Rarity (`computeRarityTier`/`computeRarityValue`, already implemented in `aircraftRarity.ts`).
- **Real data, needs a new throttled network lookup** (see Decision 7): Airline, Route.
- **No backing computation anywhere in this codebase; explicit placeholders** (Non-Goals): XP, Registrations, Flight Time, Level. Each renders `"—"` and is excluded from the default-visible column set (mirroring `COLUMNS`'s `def: false` pattern in the reference file) — visible only if a user explicitly enables it from the Columns tab, at which point it still just shows `"—"` for every row. This is called out in a short inline code comment in `columns.ts`, not silently faked with random numbers (unlike the reference mock's own `genAircraft()`, which exists purely to demo the UI with plausible-looking fake data).

### 7. Plane-listing panel owns its own independent `fetchAircraft()` poll
Following the precedent already established twice in this codebase (`MapView.tsx`'s aircraft-icon-layer poll and `rangeOutlineAircraftRef`'s separate poll for the sweep overlay, both polling `fetchAircraft()` independently at `AIRCRAFT_FEED_REFRESH_INTERVAL_MS`), `PlaneListingPanel.tsx` runs its own poll rather than having `MapView.tsx` lift the full aircraft list into React state and prop-drill it down. Lifting it into state would force the entire `MapView` tree (including the map container) to re-render every poll tick; an independent poll scoped to the panel's own component keeps that re-render contained to the drawer subtree, and only actually runs/renders while the drawer is open (see Decision 8).
- `siteLocation` (needed for the Distance column) is the one piece of state that *is* lifted from `MapView.tsx`, since it changes rarely (only on location resolution/re-jump, not every second) — a plain `useState<GeoCoords | null>` mirroring the existing `userLocationRef.current` assignment, passed down as a prop.

### 8. Table poll only runs while the drawer is open
`PlaneListingPanel`'s `fetchAircraft()` poll (`setInterval`, `AIRCRAFT_FEED_REFRESH_INTERVAL_MS`) starts on mount and clears on unmount; `LayerDrawer` only mounts `PlaneListingPanel` while `drawerOpen` is true (not just visually hidden via CSS), so the extra poll and table re-render cost only exists while a user actually has the drawer open — avoiding a third always-running poll for a panel most sessions won't have open most of the time.

### 9. Route/Airline lookups are throttled and cached, not fetched per-row per-poll
`getFlightRoute()` (`flightRoute.ts`) POSTs to the third-party `adsb.im` public routeset API and is currently only ever called once, on-demand, for the single selected aircraft (`AircraftOverlay`). Calling it for every row of a potentially-large table on every 1-second poll tick would be a large, unnecessary burst of requests against a public API not meant for that load. Instead:
- Route/Airline lookups are keyed by **callsign**, not by poll tick: `PlaneListingPanel` maintains a `Map<callsign, FlightRoute | null>` cache (component-local, reset on unmount) and only calls `getFlightRoute()` for a callsign it hasn't already resolved (or that has changed since last resolved), regardless of how many poll ticks that callsign has appeared in.
- Airline is derived locally and instantly from the callsign's own ICAO 3-letter prefix against the new vendored `airlineDesignators.json` — no network call at all for that column, only Route needs the `adsb.im` lookup.
- **Known limitation, accepted**: a very large simultaneous aircraft count (rare for a single feeder's typical range) means a burst of first-seen-callsign lookups the first time the table renders with many rows; unlike the per-second poll itself, this is a one-time cost per newly-seen callsign, not a recurring one.

### 10. Sortable table, no virtualization
The reference implementation's own table has no virtualization (a plain `<table>`/`<tbody>` re-rendered on every filter/sort change) and its own mock generates 46 rows — in the same range as a typical single feeder's realistic simultaneous aircraft count (tens, rarely hundreds). `PlaneTable.tsx` follows the same plain-`<table>` approach: sort state (`{ key, dir }`) held in the panel, `Array.prototype.sort()` on click, `<thead>` sort-direction indicator matching the reference's chevron icons. Column visibility (`Set<columnKey>`) defaults to the same subset of columns the reference file marks `def: true` for its own analogous fields, persisted to `localStorage` under a new key (mirroring `theme.ts`'s `THEME_STORAGE_KEY` pattern) so a user's column choices survive a reload.
- **Alternative considered (deferred, not rejected outright)**: windowed/virtualized rendering (e.g. `react-window`) for very large row counts. Not pursued now — no evidence this app's realistic aircraft counts need it, and it would be this project's first virtualization dependency. Revisit if real-world usage shows the plain table is slow.

## Risks / Trade-offs

- **[Risk] Splitting the user-location toggle is a documented behavior change** to an existing, specced capability (`user-location-marker`) — any external documentation/screenshots referencing "one toggle for marker + rings" is now stale. → *Mitigation*: the acceptance criteria explicitly requests this split; the spec delta (see `specs/user-location-marker/spec.md`) documents the new two-toggle behavior precisely, and no other capability depends on the old combined-toggle behavior.
- **[Risk] Moving every layer toggle out of `.controls` and into an accordion changes muscle memory** for anyone used to the flat button column. → *Mitigation*: every toggle keeps its exact same underlying handler/behavior/state — only discoverability changes (one click to open the drawer, then find the right accordion group), which is the entire point of this change (the flat stack no longer scales).
- **[Risk] Route/Airline lookups still call a public third-party API (`adsb.im`) from every client**, now potentially for more distinct callsigns per session than before (every row a user has ever seen in the table, not just ones they clicked). → *Mitigation*: Decision 9's per-callsign cache means each distinct callsign is looked up at most once per session, not once per poll tick — bounded by "how many distinct aircraft passed through my feeder's range today," not by polling frequency.
- **[Trade-off] XP/Registrations/Flight Time ship as inert placeholder columns**, not real features, despite appearing in the acceptance criteria's column list. → *Mitigation*: explicitly called out in this design and `proposal.md` as an intentional scope boundary (Non-Goals), not a missed requirement; a future change can wire up real per-hex session/history tracking (analogous to `aircraft-tracks-layer`'s existing session-local track buffers) if that gamification system is wanted as its own feature.
- **[Trade-off] No table virtualization** — acceptable for today's realistic single-feeder aircraft counts per Decision 10, revisit only if it proves slow in practice.

## Migration Plan

Primarily additive (new `components/map/drawer/` tree, new small lookup modules, `Aircraft` interface field additions) plus one localized, deliberate behavior change (Decision 5's toggle split) and one JSX relocation (every existing `.controls` button moves into the new drawer, calling the exact same handler it already called). Rollback is reverting `MapView.tsx`'s render section back to the flat `.controls` list and re-merging `setUserLocationVisibility` — no data migrations, no new persisted state beyond the new `localStorage` column-visibility key (safe to ignore/clear).

## Open Questions

- Exact vendored `airlineDesignators.json` source/coverage (which carriers, how many entries) is left to implementation to source from a suitable public ICAO-designator dataset, same as `aircraftRareness.json` was vendored from `taildragger`'s dataset in a prior change — not fixed precisely here.
- Exact drawer width, breakpoint behavior on narrow/mobile viewports, and whether the top-right cluster hides while the drawer is open on mobile (the reference file does this at `max-width: 640px`) are left to implementation to tune visually, following the reference's own mobile CSS as a starting point.
- Whether filter/search state (not just column visibility) should also persist to `localStorage` across sessions is left open — Decision 10 only commits to persisting column visibility; implementation may extend this if it proves clearly desirable, without blocking this change.
