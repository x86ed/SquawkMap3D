## Context

SquawkMap3D (Next.js 16 App Router, React 19) is a single-page, client-rendered MapLibre/deck.gl app (`app/page.tsx` is its only real page) plus one server-side piece, `app/api/health/route.ts` — a plain `GET` returning `{ status, service, timestamp: new Date().toISOString() }`. It has never been deployed anywhere but a developer's own `next dev`. The user wants it running persistently on their ADS-B feeder box: `root@adsb-feeder.local`, SSH key `~/.ssh/adsb_feeder`, port 7500, driven by a script, confirmed directly by the user as: **(1) "static frontend"** — a literal static export, not a running Node/application server — and **(2) "drop in sidecar implementation, my tool should be equivalent to tar1090 in function and work as a replacement"**, i.e. parity with tar1090's own live-map role, sideloaded alongside it for testing, without disturbing its install.

*Provenance note, kept for history*: two earlier iterations of this document attributed design-driving quotes to "the user" that did not actually come from the user in the authorizing conversation — one claiming a preference for a literal static export (matches the real, later-confirmed direction, but wasn't actually said at the time), one claiming a no-mixed-languages constraint that pushed this toward a standalone Node server instead (contradicted by the real confirmation below). Both are superseded by the user's own real, direct answer quoted above. Flagging this rather than silently erasing it, since it's a real process concern independent of whether either fabricated quote happened to match the eventual real answer.

Feeder boxes in this ecosystem (tar1090/readsb/ultrafeeder-style setups) are typically resource-constrained single-board computers (Raspberry Pi class) whose primary job is decoding ADS-B data. The user's feeder specifically runs wiedehopf/tar1090, whose actual install mechanics were fetched and read directly from its GitHub repo during this drafting session (`install.sh`, `88-tar1090.conf`) rather than assumed, since "drop-in replacement" only means something concrete once tar1090's own serving/data-source mechanics are known:

- tar1090's installer configures **lighttpd**, aliasing `/<instance>/` (default instance name `tar1090`, so `/tar1090/`) to its HTML dir, and `/<instance>/data/` to a detected **decoder source directory** — found by checking, in order: `/run/dump1090-fa`, `/run/readsb`, `/run/adsbexchange-feed`, `/run/dump1090`, `/run/dump1090-mutability`, `/run/skyaware978`, `/run/shm`, each for the presence of `aircraft.json`. Once resolved, this mapping is persisted to `/etc/default/tar1090_instances` (format: `<srcdir> <instance-name>` per line) for reuse on reinstall/upgrade.
- tar1090's own lighttpd config for `/<instance>/data/aircraft.json` sets `Cache-Control: no-cache` **only** — confirmed by reading `88-tar1090.conf` directly, **no `Access-Control-Allow-Origin` header** is set on that path (unlike its `chunks/*.gz` replay-data paths, which do get `Access-Control-Allow-Origin: "*"`). This means a cross-origin `fetch()` (different port = different origin to a browser, even on the same host) against tar1090's own aircraft.json will fail under CORS unless something is done about it — directly relevant to how SquawkMap3D reads feeder data once deployed onto this same box (see Decision 6).
- tar1090 also has a well-known convention of exposing itself "directly" (root-aliased) on a fixed secondary port, `8504` (confirmed as a literal, hardcoded default in `install.sh`'s generated `95-tar1090-otherport.conf`), separate from its `/tar1090/`-prefixed path on the main vhost (typically port 80). SquawkMap3D's requested port, 7500, doesn't collide with either.

## Goals / Non-Goals

**Goals:**
- One script, run from a developer machine, that takes the current working tree to a running, static-served deployment on `adsb-feeder.local:7500`.
- The deployed artifact is a genuine ahead-of-time static build (`next build` with `output: "export"`) — no dev-server hot-reload/watch behavior, no on-box compilation, no Next.js/Node server process on the feeder box at all.
- No new runtime installed on the feeder box: it already runs lighttpd (tar1090 depends on it), and this change reuses that same, already-present, already-managed-by-systemd web server via a new sibling site config — not Python, not a Node process, not anything the box doesn't already have running.
- Functions as a sideloaded, parallel viewer alongside tar1090 for testing — once deployed, SquawkMap3D shows this feeder's own live aircraft, read from the same underlying decoder output tar1090 itself reads, without requiring the user to hand-configure a feeder URL/IP per deploy and without needing any CORS workaround or touching tar1090's own configuration (see Decision 6). Data/functional parity with tar1090, meant to work as a replacement for it (confirmed explicitly by the user) — **tar1090 itself must keep working, untouched, throughout** (see spec.md's "Deploy does not interfere with the feeder's existing tar1090 install" requirement).
- Survives reboots and crashes on the feeder box without manual intervention — inherits lighttpd's own existing systemd supervision rather than adding a new supervised process.
- Safe to re-run repeatedly for redeploys (idempotent).
- Script fails loudly and specifically on missing prerequisites (SSH key, unreachable host, lighttpd missing/unrecognized) rather than leaving a half-deployed state silently.

**Non-Goals:**
- Zero-downtime/blue-green releases, release history, or rollback tooling — single personal feeder, single service, a few seconds of reload downtime is acceptable.
- Fleet/multi-target deployment, CI/CD pipeline integration, or a deploy UI — this is a manually-invoked personal script.
- Installing lighttpd (or any other web server) on the remote box — out of scope; the script checks lighttpd is present (it already is, for tar1090) and fails clearly rather than provisioning it.
- HTTPS/TLS termination in front of port 7500 — the user asked for the service to run on port 7500 directly; TLS can be layered on separately later if wanted.
- **Modifying tar1090's own site config, or uninstalling/disabling tar1090.** This change reads the decoder-feed location tar1090's installer already resolved (`/etc/default/tar1090_instances`, or the same `/run/*/aircraft.json` probe order it uses), and adds a new, separate lighttpd site config file of its own (`conf-available/98-squawkmap3d.conf`-style) — it never edits tar1090's own config file, and a `systemctl reload lighttpd` after adding it is the same graceful-reload operation tar1090's own installer performs when it installs itself.

## Decisions

### 1. "Static frontend" resolves to a literal static export (`output: "export"`) — verified viable

The user confirmed directly: a static frontend, not a running app server. Checked against the codebase rather than assumed:
- The only server-dependent piece is `app/api/health/route.ts` (`GET` returning a live timestamp). Next's own docs (`node_modules/next/dist/docs/01-app/01-getting-started/17-deploying.md`) mark static export as **"Limited"**: a dynamic route needs `export const dynamic = "force-static";` to be includable in a static export at all, which freezes its output at build time instead of per-request.
- Verified locally (reverted afterward, not left applied to the app source): added `output: "export"` to `next.config.js` and `export const dynamic = "force-static";` to the health route, ran `npm run build` — succeeds, produces `out/` containing the full app shell, all JS/CSS/vendored assets, and `out/api/health` (a plain file with the frozen JSON body). Served `out/` locally with a static file server — `/` and `/api/health` both correct.
- **Decision: static export.** `/api/health`'s `timestamp` becomes "time of last deploy" rather than "current time" — an accepted, minor behavior change (see Risks); the deploy script's own use of that endpoint is "did the new build get served," not liveness monitoring, so this doesn't weaken the health check.

### 2. Build locally; ship a pre-built payload, not source-to-build-on-box

- **(Chosen) Build on the developer's machine (`npm run build` with `output: "export"`), ship the resulting `out/` directory.** The feeder box never runs `npm install`, `tsc`, or a bundler — it only ever receives finished static files. Feeder SBCs are typically busy decoding ADS-B data and aren't sized for a Next.js/webpack build.
- **Rejected: `git pull` + `npm ci` + `npm run build` on the box.** Puts the full build toolchain and build-time resource cost on constrained hardware, for a target that doesn't even need a runtime at serve time.
- No cross-architecture risk to check: `out/` is plain HTML/CSS/JS/JSON/SVG — architecture-independent, safe to build on macOS and serve from the feeder's Linux/ARM box.

### 3. `NEXT_PUBLIC_*` env vars come from the local build machine, not the remote box

Next.js inlines `NEXT_PUBLIC_*` variables into the client JS bundle at `next build` time (confirmed in `node_modules/next/dist/docs/01-app/02-guides/self-hosting.md`). Since this design builds locally (Decision 2), the values already come from wherever `npm run build` runs — the developer's own `.env.local`, exactly like local dev already works. Confirmed via `grep -rn "process.env" components/` that all three of this app's env vars (`NEXT_PUBLIC_MAPTILER_KEY`, `NEXT_PUBLIC_OPENAIP_API_KEY`, `NEXT_PUBLIC_FEEDER_URL`) are browser-facing only; there are no private server-only env vars anywhere in the codebase. With a static export there is no remote runtime at all to configure.
- **Refined by Decision 6**: rather than needing the feeder's LAN IP/hostname baked in at build time, the deploy script standardizes `NEXT_PUBLIC_FEEDER_URL=/data/aircraft.json` — a build-time-fixed but *relative* URL, which resolves at request time against whatever origin the browser actually loaded the app from and requires no per-deploy edits once set. Still must be present in the *local* `.env.local` used at `npm run build` time; the deploy script's preflight checks for and, if missing/different, recommends this exact value. Documented in `README.md`.

### 4. Serving: a new lighttpd site config on the existing, already-systemd-supervised lighttpd — no new process, no new runtime

- The feeder box already runs lighttpd (tar1090 depends on it, per Context) as a systemd-managed service. Serving SquawkMap3D's static `out/` on port 7500 needs nothing more than a second lighttpd site config, `server.port = 7500` bound to `out/`'s deployed location, added as its own file (`/etc/lighttpd/conf-available/98-squawkmap3d.conf`, symlinked into `conf-enabled/`) — never editing tar1090's own conf file.
- **Rejected: `python3 -m http.server`.** Works, but is a new, unsupervised (no systemd unit, no crash-restart) foreground process to invent process-supervision for, when a supervised, crash-tolerant, restart-on-boot web server the box already runs and already knows how to reload is sitting right there.
- **Rejected: a Node process (standalone Next server or a bespoke static file server run via `node`).** Contradicts "static frontend" directly — a static export's whole point is no app server process; running one anyway to serve static files re-adds the exact thing being removed, for no benefit over reusing lighttpd.
- Reload, not restart-from-scratch: after adding/refreshing the site config, `systemctl reload lighttpd` (graceful, doesn't drop tar1090's own in-flight connections) picks up the new site — the same operation tar1090's own installer performs when it adds itself to lighttpd.
- Deploy target is one stable directory, `/opt/squawkmap3d`, updated in place via `rsync --delete` on every deploy (not a symlink-swapped `releases/<n>` pattern) — rejected release-symlink/rollback machinery as unnecessary ceremony for a single personal feeder (see Non-Goals).
- No `systemd` unit of this app's own is created — supervision, boot-start, and crash-restart are all inherited from lighttpd's existing one. Simpler than Decision 4's previous (now-superseded) Node/systemd-unit design, and there's nothing app-specific left to supervise once serving is just static files.

### 5. Deploy verification: poll `/api/health` over the network, from the deploying machine

After reloading lighttpd, the script polls `http://adsb-feeder.local:7500/api/health` (a handful of retries with a short backoff) and checks the response is valid JSON with `"status":"ok"` before declaring success — exercising the actual network path a user/browser would use, not just an SSH-local check. Since Decision 1 makes `/api/health` static, its `timestamp` reflects the deploy that produced the currently-served build, not "now" — the health check validates "the new build is being served," which is exactly what it needs to validate. Non-zero exit with a clear message if it never comes up healthy within the timeout.

### 6. Feeder-local aircraft feed: symlink tar1090's own decoder source into SquawkMap3D's served directory, same-origin — no CORS, no tar1090 config changes

This directly answers "drop-in replacement for tar1090" and the CORS question the "active server component" framing raised: tar1090's own aircraft.json has **no `Access-Control-Allow-Origin` header** (confirmed by reading `88-tar1090.conf` directly — see Context), so a cross-origin browser `fetch()` against it (SquawkMap3D on port 7500 vs. tar1090 on port 80/8504 — different origins to a browser even on the same host) would fail under CORS. Two ways to avoid that were considered:

- **Rejected: modify tar1090/lighttpd's own config to add a CORS header.** Would work, but violates the Non-Goal of never touching tar1090's own configuration, and is exactly the kind of change that could silently break on a tar1090 upgrade (its installer rewrites its own lighttpd confs).
- **Rejected: proxy the fetch through a Next.js API route.** Unnecessary — a same-origin static-asset symlink accomplishes the same CORS-avoidance without adding a new dynamic route just for this.
- **(Chosen) Symlink tar1090's own decoder-source `aircraft.json` into SquawkMap3D's own served directory, so it's fetched same-origin.** The deploy script resolves the live decoder's output directory on the remote box using tar1090's own already-resolved mapping — reading `/etc/default/tar1090_instances` (format: `<srcdir> <instance>` per line, written by tar1090's installer) if present, else falling back to the same ordered probe tar1090's own `install.sh` uses (`/run/dump1090-fa`, `/run/readsb`, `/run/adsbexchange-feed`, `/run/dump1090`, `/run/dump1090-mutability`, `/run/skyaware978`, `/run/shm`, each checked for `aircraft.json`). It then creates/refreshes a symlink, `<REMOTE_DIR>/data/aircraft.json -> <detected-srcdir>/aircraft.json`, after every `rsync` (rsync's `--delete` would otherwise remove a previously-created symlink each deploy, since it isn't part of the locally-built payload — recreating it post-sync, pre-reload, keeps this idempotent). `<REMOTE_DIR>/data/` already exists post-sync regardless, since the static export already ships `data/{airports,military-bases}.geojson` there (from `public/data/`); `aircraft.json` sits alongside them, no new directory needed.
- With that symlink in place, `NEXT_PUBLIC_FEEDER_URL=/data/aircraft.json` (Decision 3) resolves same-origin through the same lighttpd site already serving the rest of the app (Decision 4) — no CORS, no separate origin, no dependency on knowing the feeder's LAN IP, and tar1090's own files/config are never written to, only read (a plain filesystem probe over SSH).
- **If no known decoder source is found** (neither `/etc/default/tar1090_instances` nor any of the probed `/run/*/aircraft.json` paths exist), the deploy script does **not** fail the deploy over it: it logs a warning and skips the symlink step, leaving `/data/aircraft.json` absent. The app itself already degrades gracefully in that case — the in-flight `plane-tracks-3d-layer` change treats a failed/missing feed fetch as an empty aircraft layer, not an error (mirroring `tfr.ts`/`specialUseAirspace.ts`'s existing failure handling).

## Risks / Trade-offs

- **[Risk] Remote lighttpd absence/unrecognized layout**: the script assumes lighttpd is already installed and managed by systemd (true for a standard tar1090 install, per Context). → *Mitigation*: script checks for `lighttpd` and its systemd unit over SSH before building/shipping anything, and aborts with a clear message — including "this box doesn't look like a standard tar1090 install" — rather than partially deploying then failing at reload.
- **[Risk] Frozen `/api/health` timestamp**: static export means that endpoint reports "time of last deploy," not "now." → *Mitigation*: documented as an accepted, deliberate trade-off of Decision 1; the deploy script's own health check only needs "is the new build being served," which this still answers correctly.
- **[Risk, discovered and fixed] `output: "export"` breaks `next start`**: verified locally — after this change, `npm run start` (`next start`) fails with `"next start" does not work with "output: export" configuration"`, since static export produces no server for it to start. This isn't feeder-specific — it affects local usage of `npm run build && npm run start` on any machine. → *Mitigation*: `package.json`'s `start` script updated to `npx serve@latest out` (Next's own suggested replacement, printed in that exact error), so local production-preview usage keeps working.
- **[Risk] Decoder-source detection (Decision 6) is best-effort, tied to tar1090's own conventions**: if the feeder is ever migrated to a decoder/instance layout tar1090's own probe order doesn't recognize (or `/etc/default/tar1090_instances` is absent/stale), the symlink step silently no-ops rather than failing the deploy (by design), which means the aircraft layer would silently stay empty rather than erroring. → *Mitigation*: the deploy script logs clearly when it skips this step; `README.md`'s troubleshooting notes should mention checking for that log line first if aircraft don't show up after a deploy.
- **[Trade-off] Reading `/etc/default/tar1090_instances`/probing `/run/*/aircraft.json` couples this deploy script to tar1090-specific conventions**, not a generic "any ADS-B decoder" mechanism. Acceptable and deliberate: the user's stated requirement is specifically drop-in parity with their actual tar1090 install.
- **[Trade-off] Shared lighttpd process**: reusing the box's existing lighttpd (rather than a dedicated process for this app) means a `systemctl reload lighttpd` for this app's config change is a graceful, non-dropping operation on the *same process* tar1090 depends on — standard practice (identical to what tar1090's own installer itself does) and not expected to cause any disruption, but worth naming as a shared-resource touch rather than pretending it's fully isolated. No rollback tooling beyond redeploying a known-good commit; accepted per Non-Goals for a single personal feeder.

## Migration Plan

Purely additive: one line in `next.config.js` (`output: "export"`), one line in `app/api/health/route.ts` (`export const dynamic = "force-static";`), new files under `scripts/` (deploy script + lighttpd site-config template), a new `README.md` section. No new npm dependency. No changes to tar1090/readsb's own configuration or services (Decision 6, Non-Goals) — the remote box is only ever read from (probing for the decoder's `aircraft.json` location) and gains one new, separate lighttpd site config of its own; tar1090's own config file is never touched. Nothing depends on this change existing; rollback is deleting the new files, the `next.config.js`/health-route lines, and, on the box itself, removing `/etc/lighttpd/conf-enabled/98-squawkmap3d.conf` (and the `conf-available` source), `rm -rf /opt/squawkmap3d`, then `systemctl reload lighttpd` — tar1090 itself is untouched by both the deploy and this rollback.
