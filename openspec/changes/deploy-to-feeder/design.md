## Context

SquawkMap3D (Next.js 16 App Router, React 19) is a single-page, client-rendered MapLibre/deck.gl app (`app/page.tsx` is its only real page) plus one server-side piece, `app/api/health/route.ts` — a plain `GET` returning `{ status, service, timestamp: new Date().toISOString() }`. It has never been deployed anywhere but a developer's own `next dev`. The user wants it running persistently on their ADS-B feeder box: `root@adsb-feeder.local`, SSH key `~/.ssh/adsb_feeder`, port 7500, "a published static version of the codebase, not hot loaded," driven by a script.

Feeder boxes in this ecosystem (tar1090/readsb/ultrafeeder-style setups) are typically resource-constrained single-board computers (Raspberry Pi class) whose primary job is decoding ADS-B data — not compiling TypeScript/webpack bundles or running a general-purpose app runtime.

## Goals / Non-Goals

**Goals:**
- One script, run from a developer machine, that takes the current working tree to a running, auto-restarting service on `adsb-feeder.local:7500`.
- The deployed artifact is a genuine ahead-of-time production build — no dev-server hot-reload/watch behavior, no on-box compilation, no application runtime process required on the feeder box beyond a plain file server.
- Survives reboots and crashes on the feeder box without manual intervention (systemd).
- Safe to re-run repeatedly for redeploys (idempotent).
- Script fails loudly and specifically on missing prerequisites (SSH key, unreachable host, remote file-server runtime missing) rather than leaving a half-deployed state silently.

**Non-Goals:**
- Zero-downtime/blue-green releases, release history, or rollback tooling — single personal feeder, single service, a few seconds of restart downtime is acceptable.
- Fleet/multi-target deployment, CI/CD pipeline integration, or a deploy UI — this is a manually-invoked personal script.
- Installing any new runtime/package manager on the remote box beyond what it's assumed to already have (Python 3 — see Decision 1) — the script checks and fails clearly rather than provisioning system packages.
- HTTPS/TLS termination or a reverse proxy in front of port 7500 — the user asked for the service to run on port 7500 directly; a reverse proxy can be layered on separately later if wanted.
- Adding any new dynamic/server-side route to the app itself. If a future change needs one, it must first revisit Decision 1 (this deploy mechanism would need to move to a Node server — see that decision's trade-off).

## Decisions

### 1. "Published static version... not hot loaded" resolves to a literal static export (`output: "export"`) — verified viable, not assumed

This was the one genuinely ambiguous piece of the request. It's now resolved and empirically verified in this drafting session (no code left applied to the app — see below), triggered by the user directly asking whether a static build can do what tar1090 does given tar1090 "has an active server component":

- **Aircraft-data liveness never depended on this app's own server, static or not.** The in-flight `plane-tracks-3d-layer` change's design.md (Decision 3) fetches `aircraft.json` directly from the browser against `NEXT_PUBLIC_FEEDER_URL` — a separate, always-running service (the feeder box's own readsb/dump1090-fa decoder) — explicitly "mirrors how tar1090 itself works (browser fetches its own decoder's JSON directly)." tar1090's own apparent "active server component" is that same pattern: its web UI is static HTML/CSS/JS; the liveness comes from client-side polling against a JSON file a *separate* decoder process continuously rewrites, served by a plain static file server (lighttpd, in the standard tar1090 setup) — not from tar1090 running a dynamic app server. So whether SquawkMap3D itself is served statically or by a Node process has no bearing on whether aircraft data displays live.
- **What static export actually costs is narrow, and was checked, not assumed**: the only genuinely per-request-dynamic thing in this codebase is `app/api/health/route.ts`. Local experiment (reverted afterward — not left applied):
  1. Added `output: "export"` to `next.config.js` and ran `npm run build`. **Failed**: `Error: export const dynamic = "force-static"/export const revalidate not configured on route "/api/health" with "output: export"`.
  2. Added `export const dynamic = "force-static";` to `app/api/health/route.ts` and rebuilt. **Succeeded** — Next reports the whole app as static (`○ (Static) prerendered as static content`), producing `out/` containing `index.html`, all JS/CSS chunks, all vendored public assets (`aircraft-shapes/`, `aircraft-silhouettes/`, etc.), and `out/api/health` — a plain extensionless file containing the JSON body, frozen at build time (its `timestamp` field is the build time, not request time — the one real behavior change).
  3. Served `out/` locally with `python3 -m http.server`: `GET /` → 200 (the map app loads); `GET /api/health` → 200 with the correct JSON body (served with `Content-Type: application/octet-stream` since the file has no extension — cosmetic, the deploy script's health check doesn't depend on `Content-Type`).
  - This confirms static export is fully viable for this app today with exactly one required source change (`export const dynamic = "force-static";` on the health route) and no other code changes.
- **Decision: static export (A).** Matches the user's literal wording, and removes the biggest piece of ops complexity a Node-server approach would have needed (no Node.js runtime, no Node-version preflight, no long-running app process to supervise beyond a file server) — meaningful on feeder-class hardware. The `/api/health` timestamp becomes "time of last deploy" rather than "current time," which is an acceptable, explicitly-documented behavior change (see Risks) since the deploy script's own use of that endpoint is just "did the new build get served," not liveness monitoring.
- **Rejected: standalone Node server** (`output: "standalone"` + `next start`/`server.js`, the option explored earlier in this session before the user's question prompted re-checking the aircraft-liveness assumption). Would have kept `/api/health` genuinely live and left headroom for a future dynamic route, at the cost of requiring Node ≥20.9 on the feeder box and a supervised Node process instead of just static files. Rejected because nothing in this app today needs that headroom, and it directly contradicts the user's own "static" wording once the (mistaken) belief that live aircraft data required a server was corrected.
- **If a future change adds a genuinely dynamic server-side route**, this decision must be revisited before that change can deploy through this same mechanism — noted in Non-Goals and Risks.

### 2. Build locally; ship a pre-built payload, not source-to-build-on-box

- **(Chosen) Build on the developer's machine (`npm run build` with `output: "export"`), ship the resulting `out/` directory.** The feeder box never runs `npm install`, `tsc`, or a bundler — it only ever receives finished static files. This matters because feeder SBCs are typically busy decoding ADS-B data and are not sized for a Next.js/webpack build; it also matches "published static version" directly (ship a finished artifact, don't build in place).
- **Rejected: `git pull` + `npm ci` + `npm run build` on the box.** Puts the full build toolchain (TypeScript, ESLint deps, webpack) and the resource cost of a full build on constrained hardware, competing with the feeder's actual job, for a target that (per Decision 1) doesn't even need a Node runtime at serve time.
- No cross-architecture risk to check here (unlike a Node/`sharp`-style native-binary concern): `out/` is plain HTML/CSS/JS/JSON/SVG — architecture-independent, safe to build on macOS and serve from the feeder's Linux/ARM box via any static file server.

### 3. `NEXT_PUBLIC_*` env vars come from the local build machine, not the remote box

Next.js inlines `NEXT_PUBLIC_*` variables into the client JS bundle at `next build` time (confirmed in `node_modules/next/dist/docs/01-app/02-guides/self-hosting.md`). Since this design builds locally (Decision 2), the values already come from wherever `npm run build` runs — the developer's own `.env.local`/`.env.production.local`, exactly like local dev already works. Confirmed via `grep -rn "process.env" components/` that all three of this app's env vars (`NEXT_PUBLIC_MAPTILER_KEY`, `NEXT_PUBLIC_OPENAIP_API_KEY`, `NEXT_PUBLIC_FEEDER_URL`) are browser-facing only; there are no private server-only env vars anywhere in the codebase. With a static export there is no remote runtime at all to configure — no `Environment=` plumbing needed in the systemd unit beyond the port the file server binds to.
- **Caveat surfaced for the user**: if they intend to point `NEXT_PUBLIC_FEEDER_URL` at the feeder's own local `aircraft.json` once this app runs on that same box, that value must be set in the *local* `.env.local` used at `npm run build` time before running the deploy script — it cannot be changed later by editing anything on the remote box; a redeploy (rebuild + re-run the script) is required to change it. Documented in `README.md`.

### 4. Process supervision: systemd unit running `python3 -m http.server`, root-owned, single stable directory

- No Node.js (or any other new runtime) is required on the feeder box (Decision 1). The remaining question is what serves the static `out/` payload on port 7500. Verified locally: Python 3's standard-library `http.server` module correctly serves both `/` (the app shell) and the extensionless `out/api/health` file with the right bytes. Python 3 is near-universally preinstalled on Debian/Raspberry Pi OS-class images (the common base for ADS-B feeder builds), so this adds no new package-install requirement in the common case — the script still checks for it and fails clearly if absent (see Goals), rather than assuming.
- **Rejected: assume/require nginx or lighttpd already configured.** tar1090 setups commonly run lighttpd, but that's not guaranteed (many feeder images are Docker/container-based, where a bare host-level lighttpd may not exist or may not be easily reachable from a deploy script without knowing that image's specific layout). `python3 -m http.server` needs no configuration file, no site/vhost setup, and no assumption about what else is installed — simpler and more portable across whatever the box's ADS-B software actually is, at the cost of being a minimal, single-threaded, non-production-grade file server. Acceptable: this is one browser, on a LAN, requesting a modest set of static assets — not internet-scale traffic. Revisit if that stops being true.
- systemd is the natural fit for a root-accessible Linux box: `Restart=on-failure` for crash recovery, `WantedBy=multi-user.target` + `systemctl enable` for boot persistence, `journalctl -u squawkmap3d` for logs.
- The unit runs as root (no `User=` line), matching the only access this design has (root over SSH) and the single-owner, single-purpose nature of this box. Deliberate trade-off, not an oversight — a dedicated least-privilege system user would be better practice but adds provisioning this script doesn't otherwise need for a personal box with no multi-tenant concern today.
- Deploy target is one stable directory, `/opt/squawkmap3d`, updated in place via `rsync --delete` on every deploy (not a symlink-swapped `releases/<n>` pattern) — rejected release-symlink/rollback machinery as unnecessary ceremony for a single personal feeder (see Non-Goals). `systemctl restart` after every sync (not just `enable --now`, which doesn't restart an already-running unit) ensures a redeploy actually serves the new build — though note `http.server` reads files per-request from disk, so even without a restart, an in-place `rsync` would already serve updated file contents on the next request; the explicit restart is kept anyway for consistency/simplicity of reasoning (one clear "deploy = restart" mental model) rather than relying on that implementation detail.

### 5. Deploy verification: poll `/api/health` over the network, from the deploying machine

After restarting the service, the script polls `http://adsb-feeder.local:7500/api/health` (a handful of retries with a short backoff) and checks the response is valid JSON with `"status":"ok"` before declaring success — exercising the actual network path a user/browser would use, not just an SSH-local `systemctl is-active` check (which would miss port-binding/firewall/network issues). Per Decision 1, this endpoint's `timestamp` field now reflects build time, not request time — the health check only asserts the endpoint is reachable and well-formed, not that the timestamp is "fresh." Non-zero exit with a clear message if it never comes up healthy within the timeout.

## Risks / Trade-offs

- **[Accepted behavior change] `/api/health`'s `timestamp` is frozen at build time, not live.** A direct, understood consequence of Decision 1, not a bug. If genuine request-time liveness is ever needed for this endpoint specifically, it would need to move outside the static export (e.g., a tiny separate always-on process) or the whole deploy mechanism would need to revisit Decision 1.
- **[Risk] Remote Python 3 absence**: the script assumes `python3` is present on the feeder box. → *Mitigation*: script checks `python3 --version` over SSH before building/shipping anything and aborts with a clear message, rather than partially deploying then failing at `systemctl start`.
- **[Risk] `python3 -m http.server` is not a production-grade server** (single-threaded, no gzip, minimal error handling, `Content-Type: application/octet-stream` for extensionless files like `/api/health`). → *Mitigation*: accepted for this scale (one personal box, LAN-local, one browser at a time); revisit (e.g., swap in a `lighttpd`/`nginx` config if one already exists on the box) if that assumption stops holding.
- **[Risk] Root-owned service**: no privilege separation. → *Mitigation*: documented as an accepted trade-off for this single-purpose personal box (Decision 4); not a change to make silently later without calling it out.
- **[Trade-off] No rollback tooling**: a bad deploy must be fixed by redeploying a known-good commit, not by an automated rollback command. Accepted per Non-Goals.
- **[Risk] Future dynamic routes break this deploy mechanism**: if the app ever needs a genuine per-request server route beyond what static export supports, this whole approach (and Decision 1) needs revisiting before that feature can ship to the feeder. Flagged so that isn't discovered the hard way mid-implementation of some unrelated future change.

## Migration Plan

Purely additive: one line in `next.config.js` (`output: "export"`), one line in `app/api/health/route.ts` (`export const dynamic = "force-static";`), two new files under `scripts/`, a new `README.md` section. No existing app behavior changes beyond the health endpoint's timestamp semantics (Risks). No new npm dependency. Nothing depends on this change existing; rollback is deleting the new files and the two source lines and, on the box itself, `systemctl disable --now squawkmap3d && rm -rf /opt/squawkmap3d /etc/systemd/system/squawkmap3d.service`.

## Open Questions

- Should the deploy script also offer a `--rollback`/`--to <ref>` mode later? Left as a follow-up per the Non-Goals; not blocking this change.
- Should a reverse proxy (nginx/Caddy) be added in front of port 7500 for TLS or request hardening? Out of scope per Non-Goals — the user asked specifically for the service on port 7500 directly.
- If the feeder box turns out to already run lighttpd (common in tar1090 setups) with spare vhost capacity, should the deploy script prefer reusing it over `python3 -m http.server`? Left as a possible follow-up refinement, not required — `python3 -m http.server` was chosen specifically to avoid depending on an assumption about what's already configured on the box (Decision 4).
