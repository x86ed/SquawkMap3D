## Context

SquawkMap3D (Next.js 16 App Router, React 19) is a single-page, client-rendered MapLibre/deck.gl app (`app/page.tsx` is its only real page) plus one server-side piece, `app/api/health/route.ts` — a plain `GET` returning `{ status, service, timestamp: new Date().toISOString() }`. It has never been deployed anywhere but a developer's own `next dev`. The user wants it running persistently on their ADS-B feeder box: `root@adsb-feeder.local`, SSH key `~/.ssh/adsb_feeder`, port 7500, "a published static version of the codebase, not hot loaded," driven by a script — explicitly, "a drop-in replacement for [wiedehopf/tar1090](https://github.com/wiedehopf/tar1090) which runs locally on my feeder," sideloaded alongside it for testing without breaking it, and: **"ship something in typescript if you need backend infra on this. i don't want to mix languages."**

That last constraint directly overturned this design's original serving-mechanism choice (see Decision 1) — an earlier iteration of this document had settled on a literal static export served by Python's `python3 -m http.server`, verified working, but introducing Python as new remote runtime infra was exactly the kind of language-mixing the user ruled out. This is scoped to *backend/serving infrastructure that runs on the feeder box* — the local deploy script itself (bash, orchestrating `ssh`/`rsync`/`systemctl`) is ops tooling, not application infra, and isn't what "backend infra" refers to here.

Feeder boxes in this ecosystem (tar1090/readsb/ultrafeeder-style setups) are typically resource-constrained single-board computers (Raspberry Pi class) whose primary job is decoding ADS-B data. The user's feeder specifically runs wiedehopf/tar1090, whose actual install mechanics were fetched and read directly from its GitHub repo during this drafting session (`install.sh`, `88-tar1090.conf`) rather than assumed, since "drop-in replacement" only means something concrete once tar1090's own serving/data-source mechanics are known:

- tar1090's installer configures **lighttpd**, aliasing `/<instance>/` (default instance name `tar1090`, so `/tar1090/`) to its HTML dir, and `/<instance>/data/` to a detected **decoder source directory** — found by checking, in order: `/run/dump1090-fa`, `/run/readsb`, `/run/adsbexchange-feed`, `/run/dump1090`, `/run/dump1090-mutability`, `/run/skyaware978`, `/run/shm`, each for the presence of `aircraft.json`. Once resolved, this mapping is persisted to `/etc/default/tar1090_instances` (format: `<srcdir> <instance-name>` per line) for reuse on reinstall/upgrade.
- tar1090's own lighttpd config for `/<instance>/data/aircraft.json` sets `Cache-Control: no-cache` **only** — confirmed by reading `88-tar1090.conf` directly, **no `Access-Control-Allow-Origin` header** is set on that path (unlike its `chunks/*.gz` replay-data paths, which do get `Access-Control-Allow-Origin: "*"`). This means a cross-origin `fetch()` (different port = different origin to a browser, even on the same host) against tar1090's own aircraft.json will fail under CORS unless something is done about it — directly relevant to how SquawkMap3D reads feeder data once deployed onto this same box (see Decision 6).
- tar1090 also has a well-known convention of exposing itself "directly" (root-aliased) on a fixed secondary port, `8504` (confirmed as a literal, hardcoded default in `install.sh`'s generated `95-tar1090-otherport.conf`), separate from its `/tar1090/`-prefixed path on the main vhost (typically port 80). SquawkMap3D's requested port, 7500, doesn't collide with either.

## Goals / Non-Goals

**Goals:**
- One script, run from a developer machine, that takes the current working tree to a running, auto-restarting service on `adsb-feeder.local:7500`.
- The deployed artifact is a genuine ahead-of-time production build — no dev-server hot-reload/watch behavior, no on-box compilation.
- All backend/serving infrastructure that runs on the feeder box is TypeScript/Node.js — the same stack as the rest of this codebase. No new language runtime (Python, etc.) introduced as application infra, per explicit user constraint.
- Functions as a sideloaded, parallel viewer alongside tar1090 for testing — once deployed, SquawkMap3D shows this feeder's own live aircraft, read from the same underlying decoder output tar1090 itself reads, without requiring the user to hand-configure a feeder URL/IP per deploy and without needing any CORS workaround or touching tar1090's own configuration (see Decision 6). Data/functional parity with tar1090, not an install-level replacement — **tar1090 ("the original map") must keep working, untouched, throughout** (confirmed explicitly by the user; see spec.md's "Deploy does not interfere with the feeder's existing tar1090 install" requirement).
- Survives reboots and crashes on the feeder box without manual intervention (systemd).
- Safe to re-run repeatedly for redeploys (idempotent).
- Script fails loudly and specifically on missing prerequisites (SSH key, unreachable host, remote runtime too old/missing) rather than leaving a half-deployed state silently.

**Non-Goals:**
- Zero-downtime/blue-green releases, release history, or rollback tooling — single personal feeder, single service, a few seconds of restart downtime is acceptable.
- Fleet/multi-target deployment, CI/CD pipeline integration, or a deploy UI — this is a manually-invoked personal script.
- Installing Node.js itself on the remote box, or managing the feeder's other software (readsb, tar1090, etc.) — out of scope; the script checks Node is present and fails clearly rather than provisioning it.
- HTTPS/TLS termination or a reverse proxy in front of port 7500 — the user asked for the service to run on port 7500 directly; a reverse proxy can be layered on separately later if wanted.
- **Modifying tar1090's, readsb's, or lighttpd's own configuration, or uninstalling/disabling tar1090.** This change only *reads* the location tar1090's installer already resolved (`/etc/default/tar1090_instances`, or the same `/run/*/aircraft.json` probe order it uses) to link SquawkMap3D's own copy of the feed — it never writes to tar1090/readsb/lighttpd's files or services.

## Decisions

### 1. "Published static version... not hot loaded" resolves to a production Node server (`next build` + standalone `server.js`) — revised from a literal static export after an explicit no-mixed-languages constraint

This went through two iterations in this drafting session, both grounded in verification rather than assumption:

- **First resolution: literal static export (`output: "export"`)**, triggered by the user asking whether a static build can do what tar1090 does. Verified locally (build succeeded, `python3 -m http.server` correctly served both the app shell and `/api/health` as a static file, with one required source line: `export const dynamic = "force-static";` on the health route). This was a legitimate, working design — but it required *some* static file server on the remote box, and Python's stdlib `http.server` was the server chosen for it (see the now-superseded Decision 4 reasoning, no longer in this document).
- **Overturned by the user's explicit constraint**: *"ship something in typescript if you need backend infra on this. i don't want to mix languages."* Python, even just as a thin stdlib file server, is exactly the kind of new-language backend infra this rules out. That forces reconsidering what serves the app on the box — and every non-Node static-file-server option (Python, or assuming lighttpd/nginx are already configured a certain way) has the same problem: it's not TypeScript/Node.
- **Final decision: standalone Node server.** `output: "standalone"` in `next.config.js` is Next's own documented minimal self-host output (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/output.md`): `next build` traces and copies only the files needed to run into `.next/standalone/server.js`, plus a pruned `node_modules` — no bespoke server code to write, and it's generated *from this codebase's own build*, not a separate language. Node.js is already this project's fundamental runtime (it's what `next dev`/`next build` themselves require) — requiring it on the deploy target isn't introducing a new dependency, it's reusing the one the project already has. This also restores `/api/health` to genuinely live (no `force-static` workaround needed — reverting that experimental one-line change entirely, see Migration Plan) and keeps headroom for any future dynamic route with zero deploy-mechanism rework.
- **Rejected: literal static export + Python file server** (the prior resolution). Directly violates the user's language constraint once stated explicitly; not revisited further.
- **Rejected: static export + a bespoke TypeScript static file server**, written and compiled locally, shipped as plain JS, run via `node`. Would have satisfied both "static... not hot loaded" *and* "no mixed languages," but is strictly more code to write/maintain (a hand-rolled file server with its own edge cases — MIME types, symlink handling, range requests) than just using Next's own standalone server, which already does all of that correctly and is a single `next.config.js` line. Rejected as unnecessary reinvention once the standalone option was back on the table for the language-constraint reason above.

### 2. Build locally; ship a pre-built payload, not source-to-build-on-box

- **(Chosen) Build on the developer's machine (`npm run build` with `output: "standalone"`), ship the resulting `.next/standalone/` + `public/` + `.next/static/`.** The feeder box never runs `npm install`, `tsc`, or a bundler — it only ever receives a finished, traced server bundle plus static assets, per Next's documented standalone-copy steps: `cp -r public .next/standalone/ && cp -r .next/static .next/standalone/.next/`. This matters because feeder SBCs are typically busy decoding ADS-B data and are not sized for a Next.js/webpack build.
- **Rejected: `git pull` + `npm ci` + `npm run build` on the box.** Puts the full build toolchain (TypeScript, ESLint deps, webpack) and the resource cost of a full build on constrained hardware, competing with the feeder's actual job.
- Cross-architecture risk was checked, not assumed: this app does not use `next/image` anywhere (`grep -rn "next/image" app components` — no matches), and the only native `.node` addon in `node_modules` is `fsevents` (macOS-only, a dev-time `chokidar` dependency, never traced into the standalone server output). So the standalone payload is pure JS/JSON/assets — safe to build on macOS and run on the feeder's Linux/ARM box. If `next/image` optimization (which depends on the native `sharp` binary) is ever adopted, this decision must be revisited.

### 3. `NEXT_PUBLIC_*` env vars come from the local build machine, not the remote box

Next.js inlines `NEXT_PUBLIC_*` variables into the client JS bundle at `next build` time (confirmed in `node_modules/next/dist/docs/01-app/02-guides/self-hosting.md`). Since this design builds locally (Decision 2), the values already come from wherever `npm run build` runs — the developer's own `.env.local`, exactly like local dev already works. Confirmed via `grep -rn "process.env" components/` that all three of this app's env vars (`NEXT_PUBLIC_MAPTILER_KEY`, `NEXT_PUBLIC_OPENAIP_API_KEY`, `NEXT_PUBLIC_FEEDER_URL`) are browser-facing only; there are no private server-only env vars anywhere in the codebase today. The deploy script only needs `PORT`/`HOSTNAME` as true remote-runtime env vars (set in the systemd unit, per Next's documented standalone-server convention), which control the server's bind address/port, not app behavior.
- **Refined by Decision 6**: rather than needing the feeder's LAN IP/hostname baked in at build time, the deploy script standardizes `NEXT_PUBLIC_FEEDER_URL=/data/aircraft.json` — a build-time-fixed but *relative* URL, which resolves at request time against whatever origin the browser actually loaded the app from (`adsb-feeder.local:7500`, a LAN IP, `localhost`, all interchangeably) and requires no per-deploy edits once set. Still must be present in the *local* `.env.local` used at `npm run build` time; the deploy script's preflight checks for and, if missing/different, recommends this exact value. Documented in `README.md`.

### 4. Process supervision: systemd unit running `node server.js`, root-owned, single stable directory

- systemd is the natural fit for a root-accessible Linux box: `Restart=on-failure` for crash recovery, `WantedBy=multi-user.target` + `systemctl enable` for boot persistence, `journalctl -u squawkmap3d` for logs — no extra runtime dependency (unlike pm2/forever, which would need installing on the box, and unlike a hand-rolled server, per Decision 1).
- The unit runs as root (no `User=` line), matching the only access this design has (root over SSH) and the single-owner, single-purpose nature of this box. Deliberate trade-off, not an oversight — a dedicated least-privilege system user would be better practice but adds provisioning this script doesn't otherwise need for a personal box with no multi-tenant concern today.
- Deploy target is one stable directory, `/opt/squawkmap3d`, updated in place via `rsync --delete` on every deploy (not a symlink-swapped `releases/<n>` pattern) — rejected release-symlink/rollback machinery as unnecessary ceremony for a single personal feeder (see Non-Goals). `systemctl restart` after every sync (not just `enable --now`, which doesn't restart an already-running unit) ensures a redeploy actually serves the new build.
- Per Next's documented standalone-output convention: `PORT` and `HOSTNAME` environment variables control the server's bind address/port (`Environment=PORT=7500`, `Environment=HOSTNAME=0.0.0.0` in the systemd unit) — `HOSTNAME=0.0.0.0` is required for the service to be reachable from other machines on the LAN, not just from the feeder box itself.

### 5. Deploy verification: poll `/api/health` over the network, from the deploying machine

After restarting the service, the script polls `http://adsb-feeder.local:7500/api/health` (a handful of retries with a short backoff) and checks the response is valid JSON with `"status":"ok"` before declaring success — exercising the actual network path a user/browser would use, not just an SSH-local `systemctl is-active` check (which would miss port-binding/firewall/network issues). Since Decision 1 keeps `/api/health` a genuinely dynamic route, its `timestamp` reflects the actual moment the health check ran, not build time — a small bonus over the (now-superseded) static-export path. Non-zero exit with a clear message if it never comes up healthy within the timeout.

### 6. Feeder-local aircraft feed: symlink tar1090's own decoder source into SquawkMap3D's served directory, same-origin — no CORS, no tar1090 config changes

This directly answers "drop-in replacement for tar1090" and the CORS question the "active server component" framing raised: tar1090's own aircraft.json has **no `Access-Control-Allow-Origin` header** (confirmed by reading `88-tar1090.conf` directly — see Context), so a cross-origin browser `fetch()` against it (SquawkMap3D on port 7500 vs. tar1090 on port 80/8504 — different origins to a browser even on the same host) would fail under CORS. Two ways to avoid that were considered:

- **Rejected: modify tar1090/lighttpd's own config to add a CORS header.** Would work, but violates the Non-Goal of never touching tar1090's own configuration, and is exactly the kind of change that could silently break on a tar1090 upgrade (its installer rewrites its own lighttpd confs).
- **Rejected: proxy the fetch through a Next.js API route.** Unnecessary — a same-origin static-asset symlink accomplishes the same CORS-avoidance without adding a new dynamic route just for this.
- **(Chosen) Symlink tar1090's own decoder-source `aircraft.json` into SquawkMap3D's own served directory, so it's fetched same-origin.** The deploy script resolves the live decoder's output directory on the remote box using tar1090's own already-resolved mapping — reading `/etc/default/tar1090_instances` (format: `<srcdir> <instance>` per line, written by tar1090's installer) if present, else falling back to the same ordered probe tar1090's own `install.sh` uses (`/run/dump1090-fa`, `/run/readsb`, `/run/adsbexchange-feed`, `/run/dump1090`, `/run/dump1090-mutability`, `/run/skyaware978`, `/run/shm`, each checked for `aircraft.json`). It then creates/refreshes a symlink, `<REMOTE_DIR>/public/data/aircraft.json -> <detected-srcdir>/aircraft.json`, after every `rsync` (rsync's `--delete` would otherwise remove a previously-created symlink each deploy, since it isn't part of the locally-built payload — recreating it post-sync, pre-restart, keeps this idempotent). The path is under `public/` specifically because that's where Next's standalone server serves static assets from at the site root (per its documented `cp -r public .next/standalone/` step) — `public/data/` already exists post-sync regardless, since the app already ships `public/data/{airports,military-bases}.geojson` there; `aircraft.json` sits alongside them, no new directory needed.
- With that symlink in place, `NEXT_PUBLIC_FEEDER_URL=/data/aircraft.json` (Decision 3) resolves same-origin through the same Node server already serving the rest of the app (Decision 4) — no CORS, no separate origin, no dependency on knowing the feeder's LAN IP, and tar1090's own files/config are never written to, only read (a plain filesystem probe over SSH).
- **If no known decoder source is found** (neither `/etc/default/tar1090_instances` nor any of the probed `/run/*/aircraft.json` paths exist), the deploy script does **not** fail the deploy over it: it logs a warning and skips the symlink step, leaving `/data/aircraft.json` absent. The app itself already degrades gracefully in that case — the in-flight `plane-tracks-3d-layer` change treats a failed/missing feed fetch as an empty aircraft layer, not an error (mirroring `tfr.ts`/`specialUseAirspace.ts`'s existing failure handling).

## Risks / Trade-offs

- **[Risk] Remote Node.js version/absence**: the script assumes Node ≥20.9 (Next 16's `engines.node` floor, per `node_modules/next/package.json`) is already installed on the feeder box. → *Mitigation*: script checks `node --version` over SSH before building/shipping anything and aborts with a clear message, rather than partially deploying then failing at `systemctl start`.
- **[Risk] Root-owned service**: no privilege separation. → *Mitigation*: documented as an accepted trade-off for this single-purpose personal box (Decision 4); not a change to make silently later without calling it out.
- **[Trade-off] No rollback tooling**: a bad deploy must be fixed by redeploying a known-good commit, not by an automated rollback command. Accepted per Non-Goals.
- **[Risk] Decoder-source detection (Decision 6) is best-effort, tied to tar1090's own conventions**: if the feeder is ever migrated to a decoder/instance layout tar1090's own probe order doesn't recognize (or `/etc/default/tar1090_instances` is absent/stale), the symlink step silently no-ops rather than failing the deploy (by design), which means the aircraft layer would silently stay empty rather than erroring. → *Mitigation*: the deploy script logs clearly when it skips this step; `README.md`'s troubleshooting notes should mention checking for that log line first if aircraft don't show up after a deploy.
- **[Trade-off] Reading `/etc/default/tar1090_instances`/probing `/run/*/aircraft.json` couples this deploy script to tar1090-specific conventions**, not a generic "any ADS-B decoder" mechanism. Acceptable and deliberate: the user's stated requirement is specifically drop-in parity with their actual tar1090 install.
- **[Superseded, noted for history] The literal-static-export + Python path explored earlier in this session was fully working** (verified: build succeeded, `python3 -m http.server` served the app and `/api/health` correctly) but is not what's being implemented — overturned by the explicit no-mixed-languages constraint. Recorded here so a future reader doesn't wonder why static export was considered and then abandoned.

## Migration Plan

Purely additive: one line in `next.config.js` (`output: "standalone"`), two new files under `scripts/`, a new `README.md` section. `app/api/health/route.ts` needs **no changes** (the `export const dynamic = "force-static";` line explored during the now-superseded static-export iteration was never committed to the app — see Decision 1). No new npm dependency. No changes to tar1090/readsb/lighttpd's own configuration or services (Decision 6, Non-Goals) — the remote box is only ever read from (probing for the decoder's `aircraft.json` location) before SquawkMap3D's own directory/service is created. Nothing depends on this change existing; rollback is deleting the new files and the `next.config.js` line and, on the box itself, `systemctl disable --now squawkmap3d && rm -rf /opt/squawkmap3d /etc/systemd/system/squawkmap3d.service` — tar1090 itself is untouched by both the deploy and this rollback.

## Open Questions

**Confirmed by the user as non-issues** — the core ask is tar1090 parity (reading its own live feed) and running SquawkMap3D on port 7500 on the same box; the following are explicitly not concerns to solve for in this change:
- A `--rollback`/`--to <ref>` mode.
- A reverse proxy (nginx/Caddy) in front of port 7500 for TLS or request hardening.
- Multiple/second tar1090 decoder instances — auto-detection via `/etc/default/tar1090_instances` (falling back to the standard probe order) covers the single-decoder setup described by the user; not being generalized further.
