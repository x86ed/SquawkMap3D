## Context

`PlaneCard.tsx`/`PlaneCard.module.css` currently render a single, non-flipping `.aircraftRarityFrame > .aircraftTierCard` face: header row (type badge, manufacturer, model, tightly-cropped silhouette SVG) plus a stat region below (empty state, feeder-UUID form, error state, or the real stat grid/XP bar). A `ResizeObserver`-driven `transform: scale()` contain-fits the whole frame into its grid cell. The sibling `iconizer` project's icon/card preview panel (`iconizer/3D-modeler/src/card.ts` + `style.css`) independently evolved a two-face flip-card version of the *same* concept — explicitly ported from and standardized against this app's `PlaneCard.tsx` per its own doc comments — adding a front face (identity header, rarity/level pills, silhouette, XP panel) alongside a back face that is essentially this app's current single face, joined by a pure-CSS `perspective`/`rotateY(180deg)`/`backface-visibility: hidden` flip on `:hover`. This design brings that two-face structure into `PlaneCard`, reversed to show the back (stats) face by default per the acceptance criteria, and keeps the click-to-`adsb.win`-dashboard behavior `PlaneCard` already has, extended to both faces.

## Goals / Non-Goals

**Goals:**
- Port the two-face flip-card DOM structure and CSS (`.card-frame`/`.card-inner`/`.card-face-front`/`.card-face-back`) from `iconizer/3D-modeler/src/card.ts` and `style.css` into `PlaneCard.tsx`/`PlaneCard.module.css`, translated to this app's CSS Modules naming and React (JSX) authoring instead of `iconizer`'s template-string HTML.
- Make the back face (current identity+stats content) the default-shown face; hovering (or, since this card can be touch-only, an equivalent focus/tap affordance already used elsewhere in the app if hover-only proves insufficient — see Open Questions) flips to the front face.
- Preserve the existing whole-card click behavior (open `https://adsb.win/dashboard/aircraft/{TYPE}` in a new tab) across both faces, still excluding clicks on the feeder-UUID form's interactive children.
- Preserve the existing `ResizeObserver` contain-fit scaling behavior, rarity-tier-driven gradient border/glow (including `mythic`/`apex` sheen), and all existing `cardStats`-driven stat-region states (empty, not-configured, invalid-token, error, ok+XP bar) — none of this app's existing data/logic changes, only where that content is rendered.

**Non-Goals:**
- No changes to `aircraftModelCard.ts`, `tierProgress.ts`, `feederUuid.ts`, `manufacturerModel.ts`, `aircraftShapes.ts`, `computeTightViewBox`, or any other data-fetching/computation logic; `PlaneCardProps` gains exactly one new field (`showBack`, see Decision 2) and is otherwise unchanged.
- No new front-face-only data: the front face's identity/pills/silhouette/XP panel reuse exactly the same props this component already receives (`typeDesignator`, `manufacturerModel`, `rarityTier`, `cardStats`) — nothing new is fetched or passed in.
- Not adopting `plens-win/Card` as an npm dependency; `iconizer`'s local re-implementation is the ported source, matching this app's existing "vendor/port, don't add a runtime dependency for a small self-contained UI piece" pattern (e.g. `aircraftShapes.ts`'s vendored SVGs).
- Not changing the overlay's four-component layout, grid/stacking behavior, or any other overlay component (`RecordPanelHero`, `TelemetryMarquee`, `FlightInfoPane`).

## Decisions

**Decision 1 — Source the flip markup/CSS from `iconizer`, not from `plens-win/Card` directly.**
`iconizer/3D-modeler/src/card.ts`'s own doc comments state it was "ported/adapted from `PlaneCard.tsx`" and its flip mechanics were "ported from https://codepen.io/edeesims/pen/wvpYWW per user request" to match `plens-win/Card`'s look — i.e. it is already a proven, working, dependency-free local implementation of the same design the acceptance criteria point at, in a sibling project on this same machine, with no network fetch required. Porting from it is strictly less risky than re-deriving the same structure from the external `plens-win/Card` GitHub repo from scratch. Alternative considered: clone/inspect `plens-win/Card` directly — rejected as redundant extra work with no benefit, since `iconizer`'s version is already the ported, standardized-to-this-app result of doing exactly that.

**Decision 2 — Back face default via a `showBack` prop selecting the resting `rotateY` offset, not a hardcoded CSS default or a JS flip-state toggle.**
`iconizer`'s `.card-inner{transform-style:preserve-3d}` / `.card-frame:hover .card-inner{transform:rotateY(180deg)}` shows the front face by default and flips to the back on hover, entirely in CSS with no re-render needed to animate. This change keeps that hover-driven flip mechanism (still no `useState`, no click-to-flip toggle logic) but makes which face rests forward a first-class, explicit prop: `PlaneCardProps.showBack?: boolean` (default `true`). `PlaneCard` sets `.cardInner`'s resting `transform` inline/via a data attribute from this prop — `showBack === true` (the default) rests at `rotateY(180deg)` so the back face (authored at `rotateY(180deg)` per the flip technique) faces forward at rest, and hovering returns it to `rotateY(0deg)`, revealing the front face; `showBack === false` rests at `rotateY(0deg)` (front face forward at rest) and hovering goes to `rotateY(180deg)`. Every view currently mounting `PlaneCard` (`AircraftOverlay`) gets `showBack`'s default (`true`) applied automatically, and is updated to pass `showBack={true}` explicitly so the behavior is visible and controllable at each call site rather than an invisible CSS-only convention with no per-view override path. Alternative considered: hardcode the base/`:hover` transform swap directly in CSS with no prop — rejected per explicit request that the back-default behavior be an enabled-by-default *flag* views loading the card set, not an unconfigurable CSS constant, since a future view (e.g. a gallery/browse context) may reasonably want front-by-default. Alternative considered: track flip state in React and toggle a class on click/tap — rejected as unnecessary complexity when the existing card already handles clicks for adsb.win navigation; overloading click for both "flip" and "navigate" would also conflict with the required click-through behavior below.

**Decision 3 — Whole-card click-through onto both faces, unchanged destination and exclusions.**
The current single-face `onClick` on `.aircraftTierCard` — opening `https://adsb.win/dashboard/aircraft/{typeDesignator}` in a new tab, skipping clicks inside `form, input, button, a` — moves onto both `.card-face-front` and `.card-face-back` (or one shared handler on `.card-inner`/`.card-frame`, since only one face is interactable at a time given `backface-visibility: hidden`). No new URL scheme is introduced; "the new card library ... on click ... take the user to adsb.win page for the aircraft" describes behavior this component already implements. Alternative considered: link out to `iconizer`'s `card-front-author`/`card-credit-link` per-operator adsb.win *profile* links instead of the aircraft dashboard — rejected; those links serve a different purpose (crediting an operator handle this app has no equivalent field for) and the acceptance criteria specifically asks for "the adsb.win page for the aircraft", which is the dashboard-per-type-designator URL this card already uses.

**Decision 4 — Front face renders using only existing props; no new data fetch.**
`iconizer`'s front face's level/rarity pills and XP panel are populated from the same `cardStats`/rarity-tier data its back face (and this app's existing single face) already uses — nothing in the front face requires data this component doesn't already receive. The silhouette art slot (mounted separately in `iconizer` via `card-wireframe.ts`, since that app renders a live 3D wireframe) is simplified here to reuse this app's own existing tightly-cropped 2D silhouette `<svg>` (`useTightAircraftShapeViewBox`/`getAircraftShape`) on the front face, since `PlaneCard` has no 3D-modeling capability or need for one — the 3D wireframe is specific to `iconizer`'s modeling tool, not part of the flip-card design itself.

## Risks / Trade-offs

- [Risk] Reversing which face is "default" vs. `plens-win/Card`'s/`iconizer`'s own front-default convention could read as an unintentional bug to anyone comparing directly against the upstream design. → Mitigation: this reversal is an explicit acceptance criterion ("make the back not the front show by default"), documented here and in the updated `aircraft-info-overlay` spec scenarios, so it's traceable as intentional.
- [Risk] Hover-only flip has no equivalent on touch devices (no persistent hover state), which could leave touch users unable to ever see the front face. → Mitigation: out of scope for this change per the acceptance criteria (which only specifies default-face and click-through behavior, not touch-flip parity); flagged as an Open Question below rather than silently shipping a touch regression relative to today's card (today's card has only one face, so touch users lose nothing they had — this is a pre-existing `iconizer`-inherited limitation of the ported hover mechanic, not a regression this change introduces).
- [Risk] Porting hand-authored template-string HTML/CSS from a different app (different build tooling, no CSS Modules, no React) risks subtle class-name collisions or specificity differences once translated into `PlaneCard.module.css`. → Mitigation: CSS Modules already scopes all class names locally, and the port keeps `iconizer`'s existing class *names* (`cardFrame`, `cardInner`, `cardFaceFront`, `cardFaceBack`, etc., camelCased for CSS Modules) so the two implementations stay easy to diff against each other going forward.

## Open Questions

- Should a tap-to-flip (or explicit flip affordance) be added for touch devices in a follow-up, given hover-only flip is unusable on touch? Not addressed by the stated acceptance criteria for this change.
