## 6. Dark-theme screen blend (WebGL)

Added after 1-5 above were already verified working, per explicit user request for a true blend mode in dark theme (a flat alpha-blended fill, even after the region fix in 5.4's round 3, still just washes the map toward one flat tint instead of brightening it while preserving underlying detail). See design.md's addendum for the full rationale/alternatives considered.

- [x] 6.1 Add `earcut` as an explicit dependency (`npm install earcut`) — already present transitively via `maplibre-gl`/`@turf/turf` (which use it internally for the same polygon-triangulation problem), pinned explicitly since this is now a direct, load-bearing usage.
- [x] 6.2 In new `components/map/terminatorGL.ts`, implement `TerminatorScreenBlendLayer`, a MapLibre `CustomLayerInterface`: compiles a minimal GLSL ES 3.00 vertex/fragment shader pair, triangulates each band polygon with `earcut` and projects vertices to Mercator world space via `MercatorCoordinate.fromLngLat` in `updateBands` (once per data refresh, not per frame), and in `render` sets `gl.blendFunc(gl.ONE_MINUS_DST_COLOR, gl.ONE)` (the fixed-function-blending trick for a true "screen" blend) before drawing each band, restoring MapLibre's documented default blend func afterward. Exposes `updateBands(bands)` and `setVisible(visible)` (the latter calling `map.triggerRepaint()` for an immediate visual update, since custom layers have no `layout.visibility` property).
- [x] 6.3 In `components/map/terminator.ts`, branch `addTerminatorLayers`/`refreshTerminator`/`setTerminatorVisibility` on `theme`: light theme keeps the original `fill`-layer/GeoJSON-source path unchanged; dark theme creates/reuses a module-level `TerminatorScreenBlendLayer` instance instead, calling `updateBands`/`setVisible` on it. Removed the now-unused `TERMINATOR_REGION_FOR_THEME`/per-theme `BAND_FILL_COLOR`/`BAND_FILL_OPACITY` records (light theme's are now plain constants; dark theme's color/opacity live in `terminatorGL.ts` instead).
- [x] 6.4 Add `TERMINATOR_GL_LAYER_ID` to the exported `TERMINATOR_LAYER_IDS` list so `layers.ts`'s pilot-mode exemption (`CUSTOM_LAYER_IDS`) still covers it.
- [x] 6.5 Manually verify: no WebGL/console errors after load, theme toggle, and terminator toggle. Verified via real-Chromium automation with console-error capture (empty) across a load → toggle-off → toggle-on → theme-swap-to-light → theme-swap-back-to-dark sequence; `map.getLayer("day-night-terminator-gl")` confirmed present before and after the swap round-trip.
- [x] 6.6 Manually verify the screen-blended dark-theme overlay visibly preserves underlying map detail (coastlines, basemap texture) through the brightened day region, rather than washing it to a flat tint. Confirmed via screenshot comparison against the prior alpha-blended version.
- [x] 6.7 First tuning pass on `BAND_TINT` for perceptibility: the initial value (`[0.16, 0.18, 0.22]`) read as barely noticeable per direct user feedback. Verified a doubled value (`[0.32, 0.36, 0.42]`) via a decoded-screenshot pixel measurement (2D canvas `getImageData`, not raw WebGL `readPixels`, which returns all-zero for MapLibre's canvas without `preserveDrawingBuffer`) showing a large brightness swing. **This measurement was misleading** — see 6.9: the sampled row was contaminated by bright airport/military pin markers scattered across the map, unrelated to the terminator itself, so the swing didn't actually confirm what it appeared to.
- [x] 6.8 Fixed a real, separate bug surfaced while investigating the user's follow-up "still isn't working" report: `terminator.ts` held the dark-theme `TerminatorScreenBlendLayer` instance in a module-level `let glLayer` variable. Every HMR reload of `terminator.ts`/`terminatorGL.ts` (routine during active development) re-executes the module, resetting that variable to `null` — but React Fast Refresh doesn't tear down the already-running map, so MapLibre still holds the *original* instance internally via `map.addLayer`. After any such reload, `updateBands`/`setVisible` calls were silently no-oping on the stale `null` reference (optional chaining swallows it), freezing the layer at whatever state it had before the reload — reproduced directly via a Playwright script that triggers a real file-touch HMR reload on a live page and confirms this. Fixed by removing the module variable entirely: `getGLLayer(map)` in `terminator.ts` recovers the live instance via `map.getLayer(TERMINATOR_GL_LAYER_ID).implementation` (MapLibre's own `CustomStyleLayer` wrapper) every time, so there's no separate piece of state that can drift out of sync with what's actually attached to the map.
- [x] 6.9 With the HMR bug fixed and ready to re-measure cleanly, redid the pixel-brightness comparison with airports/military-base markers hidden first — this changed the picture: `[0.32, 0.36, 0.42]`'s "126-point swing" from 6.7 was largely those pins, not the terminator. A zoomed-in screenshot at the exact current subsolar point (computed directly, not guessed) with `[0.32, 0.36, 0.42]` showed a **perfectly flat color with zero visible coastline/basemap detail** — repeated same-color screen blending across 8 stacked bands converges aggressively (`1-(1-x)^N`; at `x=0.32`, ~95-99% brightness), washing the whole daylight core toward the same near-white value regardless of what's underneath. That's the opposite of the point of using screen blend (brighten while preserving detail) — a flat wash is just what the original alpha-blended `fill` layers already did. Retuned to `[0.11, 0.12, 0.14]` (≈62-72% convergence at full 8-stack, leaving real headroom for detail) — confirmed via the same zoomed-in-core screenshot that coastlines/labels/borders now stay clearly visible while still reading noticeably brighter than the hidden state.
- [x] 6.10 Honest limitation, not resolved further: at typical whole-world zoom, the brightened region is still fairly subtle next to the airport/military markers and general visual density — the zoomed-in-core view is where the effect reads clearly. This is an inherent tension (strong enough to notice at a glance vs. weak enough to preserve underlying detail everywhere it applies, including the small fully-overlapped core), not a bug; `[0.11, 0.12, 0.14]` is a deliberate middle point between the two failed extremes (6.7's too-weak, 6.9's too-strong original value), not a final word — further tuning is a matter of taste/priority the user can weigh in on.
